# Журнал решений

Формат: контекст → решение → отвергнутые варианты.

## D-001. Версии стека (Этап 0)
- **Контекст:** ТЗ раздел 3 — Laravel 13.x, Filament 5.x, Livewire 4; резервы Laravel 12 / Filament 4.
- **Решение:** Laravel 13, Filament 5, Livewire 4 (через Filament), Pest, Larastan 3 (уровень 5). Все поддерживают PHP 8.3. Резервные версии не понадобились.
- **Отвергнуто:** Laravel 12 / Filament 4 — нет причин.

## D-002. intervention/image версии 3
- **Контекст:** в Packagist доступна 4.x, ТЗ требует 3.x с драйвером GD.
- **Решение:** `intervention/image:^3`, драйвер GD.
- **Отвергнуто:** 4.x — расходится с ТЗ, нет выигрыша для задачи.

## D-003. Роли пользователей
- **Контекст:** ТЗ 6.13 — роль в `users.role`, права через политики, без пакетов ролей.
- **Решение:** enum `App\Enums\UserRole` (`admin`, `manager`), колонки `users.role` (varchar, default `manager`) и `users.is_active`. Доступ в панель — `User::canAccessPanel()` (активен + есть роль). Страницы настроек, пользователи и «Система» — только `admin` (`canAccess()` / политики).

## D-004. Путь админки
- **Решение:** `config('shop.admin_path')` из `ADMIN_PATH` (по умолчанию `admin`), передаётся в `->path()` панели Filament.

## D-005. Отметка планировщика (heartbeat, AD-11)
- **Контекст:** нужна отметка последнего запуска планировщика, без Redis.
- **Решение:** `shop:heartbeat` пишет время в файл `storage/app/heartbeat` (не зависит от драйвера кэша и очищения кэша при деплое `optimize:clear`). Чтение — через сервис `App\Services\System\Heartbeat`.
- **Отвергнуто:** кэш (сбрасывается при `optimize:clear`/`cache:clear`), отдельная таблица (лишняя миграция ради одного значения).

## D-006. Деньги
- **Решение:** в БД `decimal(12,2)`; в коде — целые копейки (`int`) через value-объект/хелпер `App\Support\Money`, форматирование `1 290 ₽`. Без float.

## D-007. Composer в песочнице
- **Контекст:** скачивание dist-архивов с GitHub через прокси песочницы возвращает 403.
- **Решение:** Composer автоматически переходит на git-клоны; установка медленнее, но работает. На CI (GitHub Actions) ограничения нет.

## D-008. Alpine.js на витрине
- **Контекст:** витрина использует Livewire 4 (корзина, формы), а Livewire поставляет Alpine.js в своём бандле.
- **Решение:** не ставить `alpinejs` отдельно из npm; на всех страницах витрины подключать скрипты Livewire (`@livewireScripts`), Alpine берётся оттуда. Так нет двойной инициализации, а JS витрины меньше (NF-03).
- **Отвергнуто:** отдельный пакет `alpinejs` в Vite — конфликт двух экземпляров Alpine.

## D-009. Деньги в настройках — целые копейки
- **Контекст:** настройки (spatie/laravel-settings) хранятся в JSON; float в JSON и в форме ведёт к ошибкам округления (D-006).
- **Решение:** все денежные значения в настройках — `int` в копейках (`min_order_amount`, `price` и `free_from` способов получения). В формах Filament сумма вводится в рублях (допустимы `1 290,50`, `1290.5`, `1 290 ₽`; правило `App\Rules\RublesAmount`); перевод рубли ↔ копейки — только через `App\Support\Money` (`fromRubles`, `toRubles`, `format`) в `mutateFormDataBeforeFill/Save` страницы. Разбор строки — через bcmath, дробные копейки округляются half-up.
- **Отвергнуто:** строки `"0.00"` в настройках (приходится парсить при каждом расчёте); float.

## D-010. Настройки: кэш, миграции, секреты
- **Решение:** кэш пакета включён (`SETTINGS_CACHE_ENABLED`, по умолчанию `true`, хранилище — `CACHE_STORE`, т.е. `file`); при сохранении кэш группы сбрасывается пакетом. Миграция таблицы `settings` лежит в `database/migrations`, значения по умолчанию — в `database/settings/*` (путь в `settings.migrations_paths`), так что `php artisan migrate` создаёт всё одной командой. Токен Telegram хранится зашифрованным (`NotificationSettings::encrypted()`), в миграции значение `null`, реальные значения не засеиваются. Для шифрования нужен `APP_KEY` — в `phpunit.xml` задан тестовый ключ.
- **Ограничение пакета:** `phpdocumentor/type-resolver` не разбирает array shapes (`array{...}`) и `mixed` в `@var` — у свойств-массивов с вложенными массивами (`delivery_methods`, `payment_methods`, `social_links`, `blocks`) `@var` не указывается, структура описана обычным комментарием.

## D-011. Админка: формат дат, пароль, навигация
- **Решение:** форматы Filament задаются глобально в `AppServiceProvider` (`Table`, `Schema`, `DateTimePicker`): `d.m.Y`, `d.m.Y H:i`, `H:i`, валюта `rub`. Минимальная длина пароля 10 (NF-12) — через `Password::defaults()`, действует и в форме пользователя, и при сбросе пароля Filament. Порядок групп меню (AD-03) задан в `AdminPanelProvider::navigationGroups()` строками из `lang/ru/shop.php`; страницы и ресурсы возвращают ту же строку из `getNavigationGroup()`. Название бренда берётся из `GeneralSettings::shop_name` (при недоступной таблице — `config('app.name')`).
- **Доступ:** `canAccessPanel()` = `is_active`; страницы настроек и `UserResource` — только администратор (трейт `AdminOnlySettingsPage`, `UserPolicy`); администратор не может удалить сам себя. Менеджер получает 403 и не видит пункты в меню.

## D-012. Сессия, логи, тесты Livewire
- **Решение:** `SESSION_LIFETIME` по умолчанию 480 минут (NF-12); лог по умолчанию `daily`, хранение 14 дней (NF-21); `APP_TIMEZONE` (по умолчанию `Europe/Moscow`), локаль `ru`, faker `ru_RU`. Livewire-компоненты в тестах вызываются через `Livewire\Livewire::test()` — пакет `pest-plugin-livewire` не добавлялся (правило «пакеты только из раздела 3»).
- **Формат денег на витрине:** `Money::format()` — разряды узким неразрывным пробелом (U+202F), перед `₽` обычный неразрывный пробел (U+00A0), копейки показываются только если не нули: `1 290 ₽`, `1 290,50 ₽`.

## D-013. Шрифты витрины
- **Контекст:** шаблон Laravel подключал шрифт Instrument Sans с fonts.bunny.net через Vite-плагин; сборка зависит от внешнего хоста, а витрина — от стороннего CDN (NF-03, приватность).
- **Решение:** системный стек шрифтов, без внешних шрифтов.
- **Отвергнуто:** самостоятельный хостинг веб-шрифта — лишний вес для NF-03; можно добавить позже.

## D-014. CI на MySQL
- **Решение:** в `ci.yml` отдельная задача с сервисом `mysql:8.0`; переменные `DB_*` заданы на уровне задачи и имеют приоритет над `<env>` из `phpunit.xml` (без `force="true"`). Тесты не требуют сборки Vite (`withoutVite()`).

## D-015. Итоговая цена до Этапа 2
- **Контекст:** витрина и админка Этапа 1 используют `products.final_price`, а калькулятор цен (PR-01) появится на Этапе 2.
- **Решение:** сервис `App\Services\Pricing\ProductPriceUpdater` уже сейчас пишет `final_price`/`display_old_price`/`price_calculated_at` при сохранении товара по упрощённому правилу: `final = fixed_price ?? base_price`, `old = compare_at_price`, если он больше `final`. На Этапе 2 внутренняя логика заменяется на `PriceCalculator`, точка вызова остаётся.

## D-016. SalesModeResolver на Этапе 1
- **Контекст:** карточке товара в списке (SF-15) и колонке «Режим» (AD-40) нужен действующий режим продаж, а продажи реализуются на Этапе 4.
- **Решение:** на Этапе 1 создаётся `App\Services\Sales\SalesModeResolver` с определением режима (цена по запросу → товар → ближайшая категория → магазин) и источника. Поправки на наличие и рабочие кнопки появятся на Этапе 4; пока кнопки ведут на карточку товара.

## D-017. Разделение AD-42
- **Решение:** массовое изменение базовой цены (±% / ±₽ с предпросмотром) реализуется на Этапе 2 вместе с историей цен (PR-06) и правом «только администратор». Экспорт выбранных товаров в Excel — на Этапе 3 вместе с экспортом каталога (EX-01). Остальные массовые действия — на Этапе 1.

## D-018. Редиректы при смене slug (SF-80)
- **Решение:** при смене slug товара/категории в `redirects` пишется `from_path` (старый путь) → `to_path` (новый). Существующие редиректы, ведущие на старый путь, переписываются на новый (без цепочек); редирект, у которого `from_path` совпал с новым путём, удаляется. Проверка выполняется только для 404 на витрине (обработчик исключений / fallback), поэтому обычные запросы не платят лишним SQL-запросом.

## D-019. Поиск (SF-20)
- **Решение:** `products.search_text` = нормализованные (нижний регистр, ё→е, одиночные пробелы) название + артикул + бренд. Запрос нормализуется так же, разбивается на слова, для каждого слова `search_text LIKE %слово%` (AND). Точное совпадение артикула поднимается первым через `ORDER BY CASE WHEN LOWER(sku) = ? THEN 0 ELSE 1 END`. Спецсимволы `%`/`_` экранируются. Без полнотекстовых индексов (переносимость SQLite/MySQL 5.7).

## D-020. Обработка фото (AD-50…53)
- **Решение:** `App\Services\Media\ImageProcessor` (intervention/image 3, GD): ориентация по EXIF, варианты 1600/800/400 px по длинной стороне (без увеличения), WebP 80, если `imagetypes() & IMG_WEBP`, иначе JPEG 85. Пути `products/{product_id}/{uuid}-{size}.webp|jpg` на диске `public`. Исходник после обработки удаляется. В админке файлы загружаются во временный каталог Livewire и обрабатываются при сохранении товара; ошибка одного файла не мешает остальным (уведомление с именем файла).

## D-021. Подсчёт товаров в дереве категорий (AD-30)
- **Решение:** одним запросом получаем число товаров по `category_id`, затем суммируем по материализованным путям в PHP (без N+1 и без CTE). Дерево категорий кэшируется (NF-04) и сбрасывается при изменении категорий.

## D-022. Ассеты Filament
- **Решение:** `php artisan filament:upgrade` выполняется в `post-autoload-dump` Composer; опубликованные ассеты (`public/css|js|fonts/filament`) не хранятся в git и создаются при `composer install` — локально и в CI-сборке релиза перед загрузкой на Beget (на сервере Composer не нужен).

## D-023. Фильтр «Режим» в таблице товаров (AD-41)
- **Решение:** фильтр «Режим» использует собственную настройку режима продаж товара (`inherit` = `null`), а не действующий режим: действующий режим зависит от дерева категорий и настроек магазина и не хранится в таблице. Колонка «Режим» при этом показывает действующий режим (с источником).

## D-024. Арифметика PriceCalculator (PR-01)
- **Решение:** все суммы — целые копейки (`int`). Процент: `round_half_up(price * value / 100)` через bcmath (value — `decimal(12,4)` строкой), результат каждого шага сразу округляется до копейки. Фиксированные наценки/скидки — в копейках. Цена после фазы скидок не ниже 0.
- Округление: шаг в рублях (1/10/50/100), направление вверх/к ближайшему (половина — вверх)/вниз; «психологическая» −1 ₽ только при шаге ≥ 10 и если результат > 0. Округление применяется, если сработало хотя бы одно правило или в настройках выбрано «ко всем»; без правил при «только изменённые» цена не округляется.
- `cost_markup_percent` у товара без закупочной цены пропускается (в объяснении — шаг «пропущено: нет закупочной цены»).

## D-025. Старая цена и настройки показа
- **Решение:** `display_old_price` всегда считается по алгоритму 6.8 (и используется фильтром «Со скидкой» и меткой «Скидка»). Настройки «показывать старую цену / % скидки» влияют только на вывод на витрине.

## D-026. Загрузка правил и кэш
- **Решение:** `PriceRuleRepository` один раз загружает все активные правила с целями (2 запроса) и держит их в памяти процесса и в кэше (`pricing.rules`, сбрасывается при изменении правил); отбор по периоду — по переданному времени внутри калькулятора. Совпадение по категориям — через `CategoryTree::descendantIds` (флаг «включая подкатегории»).

## D-027. Пересчёт при изменении правил и прогресс (PR-02, PR-05)
- **Решение:** при сохранении/удалении/включении правила вычисляется множество затронутых товаров = товары, подходящие под область правила до изменения ∪ после изменения (для области «все» — все товары). Id ставятся в очередь задачами `RecalculatePrices` по 500 штук. Прогресс хранится в кэше (`pricing.recalc`: total/done), баннер в админке читает его; по завершении ключ удаляется.
- `--boundaries`: правила, у которых `starts_at` или `ends_at` попали в интервал (последний запуск, сейчас], последний запуск хранится в кэше (по умолчанию окно 16 минут).

## D-028. История цен (PR-06)
- **Решение:** `PriceHistoryRecorder` пишет изменения `base_price`, `cost_price`, `fixed_price`, `compare_at_price` из наблюдателя товара. Источник и `import_id` задаются контекстом (`PriceChangeContext`, по умолчанию «вручную» + текущий пользователь); массовое действие и импорт оборачивают изменения в свой контекст. Изменения `final_price` от правил не пишутся.

## D-029. PR-07 на Этапе 2
- **Решение:** на Этапе 2 гарантируется, что `final_price` — единственный источник итоговой цены (витрина, админка). Фиксация цены в корзине и сравнение при оформлении реализуются вместе с корзиной на Этапе 4.

## D-030. Пересчёт цен при «сырых» изменениях входных данных (PR-02)
- **Решение:** всё, что пишет `category_id`, `is_featured`, `is_new` или `path` категорий мимо наблюдателя товара, ставит пересчёт затронутых товаров в очередь через `PriceRuleRecalculator::dispatch()` (задачи по 500): массовые «Перенести в категорию» и «Задать/снять метки»; перенос ветки категорий (`CategoryObserver::saved` — товары категории и всех её потомков); удаление категории с переносом товаров (`CategoryTree::deleteMovingToParent`). Всегда без проверки, есть ли правила по категориям (простота важнее оптимизации). Настройки «Цены»: при смене округления/психологической цены ставится пересчёт всех товаров (`PriceRuleRecalculator::dispatchAll()`, тот же код, что у `shop:recalc-prices --all`); переключатели показа старой цены/% скидки пересчёта не требуют. Восстановление товара из корзины пересчитывает цену в наблюдателе (`needsUpdate`).
- Черновик нового правила в предпросмотре получает id `PHP_INT_MAX` (новое правило получит наибольший id и применится последним при равном приоритете); у редактируемого правила — настоящий id.
- Прогресс (`RecalculationProgress`) — необязательные данные: при `LockTimeoutException` пишем предупреждение в лог и пропускаем обновление. Отметка последнего запуска `--boundaries` хранится в файле `storage/app/pricing-boundaries-last-run` (переживает `optimize:clear` при деплое).

## D-031. Границы значений и диапазон дат (PR-01)
- **Решение:** наценка в процентах (`markup_percent`, `cost_markup_percent`) ≤ 1000 %; фиксированные суммы правила ≤ 99 999 999,99 ₽ — предел колонки `price_rules.value decimal(12,4)` (8 цифр в целой части; значение 9 999 999 999,99 в неё не помещается). `PriceCalculator` после каждого шага и после округления ограничивает цену максимумом `decimal(12,2)` (999 999 999 999 коп.).
- Колонки `price_rules.starts_at/ends_at`, `products.price_calculated_at`, `price_history.created_at` — `dateTime` вместо `timestamp` (у MySQL `timestamp` кончается в 2038 году). Миграции этапа 2 ещё не выпущены, поэтому правятся на месте.

## D-032. Массовое изменение цены — в очереди (AD-42)
- **Решение:** действие не меняет цены в HTTP-запросе. `BulkPriceChanger::computeTargets()` считает для выбранных товаров (пачками по 100) `id => [old, new]` в копейках; `dispatch()` режет их на задачи `ApplyBulkPriceChange` по ≤ 200 товаров (≈ 4 мс на товар — укладывается в 40 с). Задача получает автора действия явно (в очереди нет сессии) и выполняет `applyTargets()` в контексте «bulk»: под `lockForUpdate` обновляет только товар, у которого `base_price` по-прежнему равен ожидаемому «старому», остальные пропускает и считает — повтор или ретрай не применит изменение дважды. Источник истории — `bulk`, пользователь — автор.
- Жёсткий лимит выделения — 20 000 товаров (`config('shop.bulk_price_max_selection')`), больше — отказ с сообщением. Пользователь получает уведомление «Изменение цен поставлено в очередь: N товаров». Серверная проверка `changePrices` (`abort_unless`) сохраняется и покрыта тестом на прямой вызов Livewire от менеджера.

## D-033. Конвейер импорта (IM-01…IM-15)
- **Контекст:** Beget — только cron + database-очередь, задача ≤ 40 с, память ≤ 128 МБ; повторное чтение .xlsx для каждой пачки дорого.
- **Решение:**
  1. Загрузка: исходный файл (и ZIP) на приватный диск `local` в `imports/{id}/`; запись `imports` со статусом `uploaded`.
  2. Сопоставление колонок: `ColumnMapper` по заголовкам (без регистра/пробелов/знаков, синонимы приложения A, `Х:`/`Характеристика:` → характеристики); последнее сопоставление берётся из предыдущего импорта по совпадающим заголовкам.
  3. Анализ (задача `AnalyzeImport`): один потоковый проход по файлу — строки нормализуются и пишутся в промежуточный файл `imports/{id}/rows.jsonl`, параллельно считаются сводка «создано/обновлено/пропущено/ошибки» (без записи в каталог) и первые 20 строк для предпросмотра. Лист «Категории» — в отдельный `categories.jsonl`.
  4. Обработка: пачка = 200 строк промежуточного файла (смещение в байтах хранится в `imports`), каждая пачка — своя транзакция. Захват пачки атомарный (`UPDATE imports SET next_chunk = n+1 WHERE id = ? AND next_chunk = n`), поэтому очередь и резервный режим из браузера (IM-10) не обрабатывают одну пачку дважды. Повтор безопасен: идемпотентность по артикулу.
  5. Фото обрабатываются после коммита данных пачки, вне транзакции, с бюджетом времени; если бюджет исчерпан, оставшиеся фото уходят в следующую задачу.
  6. Завершение: полная синхронизация (деактивация отсутствующих), пересчёт цен затронутых товаров, сброс кэшей, событие `ImportFinished` (на него подпишется генерация sitemap на Этапе 5), уведомление в колокольчик Filament.
- **Отвергнуто:** перечитывание исходного файла для каждой пачки (O(n²) по времени для .xlsx); таблица строк в БД (лишний объём в MySQL на shared-хостинге).

## D-034. CSV: кодировка и разделитель (IM-01)

## D-035. Загрузка фото по URL (IM-11)

Таймаут 15 с, ≤ 10 МБ (обрыв по превышению), `Content-Type: image/*` и проверка содержимого, одна повторная попытка. Кэш «URL → файл» в рамках импорта. Ошибка фото — предупреждение в отчёте.

## D-039. Фоновый экспорт каталога одним проходом (EX-03)

- **Решение:** `ExportCatalog` пишет файл целиком в одной задаче (timeout 40, без повторов). Если на Beget время приблизится к лимиту — разбить на части с дозаписью (техдолг при необходимости).

## D-040. Фото на собственном хранилище и счётчик «без изменений» (EX-01, IM-06, IM-12)
- **Контекст:** экспорт пишет в ячейку «Фото» полные URL собственного хранилища (`{APP_URL}/storage/products/{id}/{file}`); повторный импорт скачивал их по HTTP, удалял старые снимки и создавал новые (другие uuid, на каждом цикле), а фото категорий пересоздавались при каждом импорте. Строка без реальных изменений считалась «обновлённой».
- **Решение:**
  1. `OwnMediaLocator` узнаёт «свою» ссылку: относительный путь под URL публичного диска (`/storage/…`) или абсолютный URL с хостом из `APP_URL` / URL диска `public`. Для товара ищется `ProductImage` по `path_large|medium|small` (с ограничением по `product_id` из пути).
  2. Снимок того же товара считается уже имеющимся: не скачивается, не удаляется в режиме «заменить» (входит в «новый набор»), порядок строки применяется как обычно. Снимок другого товара копируется с локального файла через `ImageProcessor` (без HTTP; `source_hash = sha1('own:'.path_large)`, поэтому повтор не создаёт копий). Ссылка на ещё не существующий файл — обычная ссылка (скачивание/ошибка).
  3. Категория: ячейка равна URL текущего `image_path` — картинка не трогается; чужой собственный файл копируется локально.
  4. «Обновлено» считается только если изменился товар (`isDirty()` до сохранения) или его фото (добавлены/удалены/переставлены). Остальные строки — новый счётчик `imports.unchanged_count` (также `analysis.result.unchanged`, отчёт «Без изменений», уведомление). Строки с фото классифицирует шаг фото (задача несёт флаг `unchanged`), поэтому повторный импорт демо-файла даёт `updated = 0`, `unchanged = 50`, а `updated_at` товаров не меняется.

## D-041. Фото последней пачки не теряются при конкурентном завершении (IM-09, IM-10)
- **Контекст:** задачи фото жили в памяти после снятия блокировки; второй исполнитель (очередь + резервный режим браузера) видел «нет файлов фото» и завершал импорт, удаляя `downloads/` и `media/`.
- **Решение:**
  1. Задачи фото пачки записываются в `imports/{id}/photos-working-{label}.json` ещё под блокировкой `run`, до её снятия; после работы файл удаляется, при исчерпании бюджета переименовывается в `photos-pending-{label}.json`, при исключении возвращается в pending.
  2. `finish()` берёт блокировку `run` (пока исполнитель между захватом пачки и записью файла — не завершаем) и требует отсутствия и pending-, и working-файлов.
  3. После каждого скачивания/снимка исполнитель делает `touch` файла и обновляет `last_activity_at` (кнопка резервного режима не появляется, пока фото идут). Working-файл без обновлений дольше `STALE_CLAIM_SECONDS` (120 с — как у захваченной пачки) считается брошенным и возвращается в pending. Обработка идемпотентна по `source_hash`, скачивания кэшируются на время импорта.

## D-042. Жёсткий дедлайн запроса и задачи (IM-10, раздел 2)
- **Решение:** бюджет передаётся вниз как дедлайн (`microtime(true)`): браузерный запрос — `ImportRunner::BROWSER_BUDGET` = 18 с (ТЗ: ≤ 20 с), задача очереди — `ProcessesImportSteps::BUDGET` = 30 с (лимит задачи 40 с).
  - `ImageFetcher::fetch(..., $deadline)`: загрузка не начинается, если до дедлайна меньше `MIN_WINDOW` = 4 с (бросает `ImageFetchDeadlineException` — это не ошибка фото: ничего не кэшируется и не пишется в отчёт); таймаут запроса = `min(15, остаток − 2)`.
  - `ImportPhotoProcessor` проверяет дедлайн перед каждой загрузкой и перед каждым прикреплением снимка; недоделанная задача возвращается в pending с отметками (`warned` — какие ссылки уже дали предупреждение, `photos_changed`), продолжение не создаёт дублей.
  - Шаг данных пачки (200 строк) дедлайном не прерывается — он быстрый: замер на 10 000 строк (50 пачек, SQLite) — ≈ 0,6 с на пачку вместе с созданием категорий; MySQL — ≈ 0,7 с. Запрос браузера = шаг данных (≤ ~1 с) + фото до 18 с + хвост одного снимка в GD (≈ 1 с).
- Прокси из окружения (`HTTP_PROXY`/`HTTPS_PROXY`) для загрузки фото отключены явно (`proxy => ''`, `CURLOPT_PROXY => ''`): иначе закрепление IP (`CURLOPT_RESOLVE`, D-035) не действует.

## D-043. Анализ и резервный режим: блокировка и повторы
- **Анализ:** `ImportAnalyzer::analyze()` выполняется под `Cache::lock("import:{id}:analyze")` (120 с) и проверкой статуса под ней (`uploaded|analyzing` → `analyzing`; условный `UPDATE` не годится — MySQL возвращает число изменённых, а не найденных строк); проигравший (задача очереди и «Проверить сейчас» одновременно, либо повторный вызов для уже проанализированного импорта) ничего не делает и не переписывает `rows.jsonl`.
- **Резервный режим браузера:** исключение шага не останавливает импорт сразу (очередь даёт 3 попытки): пачка откатывается и освобождается, клиенту уходит `503 {retry: true, more: true}`, JS повторяет запрос с паузой 2 с → 4 с → 8 с. Счётчик ошибок подряд — в кэше (`import:{id}:browser_failures`), сбрасывается успешным шагом; на 3-й ошибке подряд импорт получает статус «ошибка».

## D-044. Лимит временной загрузки Livewire 50 МБ — глобальный
- **Контекст:** файл импорта (IM-01) может быть до 50 МБ, а Livewire применяет правило `temporary_file_upload.rules` ко всем компонентам; настроить его для одного компонента нельзя (оно проверяется на общем маршруте `livewire/upload-file` до создания компонента).
- **Решение:** оставляем `max:51200` в `config/livewire.php` глобально. Реальные ограничения задаёт каждое поле загрузки: фото товара и категории — `PhotoUpload::effectiveMaxBytes()` (≤ 10 МБ), логотип/OG/заглушка — 2 МБ, favicon — 512 КБ, файл импорта и ZIP — `ImportWizard::maxUploadBytes()`; тест `tests/Unit/UploadLimitsTest.php` проверяет, что у каждого `FileUpload` в `app/Filament` есть `maxSize`. Практический предел зависит от `upload_max_filesize`/`post_max_size` хостинга (`shop:doctor`).

## D-045. Номера обращений

## D-046. Остатки и «под заказ» (StockService, приложение B)
- **Решение:** все изменения `stock_qty`/`reserved_qty` — только через `StockService` в транзакции с `lockForUpdate()` строк товаров (в порядке id, чтобы исключить взаимоблокировки). Учёт выполняется, если включён в настройках и у товара `stock_qty IS NOT NULL`.
- Фактически списанное/зарезервированное количество хранится в технических полях позиции `order_items.stock_applied_qty` (и флаг `orders.stock_applied`), возврат при отмене/истечении — ровно на это количество (идемпотентно).
- Без «под заказ» остаток не может уйти в минус: при нехватке обращение не создаётся. С «под заказ» списывается только доступное количество (остаток не уходит ниже 0), недостающее — «под заказ».
- Импорт пишет остатки через `StockService::setStock()` (абсолютное значение под блокировкой).

## D-050. Детали ядра продаж (Этап 4)
- Ключи способов получения/оплаты — `Str::slug(name)` с суффиксами `-2`, `-3` для дублей, вычисляются по всем строкам (деактивация не сдвигает ключи); в обращении хранится название способа (снимок).
- При разрешённом «под заказ» количество в корзине не ограничивается остатком (`maxQty = null`); резерв всегда ограничен доступным остатком (`maxReserveQty`).
- Возврат/снятие/выкуп резерва ориентируются на `orders.stock_applied` (а не на текущий переключатель учёта), чтобы корректно закрывать обращения, созданные при включённом учёте. Списание и удержание при выключенном учёте не выполняются. `setStock` пишет всегда (данные каталога).
- При оформлении недоступные позиции удаляются из корзины, количество сверх остатка уменьшается, изменённые цены обновляются; изменения фиксируются, затем покупатель получает `CartChangedException` со списком причин.
- Счётчик корзины в шапке — сумма количеств. Статус `expired` устанавливается только системой (`expireReservations`).

## D-051. Остатки при удалении обращения (OR-07)
- **Контекст:** мягко удалённый активный резерв/заказ выпадал из `shop:expire-reservations` (глобальный scope SoftDeletes), и `reserved_qty` / списанный `stock_qty` оставались занятыми навсегда.
- **Решение:** удаление идёт через `OrderService::delete(Order, ?User)`: в одной транзакции под блокировкой обращения — если `stock_applied` и статус не финальный (`completed`/`cancelled`/`expired`/`closed`), резерв снимается (`releaseReservation`), заказ возвращается на склад (`returnForOrder`) через `StockService::settleForDeletion()`; пишется строка истории «Удалено администратором»; затем мягкое удаление. Выполненный заказ и закрытые обращения остаток не меняют; повторное удаление ничего не делает. Действие «Удалить» на странице обращения и массовое удаление в списке используют сервис. Страховка: событие `deleting` модели `Order` вызывает `settleForDeletion()` (идемпотентно), поэтому прямой `$order->delete()` тоже не оставляет остаток занятым.

## D-052. Поле «Остаток» в карточке товара
- **Контекст:** форма отправляла значение `stock_qty`, загруженное при открытии страницы, и затирала списания заказов (lost update) в обход `StockService`.
- **Решение:** поле `stock_qty` — `dehydrated(false)`, в модель напрямую не пишется. Страницы `EditProduct`/`CreateProduct` запоминают значение при заполнении формы (`#[Locked] $loadedStockQty`) и после сохранения (`afterSave`/`afterCreate`) вызывают `StockService::setStock()` только если пользователь изменил поле относительно загруженного значения (очистка поля = перестать учитывать). Если поле не менялось, оно перечитывается из БД. «Зарезервировано» и «Доступно» — только для чтения, как раньше.

## D-053. Номера обращений: строки счётчиков и повтор при взаимоблокировке; лимиты количества
- **Контекст:** `INSERT IGNORE` по существующей строке `order_sequences` берёт S-блокировку, и две параллельные транзакции взаимно ждали X-блокировку (MySQL 1213).
- **Решение:** миграция `seed_order_sequences` создаёт строки `order`/`reservation`/`inquiry` (`insertOrIgnore` в `up()`, удаление в `down()`); `OrderNumberGenerator::next()` делает только `SELECT … FOR UPDATE` и `UPDATE`. Если строки нет (миграция не выполнялась): вне внешней транзакции она создаётся, внутри — исключение с понятным текстом (создание внутри чужой транзакции вернуло бы взаимоблокировку). Транзакции `createFromCart`/`createReservation`/`createInquiry` выполняются с 3 попытками (`DB::transaction($cb, 3)`): внутри только операции с БД, события — `afterCommit` (откатанная попытка их отбрасывает), `CartChangedException` бросается после коммита, поэтому повтор безопасен. Порядок блокировок: корзина → товары по id → `order_sequences` → строки заказа.
- `createFromCart` первым запросом блокирует строку корзины: второе параллельное оформление той же корзины ждёт и видит пустую корзину («Корзина пуста»), второй заказ не создаётся.
- Количество одной позиции ограничено `App\Support\QtyLimit::MAX = 999` везде: `CartService::add/update` (обрезка), `AddToCart`/`CartPage` (сообщение/обрезка), правила `ReservationForm`/`InquiryForm`, `OrderService::createReservation/createInquiry` (исключение). Переполнение `qty` и сумм невозможно, поэтому `QueryException` с привязками (имя, телефон, email) не возникает; наш код персональные данные не логирует.
- `$productId` в `AddToCart`, `ReservationForm`, `InquiryForm` — `#[Locked]`. `ReservationForm::product()` запоминает товар на время запроса.
- Все записи расписания (`shop:heartbeat`, `shop:recalc-prices`, `shop:expire-reservations`) — `withoutOverlapping(10)`: mutex истекает через 10 минут, а не через 24 часа, если процесс cron на хостинге был убит.
- Восстановление удалённых обращений не поддерживается (политика запрещает `restore`): при удалении остатки уже возвращены (дополнение к D-051).

## D-054. Главная страница (5.2, AD-20)
- **Решение:** блоки хранятся в `HomePageSettings::blocks` (JSON, формат Filament Builder: `type` + `data`, в `data` флаг `visible`). Рендер — `HomePageRenderer`, результат HTML кэшируется на 10 минут (`home.html`), кэш сбрасывается при сохранении конструктора, товаров, категорий, настроек оформления/общих. Блок «HTML» доступен только администратору (поле скрыто и отбрасывается при сохранении менеджером); его содержимое выводится без санитайзера (NF-10), остальной форматированный текст — через `HtmlSanitizer`.
- **Кэш и CSRF (дополнение):** в карточках товара на главной — обычные POST-формы с `@csrf`; токен привязан к сессии, поэтому в кэшируемом HTML он заменяется плейсхолдером, а в `HomePageRenderer::render()` подставляется токен текущей сессии (HTML кэшируется целиком, запросы к БД на тёплом кэше — только настройки). Кэш сбрасывается слушателями `HomePageServiceProvider`: `SettingsSaved` (любые настройки), `saved`/`deleted` у `Product`, `Category`, `ProductImage`, `restored`/`forceDeleted` у `Product`, `ImportFinished`. Массовые SQL-обновления мимо моделей (пересчёт цен, остатки) подхватываются по TTL 10 минут.
- **Изображения баннеров:** загрузка во временный приватный каталог `tmp/home-images`, при сохранении `ImageProcessor::processBannerImage` создаёт варианты 1600 и 800 px (WebP) в `public/home/`, в блоке хранится `{large, small, width, height}`; исходник не сохраняется, SVG и файлы > 10 МБ отклоняются. Заменённые, удалённые и осиротевшие (блок удалён) файлы удаляются после сохранения; ссылка на существующую картинку принимается, только если она уже есть в сохранённых настройках (подмена пути из браузера не даёт удалить чужие файлы).
- **Менеджер и блок HTML (6.13):** блоки `html` вырезаются из данных формы менеджера (исходный код не попадает в браузер) и при сохранении возвращаются на прежние позиции; отправленные менеджером блоки `html` отбрасываются.

## D-056. Sitemap и robots (SF-82)
- **Решение:** `shop:sitemap` пишет `public/sitemap.xml` (атомарно: временный файл + rename; при > 50 000 URL — индекс и части), ежедневно в 04:20 и после импорта (слушатель `ImportFinished` ставит задачу в очередь). Маршрут `/sitemap.xml` отдаёт файл, а если его нет — генерирует на лету. `/robots.txt` — маршрут из `SeoSettings` со строкой `Sitemap:`; статический `public/robots.txt` удаляется.
- **Блокировка (ревью PR #6):** `SitemapGenerator::generateLocked()` берёт `Cache::lock('sitemap:generate', shop.sitemap_lock_seconds)` (300 с) и дополнительно `flock` на `storage/framework/sitemap.lock` (переживает `cache:clear`, снимается ядром вместе с процессом); команда и задача `GenerateSitemap` при занятой блокировке пропускаются, а `/sitemap.xml` без файла отдаёт 503 + `Retry-After: 60` вместо параллельной генерации. Даже если обе блокировки пропали, параллельные запуски безвредны: каждый пишет в свой временный файл (`tempnam`, уникальное имя) и публикует его атомарным `rename()`, поэтому `sitemap.xml` всегда целый корректный файл (в худшем случае индекс на миг расходится с частями; следующий запуск это исправит). Задача `GenerateSitemap`: 5 попыток, `backoff` 60/120/300/600 с после исключения; занятая блокировка освобождает задачу с собственной задержкой 120 с.
- **robots.txt в закрытом режиме:** правила остаются обычными (без `Disallow: /`). Страницы витрины отвечают 503 + `Retry-After`, это поисковики считают временным; `Disallow: /` при долгом закрытии мог бы выбить страницы из выдачи.

## D-057. Хост и закрытый режим (ревью PR #6)
- **Контекст:** кэш главной хранил абсолютные URL с хостом и схемой первого запроса (отравление кэша, `www.`-алиас Beget, http/https); закрытый режим не действовал на действия Livewire-компонентов витрины, так как `livewire*` исключён из `StorefrontOpen`.
- **Решение (хост):** два слоя. (а) В production `AppServiceProvider::forceCanonicalUrl()` вызывает `URL::forceRootUrl(APP_URL)` и `URL::forceScheme('https')` при https в `APP_URL`; в `bootstrap/app.php` включён `TrustHosts` с хостом из `APP_URL` и его `www.`-вариантом (`subdomains: false`, список вычисляется на запрос, поэтому работает и с кэшем конфигурации; в local и тестах middleware не действует). Каноникал, OG и sitemap по-прежнему строятся от `APP_URL`. (б) Кэшируемый фрагмент главной не зависит от хоста: ссылки на товары (`ProductPresenter::present(..., absolute: false)`), «Смотреть все», плитки категорий и `action` формы «В корзину» — относительные (`route(..., absolute: false)`).
- **Решение (закрытый режим):** трейт `App\Livewire\Storefront\Concerns\RequiresOpenShop` (хук `bootRequiresOpenShop`) во всех компонентах витрины (`AddToCart`, `CartPage`, `CheckoutForm`, `ReservationForm`, `InquiryForm`, `MiniCart`) отвечает 503, если магазин закрыт, а пользователь не активный сотрудник; проверка на монтировании и на каждом следующем запросе. Обычный `POST /cart/add` закрыт middleware.
- **Решение (www., раунд 2):** `www.`-вариант (или голый домен, если `APP_URL` с `www.`) не обслуживается: global middleware `CanonicalHost` в production отвечает 301 (GET/HEAD) или 308 (прочие методы) на тот же путь и query на схему и хост `APP_URL`; иначе ассеты, Livewire и подписанные URL указывали бы на другой origin. Отключается `shop.canonical_host_redirect`. Остальные хосты отсекает `TrustHosts` (400).
- **Решение (SHOP_EXTRA_HOSTS, техдолг):** хосты из `SHOP_EXTRA_HOSTS` тоже перенаправляются `CanonicalHost` на хост `APP_URL` (так же, как `www.`-двойник: 301/308, в production), иначе страница технического домена тянула бы ассеты и Livewire с другого origin и JS ломался. Порядок работы: пока свой домен не привязан, в `APP_URL` стоит технический домен; после привязки `APP_URL` меняется на настоящий домен, а технический остаётся в `SHOP_EXTRA_HOSTS` (он принимается и перенаправляется).
- **Технический домен Beget:** `*.beget.tech` не входит в доверенные и отвечает 400, пока он не добавлен в `APP_URL` или в необязательную переменную `SHOP_EXTRA_HOSTS` (через запятую, `config('shop.extra_hosts')`). Список шаблонов строит `App\Support\TrustedHosts`.
- **Закрытый режим в Livewire:** `RequiresOpenShop` бросает `HttpResponseException` с тем же ответом 503 (view `errors.shop-closed` с текстом из настроек), что и `StorefrontOpen::closedResponse()`.
- **Отвергнуто:** разбор snapshot в middleware (хрупко); исключение `livewire*` нельзя убрать целиком — им пользуется вход в админку.

## D-058. Страницы согласия и политики включены по умолчанию (SF-71)
- **Решение:** миграция-сидер создаёт страницы политики и согласия активными (чекбоксу согласия нужна ссылка на документ, неактивная страница даёт 404), остальные три страницы остаются черновиками. Отметка «Шаблон — проверить у юриста» остаётся вверху текста. **Перед запуском владелец обязан заменить текст на согласованный юристом и удалить отметку.** Миграция ещё не выпускалась, поэтому изменена на месте.
- **Отвергнуто:** оставить черновики (нет ссылки у согласия); показывать текст согласия во всплывающем блоке (дублирование источника).

## D-059. Уведомления (раздел 9, NT-01…NT-04)
- **Решение:** слушатели `OrderCreated`/`OrderStatusChanged` (в `NotificationServiceProvider`) только ставят в очередь задачу `SendOrderNotifications` (3 попытки, backoff) — создание обращения никогда не зависит от почты/Telegram (NT-01). Письма — Markdown-шаблоны Laravel (`resources/views/mail/*`) с логотипом и названием магазина; SMTP — только в `.env` (NT-03). Telegram — Bot API `sendMessage`, `parse_mode=HTML`, все подставляемые значения через `htmlspecialchars` (NT-02); токен хранится зашифрованным в настройках (D-010).
- Повторная отправка при ретрае не дублирует каналы: задача отправки — отдельная на каждый канал/получателя.
- Уведомление «резерв истекает в течение 6 ч» отправляется один раз (`orders.expiring_notified_at`).
- В логи не пишутся телефоны и email целиком (NF-15): маскирование `+7******4567`, `i***@example.ru`.
- **Ревью PR #7, раунд 1:**
  - Письма — Markdown, поэтому текст покупателя (имя, адрес, комментарий, email, телефон, названия позиций и способов) проходит через `App\Support\MarkdownEscaper` (директивы `@md` для многострочного и `@mdi` для однострочного текста, вывод «сырой»: HTML-экранирование и экранирование Markdown делаются одним шагом, `{{ }}` для таких значений не используется). Ломается и автоссылка GFM (`https://`, `www.`, email).
  - Telegram: сообщение строится в пределах 4000 видимых символов (`OrderMessage::compose`): шапка, клиент, итог, срок резерва и ссылка в админку остаются всегда, позиции сокращаются строкой «…и ещё N поз.». Готовый HTML не режется; в `TelegramNotifier` остался только последний рубеж — простой экранированный текст, обрезанный по видимым символам.
  - Исключения почтового транспорта содержат адрес получателя: задача бросает `MailDeliveryException` без `previous` и с маскированными адресами (NF-15). SMTP-таймаут — `MAIL_TIMEOUT` (по умолчанию 20 с, меньше лимита задачи в 40 с).
  - Разветвление уведомлений и «отметка + постановка» в `shop:notify-expiring-reservations` выполняются в одной транзакции (`JobFanOut`): очередь `database` использует то же соединение, поэтому вставки откатываются вместе с отметкой. Дочерние задачи ставятся с `beforeCommit()` — с `afterCommit()` вставка произошла бы после коммита и откат стал бы невозможен. Если `JobFanOut::dispatch()` не поставил ни одной задачи (0), команда бросает исключение внутри транзакции и отметка `expiring_notified_at` откатывается (повтор при следующем запуске). Дочерние задачи — `ShouldBeUnique` (заказ + канал + получатель + событие, `uniqueFor` 1 час); при ошибке блокировки снимаются, иначе ретрай был бы пропущен.
  - `OrderStatusChanged` несёт явный флаг `bySystem` (его выставляет `expireReservations`), «истёк автоматически» больше не выводится из `user === null`.
  - Отметка планировщика (`storage/app/heartbeat`) — один файл, перезаписываемый каждую минуту, чистить нечего; пункта «старые отметки» в `shop:cleanup` нет. Шаги `carts` и `exports` проверяют бюджет времени, исчезнувшие файлы пропускаются.
  - `schedule:run` выполняет задачи одной минуты последовательно, фоновых процессов (`runInBackground`) не используем. Тяжёлые ежедневные задачи разнесены по времени и каждая укладывается в ~50 с: 03:10 пересчёт цен, 04:20 sitemap, 04:40 cleanup, 04:50 `queue:prune-failed` (перенесён с 00:00, где совпадали пять задач).

## D-060. Остатки скелета Laravel: пакеты и скрипт `dev` (техдолг этапа 0)

## D-070. Возрастное ограничение: оба режима, cookie и размытие на клиенте (AG-01…AG-14)
- **Контекст:** владелец продаёт часть товаров с ограничением 16+/18+ и хочет и «плашку для всего сайта», и «только для ограниченных товаров». Главная и подборки кэшируются на 10 минут (общий кэш без привязки к посетителю), поисковые роботы блокироваться не должны.
- **Решение:** режим выбирается в настройках (`AgeGateSettings`: `site` / `restricted`). Ограничение `null/16/18` у категории и товара (varchar(2), enum `AgeRestriction`), действующее значение — собственное у товара, иначе ближайшая категория (по кэшированному дереву, без запросов). Подтверждение хранится в cookie `shop_age` (уровень, N дней из настроек), cookie не шифруется. Размытие и показ плашки решает CSS/мелкий скрипт по `data-age` и cookie, поэтому кэш фрагментов не зависит от посетителя; без JS работает обычная форма `POST /age-gate/confirm`. Страница всегда отдаётся полностью (плашка — оверлей), роботы получают 200 без `noindex`. «Нет» → 302 на главную с сообщением. В оформлении с такими товарами обязателен чекбокс возраста, уровень пишется в `orders.age_confirmed_level`.
- **Отвергнуто:** серверная подмена контента по cookie (ломает кэш и выглядит как клоакинг); блокировка по User-Agent; хранение возраста в сессии (теряется между визитами); защита файлов изображений на сервере (владелец принял «добросовестное» подтверждение).

## D-071. Покупатели: отдельная таблица `customers` и guard `customer`; заказ без регистрации по настройке (CA-01…CA-28)
- **Контекст:** сотрудники живут в `users` и Filament; нужен кабинет покупателя, при этом гостевой заказ должен остаться.
- **Решение:** таблица `customers` + guard `customer` (session), сотрудники остаются в `users`/`web`. Причины: исключение эскалации в админку, разные политики паролей и сессий, разный объём и режим ПДн (обезличивание покупателей), независимость кода v1. Настройка «Разрешить заказ без регистрации» (по умолчанию вкл.), у группы покупателей — флаг «Заказ только после входа». Существующие заказы остаются гостевыми; после подтверждения email гостевые обращения с тем же email привязываются (`OrderLinker`).
- **Отвергнуто:** единая `users` с признаком (риск доступа в админку, смешение политик); отдельный пакет мультиаутентификации; обязательная регистрация.

## D-072. Подтверждение email 6-значным кодом: хранение и лимиты (CA-04, CA-12)
- **Решение:** код — `random_int`, в БД хранится HMAC-SHA256 с ключом приложения (не открытый код), TTL 15 мин, 5 попыток на код, не более 20 неверных вводов в сутки на email (затем блокировка на сутки и письмо владельцу), повторная отправка не чаще раза в 60 с, новый код аннулирует старый, использование атомарно (`UPDATE … WHERE consumed_at IS NULL`). Лимиты на email и IP через `RateLimiter` (файловый кэш). Запросы кода входа/сброса отвечают одинаково для существующих и несуществующих аккаунтов. Все параметры — в настройке «Покупатели и регистрация». Вход по паролю или по коду; сброс пароля и смена email — через код (ссылок с токенами нет).
- **Отвергнуто:** `Hash::make` для кода (медленно и не нужно для одноразового короткоживущего значения); «ссылки подтверждения» (требуют токен в URL, почтовые сканеры их «прокликивают»).

## D-073. Группа покупателей — роль покупателя; «Гость» и «Розница» — системные (CG-01…CG-19)
- **Контекст:** нужны видимость разделов и категорий, показ цен, режимы, доставка, оплата, скидки и ступени; владелец хочет настраивать и гостя.
- **Решение:** одна сущность `customer_groups` для доступа и цен. Системные группы `guest` и `retail` (нельзя удалить и менять код), гость настраивается как любая; значения по умолчанию воспроизводят поведение v1. Доступ к категориям — `all / all_except / only` с подкатегориями через `customer_group_categories`; в режиме `only` родители выбранных доступны как навигационные. Режимы продаж группы зажимают результат `SalesModeResolver`; скрытые цены (`login`/`request`) понижают режим до заявки. Принудительное применение — единый сервис `CatalogAccess` в каталоге, поиске, подсказках, меню, страницах, фасетах, sitemap, корзине и оформлении; скрытое → 404; sitemap и robots строятся для «Гостя»; контент, видимый только вошедшим, отдаётся с `noindex` и `Cache-Control: private`. Кэши ключуются `группа + версия каталога`. Поля, действие которых реализуется позже, создаются миграцией того этапа.
- **Отвергнуто:** отдельные «ценовые группы» и «группы доступа» (двойная сущность); хранение доступа флагами у категорий (непрозрачно для нескольких групп); кэш без ключа группы.

## D-074. Роли сотрудников и права: таблицы `roles`/`role_permissions`, `PermissionService` (RB-01…RB-16)
- **Контекст:** v1 хранит `users.role` (admin/manager). Владелец хочет настраиваемые роли с галочками прав; пакеты ролей запрещены (CLAUDE.md, раздел 3).
- **Решение:** `roles` + `role_permissions(role, permission)`, реестр прав `PermissionRegistry` в коде (`{раздел}.{действие}` плюс специальные: `prices.bulk`, `imports.full_sync`, `orders.delete`, `orders.edit_items`, `orders.edit_prices`, `html_block.edit`, `settings.<страница>.update`, `users.*`, `roles.*`, `system.*`). «Администратор» разрешает всё и не редактируется (в том числе будущие права), «Менеджер» создаётся по матрице 6.13. Политики, `canAccess()` страниц и сервисы вызывают `PermissionService::allows()`; проверки обязательны на сервере. Миграция: `role_id` по значению `role`, затем колонка `role` удаляется (`down()` восстанавливает). Защита последнего активного администратора (закрывает техдолг этапа 0), неизменяемость системных ролей, запрет выдавать права, которых нет у выдающего, журнал `admin_audit_log`. Кэш прав — по роли с версией.
- **Отвергнуто:** spatie/laravel-permission и аналоги (лишний пакет, чужая модель); хранение прав JSON-полем роли (нельзя индексировать и мигрировать); оставить enum и добавить флаги.

## D-075. Оптовый доступ по заявке (CG-20…CG-24)
- **Решение:** заявка `wholesale_applications` от вошедшего покупателя с подтверждённым email (компания, ИНН с контрольной суммой, контакт, комментарий, согласие); уведомление магазина (email/Telegram); менеджер одобряет с обязательным выбором группы (реквизиты копируются в профиль) или отклоняет с причиной; письмо и уведомление в кабинете; повторное решение запрещено; лимиты, предупреждение о дубле ИНН; всё в журнале действий.
- **Отвергнуто:** заявка от гостя без аккаунта (нечего привязывать к группе); автоматическое одобрение по ИНН (нет проверки контрагента).

## D-076. Характеристики: нормализация с числовой колонкой; JSON — кэш для показа (FL-01…FL-22)
- **Контекст:** `products.attributes` (JSON `[{name,value}]`) не индексируется; нужны фильтры, диапазоны и счётчики в пределах 30 SQL на страницу.
- **Решение:** `attributes` (list/number/boolean, единица), `attribute_values`, `product_attribute_values` (+ `value_number decimal(14,4)`, `value_bool`), `category_filters` (набор и порядок на категорию, наследование от ближайшего родителя с собственным набором). JSON-поле **сохраняется как кэш показа** и пересобирается при каждом сохранении характеристик (`AttributeSyncService`): карточка и экспорт не получают дополнительных запросов, старый код остаётся рабочим; источник истины — нормализованные таблицы. Миграция выполняется из админки (действие «Перенести характеристики из JSON»: предпросмотр → фоновая задача `MigrateAttributesFromJson` пачками по 500 с прогрессом), команда `shop:attributes-migrate --dry-run` — запасной вариант; обязательных ручных шагов по SSH нет. Авто-типы: boolean/number при ≥ 95 % числовых значений, иначе list; характеристики с > 200 значениями — нефильтруемые; повторный запуск безопасен. Колонки «Х: имя, ед.» разбираются по порядку: полная подпись → полное имя (совместимость с v1) → разбор суффикса. Импорт «Х: …» пишет в справочник (новые — нефильтруемые).
- **Отвергнуто:** оставить только JSON (нет индексов и диапазонов); полная замена JSON без кэша (+запросы на карточке, переписывание экспорта); EAV в одной таблице значений-строк (нет числового индекса).

## D-077. Фасеты, URL и SEO фильтров (FL-07…FL-14)
- **Решение:** GET-параметры `a[slug][]`, `a[slug][min|max]`, `o[slug][]` с нормализацией и белым списком. Логика — ИЛИ внутри характеристики, И между характеристиками. Выборка — коррелированные `EXISTS` по `product_attribute_values`; счётчики — по одному сгруппированному запросу на характеристику при применённых остальных фильтрах (без своего), числовые min/max — одним запросом; без CTE и оконных функций (MySQL 5.7). Индексы `(attribute_id, attribute_value_id, product_id)` и `(attribute_id, value_number, product_id)`. Кэш фасетов 10 мин по ключу с группой и версией каталога (файловый кэш без тегов). Максимум 9 настраиваемых фильтров и ≤ 10 фасетных запросов на страницу (9 списочных/опционных + 1 числовой). SEO: индексируется страница без фильтров и (при флаге характеристики `index_single_value`) страница с одним фильтром и одним значением; остальные комбинации — `noindex,follow` и canonical на категорию; `robots.txt` параметры не закрывает (роботы должны видеть `noindex`).
- **Отвергнуто:** `Disallow` для параметров (роботы не увидят `noindex`); кэш самих списков под фильтры (дорого и бесполезно при быстрых индексированных запросах); ползунки с гистограммой («Позже»).

## D-078. Модификации: карточка + варианты; `StockService` работает с stockable (VR-01…VR-29)
- **Контекст:** размер/цвет как на маркетплейсах; остатки, цены, импорт и фильтры уже существуют на уровне товара.
- **Решение:** справочник опций (`option_types`, `option_values`), оси карточки (`product_options`, ≤ 3), `product_variants` со своими SKU, штрихкодом, остатком, резервом и необязательными ценами (наследуют карточку), значения в `product_variant_values`, `combo_hash` против дублей, мягкое удаление. `StockService` оперирует «stockable» (товар без модификаций или модификация); порядок блокировок во всех операциях: товары, затем модификации, по возрастанию id (нет взаимоблокировок); `stock_qty`/`reserved_qty`/`final_price` карточки — агрегаты по активным модификациям (min/max цены, сумма остатков; если хотя бы одна активная модификация не учитывается — карточка «не учитывается»), поэтому сортировка, фильтры и «в наличии» каталога не меняются; сверка `shop:variants-rollup`. Режим продаж — на уровне карточки, наличие — модификации. Поиск по артикулу и штрихкоду модификаций — `OR EXISTS` по `product_variants` (индексы `sku`, `barcode`), `products.search_text` не расширяется (поле varchar(1000)). Цена карточки в списках — «от X»; URL карточки прежний, `?variant=` с canonical на карточку. Составные уникальные ключи — через `variant_key = COALESCE(variant_id, 0)` (NULL не уникализируется ни в MySQL, ни в SQLite). Включение и выключение модификаций запрещено при незавершённых обращениях товара. Импорт: строка = модификация, «Артикул карточки» + «Опция: …», карточка должна быть выше в файле.
- **Отвергнуто:** каждая комбинация — отдельный товар (дубли карточек и SEO); хранить остатки модификаций в JSON; пересчитывать агрегат на чтении (медленно для сортировки).

## D-079. PDF-выгрузки: пакет `barryvdh/laravel-dompdf` (CX-01…CX-14)
- **Контекст:** нужна выгрузка истории заказов и бланка/счёта в PDF на Beget (без Node, бинарников, SaaS); CLAUDE.md требует обоснования нового пакета.
- **Решение:** `barryvdh/laravel-dompdf` (чистый PHP, кириллица через DejaVu, внешние ресурсы и PHP в шаблонах отключены). Excel — прежний `spatie/simple-excel`. Синхронные пороги: Excel ≤ 300 обращений, PDF ≤ 200 без состава / ≤ 50 с составом, иначе задача очереди и ссылка в кабинете, файл 24 часа на приватном диске, скачивание через контроллер с проверкой владельца; жёсткие лимиты PDF (1 000 без состава / 300 с составом) и Excel (20 000 строк) настраиваются; формирование чанками по 100 заказов. Один шаблон для истории, печатной формы в админке и «счёта / бланка заказа» оптовика. Символ «₽» проверяется на приёмке, при отсутствии глифа — «руб.». Если обёртка не поддерживает Laravel 13, подключается `dompdf/dompdf` напрямую.
- **Отвергнуто:** mPDF и TCPDF (тяжелее или ручная вёрстка), wkhtmltopdf и headless Chrome (нет на shared-хостинге), внешние сервисы генерации (запрещены разделом 2).

## D-080. Цены групп и ступеней: `PriceResolver` и денормализация (GP-01…GP-23)
- **Решение:** порядок для (группа, количество): ступень (`min_qty ≥ 2`, наибольшая ≤ qty) → точная цена группы (`min_qty = 1`) → розничная `final_price` (с правилами, привязанными к группе, `price_rule_groups`) × (1 − скидка группы), округление — по настройке. Ступени и точные цены — одна таблица `product_price_tiers` (товар или модификация, группа, `min_qty`, цена). Итог шагов 2–3 заранее считается задачей `RecalculatePrices` в `product_group_prices_final` (только когда отличается от розницы; у карточки с модификациями — минимум), чтобы сортировка и фильтр по цене работали по группе зрителя (`COALESCE` + коррелированный подзапрос по уникальному индексу, `GroupPriceSql`, а не LEFT JOIN; индекс `(customer_group_id, final_price)`). Ступень определяется в момент действия (корзина, оформление) единым `PriceResolver`; в заказ пишутся группа, источник цены, ступень и розничная цена. Импорт/экспорт: «Цена: <код>» и «Цена: <код> от <N>»; история цен получает группу и `min_qty`. Розничная цена зачёркнутой — флаг группы.
- **Отвергнуто:** вычислять цену группы в SQL при каждом запросе; хранить строки для всех групп всех товаров (раздувает таблицу); суммировать ступени по карточке («Позже»).

## D-081. Промокоды: условия, «лучшая цена», атомарный учёт (PM-01…PM-20)
- **Решение:** типы `percent / fixed / free_delivery`, области `all / categories / products / brands`, минимальная сумма, период, общий и персональный лимиты, «только для зарегистрированных», допустимые группы (по умолчанию «Гость» и «Розница»), флаги «действует на товары со скидкой» и «суммируется с акциями» (по умолчанию выкл.: покупателю достаётся лучшая цена, а не две скидки), один код на заказ. Фиксированная сумма распределяется по строкам методом наибольших остатков в копейках. Повторная валидация и увеличение счётчика (`UPDATE … WHERE usage_count < usage_limit`, проверка затронутых строк) — внутри транзакции создания заказа под `lockForUpdate()`; освобождение при отмене (идемпотентно). Массовая генерация одноразовых кодов (префикс, алфавит без похожих знаков, ≤ 5 000, пачки по 500) с экспортом. Перебор кодов ограничен. Лимит гостя считается по HMAC-хэшу email и телефона (не по sha1); «товар со скидкой» определяется полем строки `promo_old_price` (только старая цена правил цен или `compare_at_price`, без зачёркнутой розницы группы); порядок блокировок: заказ → товары → модификации → промокод. Скидка хранится в заказе и в позициях (`promo_discount`), `total = items_total − promo_discount − manual_discount + delivery_price`.
- **Отвергнуто:** считать скидки на клиенте; суммировать акцию и код по умолчанию; хранить использование только счётчиком без журнала применений (нет персонального лимита и освобождения).

## D-082. Промо-ссылки `/go/{slug}` и атрибуция (PM-21…PM-28)
- **Решение:** короткая ссылка ведёт 302 (не 301) на товар / модификацию / категорию / отфильтрованный каталог / внутренний путь (внешние адреса запрещены), добавляет UTM, при наличии промокода ставит cookie `shop_promo` (30 дней), корзина применяет код автоматически и показывает его. Атрибуция «последний клик» через cookie `shop_pl` (30 дней) → `orders.promo_link_id`. Клики — агрегат по дням (`promo_link_stats`, без построчных логов, без ботов), заказы и выручка считаются запросом по `orders.promo_link_id` (нет денормализованных счётчиков, которые могли бы разойтись). `/go/` закрыт в `robots.txt` и отдаёт `X-Robots-Tag: noindex`. QR-код — «Позже»: генерация QR на PHP без нового пакета (GD её не умеет) нецелесообразна; временно — внешний генератор.
- **Отвергнуто:** построчное логирование кликов (ПДн и объём); 301 (кэшируется браузерами, ломает смену цели и срока); добавление QR-пакета ради необязательной функции.

## D-083. Резерв нескольких товаров через корзину (MR-01…MR-13)
- **Решение:** корзина принимает режимы `cart`, `both`, `reservation`. Для строки определяется вид оформления (`order` / `reservation` / `flexible`), на оформлении покупатель выбирает «Оформить заказ» или «Зарезервировать» для гибких строк; смешанная корзина создаёт два обращения (заказ и резерв, `related_order_id`) в одной транзакции с общим порядком блокировок и понятным пояснением. Один `reserved_until` на резерв, «всё или ничего» по остаткам, срок продлевается и истекает целиком, `StockService` удерживает позиции поштучно. Частичного подтверждения и выкупа нет — используется редактирование состава (D-084). Настройка `reservation_via_cart` (по умолчанию вкл.) возвращает поведение v1 при выключении; форма резерва одного товара остаётся.
- **Отвергнуто:** частичный выкуп резерва (усложняет приложение B и статусы); отдельная «корзина резерва» (двойной интерфейс).

## D-084. Редактирование состава заказа: журнал и оптимистичная блокировка (OE-01…OE-16)
- **Решение:** полное редактирование «до выдачи» в статусах `new/confirmed/ready` (заказы) и `new/reserved` (резервы) (владелец: «полное редактирование до выдачи»; `shipped` и `completed` — «Позже»): позиции (включая модификации), количества, цены (право `orders.edit_prices`), доставка, общая скидка (`manual_discount`), контакты. Остатки меняет только `StockService::applyItemChanges()` в одной транзакции с блокировками; дельта считается от прежнего количества позиции (см. D-090), поэтому повторное сохранение ничего не списывает. Каждое изменение пишется в `order_changes` (поле или позиция, было → стало, пользователь, время, `batch_uuid`) в той же транзакции. Оптимистичная блокировка: `orders.version`, `UPDATE … WHERE version = ?`, версия растёт и при смене статуса. Промокод пересчитывается на новом составе (период и лимиты не проверяются). Письмо «Состав заказа изменён» (настройка, по умолчанию вкл.) и уведомление в кабинете. Заявка-запрос превращается в заказ действием «Создать заказ из заявки».
- **Отвергнуто:** блокировка заказа «на время редактирования» (зависшие блокировки на shared-хостинге); пересчёт цены существующей позиции при смене количества (неожиданное изменение суммы); хранение журнала в `order_status_history`.

## D-085. Порядок этапов 8–15 и правило «поле создаётся там, где начинает действовать»
- **Решение:** 8 — роли и группы (опора для остального) + возраст; 9 — кабинет (назначает группы); 10 — характеристики; 11 — модификации; 12 — цены групп; 13 — промокоды и ссылки; 14 — резерв нескольких и редактирование; 15 — выгрузка и приёмка. Фильтры (10) идут до модификаций, а фильтры по опциям включаются на 11 (набор фильтров с источником `attribute|option`); цены групп (12) после модификаций; промокоды (13) после цен и кабинета; редактирование (14) после промокодов и модификаций; PDF (15) последним, чтобы показывать финальную структуру заказа. Поля групп с эффектом позже создаются миграцией своего этапа (скидка — 12, бланк/счёт — 15, «заказ только после входа» и группа по умолчанию для новых — 9); прайс-лист группы — этап 12.
- **Отвергнуто:** делить по темам в порядке пожеланий владельца (кабинет раньше групп — некуда назначать группу; PDF раньше заказов — переделка шаблона).

## D-086. Обезличивание покупателей по запросу (CA-16, CA-17)
- **Решение:** запрос на удаление подтверждается кодом, аккаунт блокируется, через срок отмены (3 дня) команда `shop:anonymize-customers` обезличивает: имя, email (`deleted-{id}@anonymous.invalid`), телефон, адреса, компания, заявки, уведомления, корзины; в обращениях стираются имя, телефон, email, адрес, комментарий, user agent, IP согласия — состав, суммы и статусы остаются для учёта. Администратор может обезличить сразу; операция идемпотентна и пишется в журнал без ПДн.
- **Отвергнуто:** физическое удаление заказов (теряется учёт); удаление покупателя с каскадом на заказы.

## D-087. Уникальность SKU среди товаров и модификаций — на уровне приложения (VR-04)
- **Решение:** уникальные индексы в обеих таблицах + сервис `SkuGuard` проверяет пересечение в транзакции (форма, импорт, дублирование); редкая гонка между параллельным созданием товара и модификации с одним SKU ловится `shop:doctor` («коллизии артикулов»). Таблица-реестр артикулов не вводится.
- **Отвергнуто:** общая таблица `skus` с триггерами или наблюдателями (усложняет импорт и откат); именованные блокировки MySQL (недоступны в SQLite-тестах).

## D-088. Ответы владельца на вопросы ТЗ v2 (раздел 15, CG-21, CG-27)
- **Решено владельцем:** PDF по умолчанию «Бланк заказа»; при заполненных банковских реквизитах продавца в «Юридическое» (банк, БИК, р/с, к/с — поля `LegalSettings`) оптовик может скачать «Счёт на оплату» со своими реквизитами как плательщика. При обновлении создаются группы «Гость» (системная), «Розница» (системная, по умолчанию для новых) и «Опт» (скидка 0 %, заказ только после входа; создаётся миграцией этапа 9, когда появляется поле). Показ остатков — настройка группы (`stock_display`: как в общих настройках / точное число / есть-нет, CG-27). Магазин уведомляется только о заявках на опт (email + Telegram, два переключателя в настройках уведомлений); о регистрациях уведомлений нет — они видны в админке и на дашборде.
- **Решено по умолчанию:** возрастная плашка — только добровольное подтверждение, соответствие закону при продаже алкоголя и табака — ответственность владельца; заказы обезличенных покупателей хранятся бессрочно без ПДн; QR промо-ссылок — «Позже».

## D-089. Завершение прочих сессий покупателя: `customers.auth_version` и раздельные сессии (CA-31, CA-32)
- **Контекст:** при `SESSION_DRIVER=file` сессии нельзя перечислить; сброс `remember_token` гасит только cookie «запомнить меня»; `AuthenticateSession` не помогает при смене email (пароль тот же).
- **Решение:** поле `auth_version` увеличивается при смене/сбросе пароля, смене email, блокировке и запросе удаления; значение хранится в сессии, middleware guard-а `customer` сверяет его на каждом запросе. Сессии покупателя и сотрудника делят один файловый драйвер, но используют раздельные ключи guard-ов; выход покупателя — `logout()` + `regenerateToken()` без `session()->invalidate()`, пока активен guard `web`.
- **Отвергнуто:** сессии в БД (допустимо, но меняет раздел 2 и нагрузку); перечисление файлов сессий.

## D-090. Дельта остатков при редактировании заказа считается от прежнего количества (OE-04)
- **Контекст:** формула `new_qty − stock_applied_qty` неверна для позиций «под заказ» и обращений, созданных при выключенном учёте: любое сохранение списывало бы «недостающую» часть.
- **Решение:** `Δ = new_qty − old_qty`; без изменения количества остатки не трогаются; при уменьшении сначала снимается неприменённая часть (`qty − stock_applied_qty`), затем возвращается применённая; `stock_applied_qty ≤ new_qty`; при `orders.stock_applied = false` или `stock_qty IS NULL` остатки позиции не меняются. Порядок блокировок: заказ → товары → модификации → промокод.
- **Отвергнуто:** пересчёт «до целевого applied = new_qty» при каждом сохранении (ломает идемпотентность и «под заказ»).

## D-091. Защита публичного репозитория и CI
- **Контекст:** репозиторий стал публичным: код, история, PR и логи Actions видны всем, а pull request из форка может запустить CI.
- **Решение:** действия в `ci.yml` и `deploy.yml` закреплены по SHA коммита с тегом в комментарии (Dependabot обновляет оба); токен CI только на чтение (`permissions: contents: read`); `actions/checkout` с `persist-credentials: false`, чтобы токен не оставался в `.git/config` на время шагов со сторонним кодом (composer, npm); деплой идёт через окружение `production`, где владелец задаёт обязательное подтверждение и ветку `main`, а секреты Beget хранятся в секретах этого окружения. Добавлен `SECURITY.md` (приватные сообщения об уязвимостях). Настройки репозитория (ruleset для `main`, сканирование секретов, Dependabot alerts, CodeQL, права Actions) включает владелец: список и команды — `docs/DEPLOY_BEGET.md`, приложение «Безопасность CI».
- **Отвергнуто:** сделать репозиторий приватным (решение владельца); `pull_request_target` (дал бы коду из форка доступ к секретам).

## D-092. Роли сотрудников: реализация `PermissionService` и защита от эскалации (RB-04, RB-07, RB-08, RB-13)
- **Решение:** права роли кэшируются в файловом кэше по ключу `perm:role:{id}:{permissions_version}` на 10 минут; любое изменение роли увеличивает `permissions_version`, поэтому действует сразу; память запроса сбрасывается в конце запроса и на каждом цикле очереди. Решения «по сути о роли» (последний администратор, администратор видит чужие экспорты) идут через `isAdministrator()` / `hasAdministratorRole()`, доступ к функциям — только через `allows()`. Эскалация: роли и пользователю можно выдать только права, которые есть у самого сотрудника; не-администратор не меняет и не удаляет учётку с более широкой ролью; свою роль и активность менять нельзя никому. Удаление импорта сопоставлено с `imports.full_sync` (в 25.4 нет `imports.delete`, в 1.0 было только у администратора). Права «Менеджера» по умолчанию — литерал в миграции, равенство с `PermissionRegistry::managerDefaults()` проверяет тест. Журнал хранит только идентификаторы, коды и ключи прав, без имён и email. FK `users.role_id` создаётся только на MySQL (SQLite не добавляет FK к существующей таблице); запрет удаления роли с пользователями — в `RoleService`.
- **Отвергнуто:** пакеты ролей (D-074); проверка `role === 'admin'` в коде.

## D-093. Возрастная плашка: состояние на клиенте, кэшируемый HTML не зависит от cookie (AG-01…AG-14)
- **Решение:** карточки всегда несут `data-age="16|18"` (независимо от включения плашки), настройки управляют только атрибутами `<html>` (`data-age-on`, `data-age-badge`); маленький inline-скрипт в `<head>` ставит `data-age-ok` по cookie `shop_age`, размытие и скрытие оверлея делает CSS. Действующий уровень вычисляется подъёмом по кэшированному дереву категорий (до 4 обращений к массиву, без SQL) — отличие от формулировки «карта на запрос» в AG-01. Кэш `age:has_restricted` (10 мин) сбрасывается событиями товаров/категорий, окончанием импорта и массовым действием. При выключенной плашке ничего не меняется, включая оформление. Cookie `shop_age` — не HttpOnly, SameSite=Lax, исключена из шифрования. Чекбокс возраста — в оформлении заказа и резерва; заявка не охвачена (16.6 называет только CheckoutForm и ReservationForm); `OrderService` перепроверяет по заблокированным товарам и пишет `orders.age_confirmed_level`. Экспорт пишет собственное значение товара, а не действующее.
- **Отвергнуто:** решать показ плашки на сервере (кэш главной зависел бы от cookie); скрывать содержимое страниц от роботов.

## D-094. Группы покупателей: `ViewerContext`, `CatalogAccess` и версия каталога (CG-01…CG-19, CG-27)
- **Решение:** версия каталога — токен в файловом кэше, увеличивается при изменении товаров, категорий, групп, страниц, меню, настроек, импорта, цен и остатков (через существующие точки сброса: `HomePageRenderer::forget()`, `MenuService::flush()`, наблюдатель групп, `CustomerGroupService`); ключи кэша — `home:{group}:{v}`, `menus:{group}:{v}`, `access:{group}:{v}`, `age:has_restricted:{v}` (10 мин). `ViewerContext` — singleton, лениво определяет группу из запроса и сессии (одинаково для Livewire); на этапе 8 зритель — всегда «Гость», этап 9 подключает guard `customer` в `resolveGroup()`. Сотрудник может «Просмотреть витрину как…» группу (флаг в сессии, баннер, `noindex`, `Cache-Control: private`). Режим `all_except` всегда фильтрует `NOT IN` по скрытым id (переключение «по короткому списку» из 25.6 не делалось — индекс по `category_id` используется в обоих случаях). Полностью отмеченные списки режимов/доставки/оплаты хранятся как `null` (без ограничения). `price_display=login` работает в коде, но в форме скрыт до этапа 9 (некуда входить). Если у группы есть раздел «Поиск», но нет «Каталога», поиск тоже закрыт. При удалении группы её id убирается из `visible_group_ids`; опустевший список остаётся `[]` (скрыто от всех, а не открыто всем). Коды способов доставки и оплаты (CG-09) неизменяемы и совпадают с прежними ключами.
- **Отвергнуто:** отдельные кэш-теги (файловый драйвер их не поддерживает); проверка доступа только в шаблонах.

## D-095. Правки по ревью PR #20: sitemap, главная роли без дашборда, предпросмотр витрины (CG-15, CG-18, RB-08, RB-13, AG-07)
- **Решение:** (1) sitemap пересобирается задачей `GenerateSitemap` (unique until processing, после коммита) при сохранении/удалении группы, при смене `is_active`/`parent_id`/`slug` категории и товара (+ `category_id`), страницы (+ `visible_group_ids`) и при удалении записей; создание записей ничего не ставит (новый URL подберёт ночной запуск); в тестах выключено `SITEMAP_REBUILD_ON_CHANGE=false` (sync-очередь пересобирала бы файл на каждое сохранение). (2) Роль без `dashboard.view` на `/admin` перенаправляется на первый пункт своей навигации, при отсутствии доступных разделов остаётся 403. (3) Не-администратор правит и удаляет только роли, права которых — подмножество его прав (`EscalationGuard::canManageRole`, и в политике, и в сервисе); `is_system` и `permissions_version` роли не массово заполняемые. (4) «Просмотреть витрину как…» — POST с CSRF (действие Filament — Livewire-действие, выход — форма в баннере); право `customer_groups.view` проверяется на каждом запросе; корзина, оформление, резерв и заявка в предпросмотре закрыты сообщением (`ViewerContext::assertNotPreview()` в `CartService`/`OrderService`). (5) `CatalogVersion::current()` и группа «Гость» запоминаются на время запроса, сбрасываются в `ViewerContext::beginRequest()`, при `bump()` и перед каждым заданием очереди. (6) Серверный слой не рисует возрастную плашку, если cookie `shop_age` уже подтверждает нужный уровень (и ставит `data-age-ok`), поэтому посетитель без JavaScript проходит; кэшируемые фрагменты (главная) от cookie по-прежнему не зависят.
- **Отвергнуто:** вызовы пересборки sitemap в каждом контроллере/форме; статическая память `CustomerGroup::guest()` в модели (устаревала бы в долгих процессах и тестах).

## D-096. Сессии покупателя: guard `customer`, версия авторизации, формы кабинета на Blade (CA-02…CA-08, CA-31, CA-32)
- **Контекст:** файловые сессии на Beget нельзя перечислить и удалить; сессии покупателя и сотрудника в одном браузере не должны влиять друг на друга.
- **Решение:** отдельный guard `customer` (провайдер `customers`, свой брокер паролей). Сессия хранит `auth_version`, с которой покупатель вошёл; middleware `ValidateCustomerSession` в группе `web` (покрывает и Livewire) сбрасывает сессию, если версия аккаунта выросла (сброс/смена пароля, смена email, блокировка, запрос удаления) или аккаунт заблокирован/обезличен. Сброс — удаление ключа guard и cookie «запомнить меня», а не `logout()`: тот меняет `remember_token` и завершил бы действующие сессии на других устройствах. Каждое увеличение версии меняет `remember_token`, сессия из cookie «запомнить меня» без сохранённой версии принимает текущую. Выход из админки переопределён (`StaffLogoutController`), чтобы не делать `session()->invalidate()` и не выбрасывать покупателя. Формы регистрации, входа, сброса и профиля — обычные Blade-формы с контроллерами и Form Request: CSRF, `session()->regenerate()` и работа без JavaScript; состояние многошаговых сценариев (ожидаемый email, билет сброса) — в сессии.
- **Отвергнуто:** таблица сессий для «завершить другие сессии» (драйвер сессий — файлы, раздел 2); Livewire-формы входа (регенерация сессии и CSRF внутри Livewire-запросов сложнее, без JS не работают).

## D-097. Коды подтверждения и лимиты (CA-04…CA-07, CA-25)
- **Решение:** `VerificationCodeService` хранит только хэш кода; пауза повторной отправки, часовые лимиты и блокировка — `RateLimiter` на кэше (в продакшене — файловый). Для неизвестного адреса выполняются те же проверки и лимиты, но ничего не сохраняется и не отправляется — ответ неотличим от существующего аккаунта. Пауза и неверный код — возврат с ошибкой; часовой лимит и блокировка — HTTP 429 с `Retry-After`. 20 неверных вводов за сутки блокируют все назначения для адреса, владельцу (только если аккаунт есть) уходит письмо о подборе. Письма с кодом — очередь с тремя попытками и `ShouldBeEncrypted`, чтобы открытый код не лежал в `jobs`/`failed_jobs`; контроллер не трогает почтовый транспорт, поэтому сбой почты не раскрывает существование аккаунта. Вход по паролю: счётчик ошибок по паре email+IP, на 5-й — блокировка пары на 15 минут; неподтверждённый аккаунт с верным паролем получает новый код и попадает на страницу подтверждения; запрошенное удаление отменяют вход по коду и сброс пароля по коду (вход по паролю при запрошенном удалении закрыт).
- **Отвергнуто:** таблица попыток (лишние записи в БД на каждую попытку); раскрытие «такого аккаунта нет».

## D-098. Заказ без регистрации, группа новых покупателей, кабинет (CA-01, CA-09…CA-18, CA-26…CA-28, CG-11, CG-12)
- **Решение:** `ViewerContext::mayOrder()` — вошедший покупатель может оформлять; гость — только при включённой настройке «Заказ без регистрации» и без `require_login_to_order` у группы «Гость». Корзина гостю остаётся доступной, закрываются оформление, резерв и заявка (проверка на сервере в `OrderService`, на витрине вместо кнопки — ссылка «Войти»). Группа новых покупателей — флаг `customer_groups.is_default_for_new` (ровно одна группа, меняется на странице настроек через `CustomerGroupService`), а не свойство настроек: удаление такой группы запрещено. Заказы под аккаунтом хранят снимок группы (`customer_group_id`, `customer_group_name`) без внешнего ключа на группу. Выборки кабинета ограничены `customer_id`, деталь обращения — по UUID через `OrderPolicy::viewAsCustomer`, чужой UUID — 404. Страницы вошедшего покупателя отдаются с `Cache-Control: private, no-store`.
- **Отвергнуто:** закрыть корзину гостю целиком (теряется подборка до входа, CA-15 сливает корзины); ключ группы новых покупателей в настройках (рассинхрон при удалении группы).

## D-099. Заявки на оптовый доступ (CG-20…CG-25)
- **Решение:** лимит «не более 3 заявок в месяц» — скользящие 30 дней, отклонённые заявки учитываются; одна ожидающая заявка и лимит проверяются в `WholesaleApplicationService` под блокировкой строки покупателя. Покупатель, уже состоящий в группе с `is_wholesale_default`, повторно не подаёт. При одобрении реквизиты копируются в `customer_companies`, только если их нет; юридического адреса в заявке нет — он остаётся пустым и заполняется в кабинете. «Вернуть в новые» (только Администратор) очищает решение и сохраняет комментарий, но не откатывает группу и реквизиты. Уведомления магазину — два независимых переключателя (email и Telegram), по задаче на адрес и одну на Telegram; сбой отправки не ломает подачу. Журнал действий хранит только идентификаторы, IP покупателя в журнал сотрудников не пишется. При обезличивании покупателя синхронный слушатель `CustomerAnonymizing` стирает персональные поля заявок (включая причину отказа и комментарий сотрудника), статус и решение остаются. Удаление группы (CG-25) — только с выбором группы для переноса покупателей (не «Гость», не неактивная); правила цен, промокоды и групповые цены появятся на следующих этапах — их очистка добавляется там же (наблюдатель группы или внешний ключ с каскадом).
- **Отвергнуто:** календарный месяц для лимита (сброс 1-го числа позволяет 6 заявок подряд); сброс группы при «Вернуть в новые» (неожиданно для покупателя, решение принимает менеджер отдельно).

## D-100. Один Telegram-бот для покупателей и магазина (версия 2.1, TG-01)
- **Контекст:** бот уже шлёт уведомления магазину в рабочий чат (NT-02); нужны Mini App, статусы покупателю и действия сотрудников. Номера D-100+ зарезервированы за версией 2.1, чтобы не пересекаться с решениями этапов 8–15.
- **Решение:** один бот и один токен; все настройки бота переносятся миграцией настроек из группы `notifications` в новую группу `telegram` (`TelegramSettings`) с сохранением значений; переключатели уведомлений магазину остаются в «Уведомлениях». Обновления — только через вебхук с секретом в заголовке, идемпотентность по `update_id`; быстрые ответы — в теле ответа вебхука, остальное — очередь.
- **Отвергнуто:** второй бот для покупателей (две настройки, два вебхука, путаница у владельца); `getUpdates`/long polling (нужен демон — запрещено разделом 2); сторонние Telegram-SDK для PHP (Bot API — несколько HTTP-вызовов, пакет не нужен).

## D-101. Mini App — та же витрина в «режиме Telegram» (TM-06)
- **Контекст:** владелец выбрал «весь магазин» в Mini App; на Beget нет Node и SPA запрещены.
- **Решение:** Mini App использует те же маршруты, контроллеры, Livewire-компоненты, Blade-шаблоны и сервисы; режим Telegram хранится в сессии (`channel = telegram`) и меняет только макет (`layouts.telegram`) и небольшой Alpine-компонент `tgBridge` (тема, `BackButton`, `MainButton`, вибрация). Страницы без `tgBridge` остаются рабочими.
- **Отвергнуто:** отдельное SPA с API (дублирование логики цен, групп, остатков; запрещено разделом 2); параметр `?tg=1` в адресе (подделывается ссылкой, ломает кэш и канонические адреса).

## D-102. Вход в Mini App по подписи Telegram, привязка аккаунта кодом из письма (TM-02, TM-04)
- **Контекст:** покупатель не должен вводить пароль в Telegram; оптовикам нужны их цены.
- **Решение:** сервер проверяет `initData` по алгоритму Telegram (все поля, кроме `hash`, включая `signature`; HMAC-SHA256 с ключом `HMAC("WebAppData", токен)`; `hash_equals`; срок `auth_date` по умолчанию 1 ч, проверяется только при создании сессии). Неизвестный Telegram — гость. Привязка к аккаунту сайта — только после кода из письма (CA-04) или одноразовой ссылки из кабинета (TG-07); привязка подтверждается кнопкой в боте с маскированным email (защита от подсунутой чужой ссылки), владельцу уходит письмо; после привязки Mini App входит автоматически, только пока `customers.auth_version` равна запомненной при привязке — сброс пароля, смена email, «завершить сессии» и блокировка снимают привязку. Вход через Telegram действует только в режиме Telegram и не появляется на сайте.
- **Отвергнуто:** вход по `initDataUnsafe` (подделывается клиентом); автоматическое создание аккаунта по Telegram без email (ломает модель кабинета CA и обезличивание); сопоставление по номеру телефона без кода (номер в профиле не подтверждён).

## D-103. Cookie сессии в Mini App и поддержка Telegram Web (TM-03)
- **Контекст:** приложения Telegram открывают Mini App во встроенном браузере (cookie первой стороны), Telegram Web — во фрейме другого сайта, где браузеры ограничивают cookie.
- **Решение:** для `/tg*` и в режиме Telegram middleware `TelegramCookieMode` выставляет cookie сессии `SameSite=None; Secure; Partitioned`, остальные cookie витрины (XSRF, корзина, возраст, промо, согласие) создаются одной фабрикой `StorefrontCookie` с теми же атрибутами; пустой `WebApp.initData` на клиенте снимает режим (`POST /tg/leave`); поддерживаются официальные приложения Telegram, Telegram Web — где браузер принимает такие cookie, иначе понятное сообщение «Откройте в приложении Telegram или на сайте». Для ответов в режиме Telegram вместо `X-Frame-Options` отправляется `Content-Security-Policy: frame-ancestors 'self' https://web.telegram.org`; админка во фрейме не открывается.
- **Отвергнуто:** передавать `initData` с каждым запросом вместо сессии (переписка всех форм и Livewire-запросов); отключать защиту от фреймов для всего сайта.

## D-104. Внешний скрипт telegram-web-app.js (TM-13)
- **Контекст:** раздел 3 требует собирать фронтенд Vite и не тянуть внешние скрипты; Mini App не работает без официального скрипта Telegram.
- **Решение:** `https://telegram.org/js/telegram-web-app.js` подключается только на `/tg` и в режиме Telegram, без закрепления версии и SRI (Telegram требует актуальную версию и меняет файл), не входит в бюджет NF-03.
- **Отвергнуто:** копия скрипта в `resources/js` (устаревает и ломается при обновлении клиентов Telegram); собственная реализация протокола `postEvent` (недокументированные детали для разных платформ).

## D-105. Действия сотрудников из Telegram и «Рабочее место» (TS-03, TS-05)
- **Контекст:** менеджеру нужно реагировать на заказ с телефона, не открывая полную админку.
- **Решение:** кнопки в сообщениях рабочего чата и Mini App «Рабочее место» вызывают те же сервисы смены статуса и проверяют права через `PermissionService` при каждом действии; сотрудник определяется по привязке `telegram_accounts.user_id` (одноразовая ссылка из профиля). Защита от гонок — `orders.version`, опасные действия — в два нажатия. Вход «Рабочего места» — отдельный guard `telegram_staff` (провайдер `users`), который не принимают ни панель Filament, ни маршруты `auth:web`; переключение покупатель ↔ сотрудник в `/tg/session` выходит из другого guard. Пометка сессии флагом отвергнута на ревью: флаг перезаписывается при входе в Mini App покупателя, а маршруты `auth:web` вне Filament его не проверяют. Журнал — `admin_audit_log` и `order_status_history.source = telegram`.
- **Отвергнуто:** Filament во встроенном браузере Telegram (тяжело, вход через Telegram дал бы полный доступ к админке); действия без привязки сотрудника по участию в рабочем чате (любой участник группы мог бы менять заказы).

## D-106. Минимальные исправленные версии PHP (PHP2Shell, CVE-2026-109618/109619)
- **Контекст:** 21.10.2026 PHP выпустил экстренные исправления двух уязвимостей с удалённым выполнением кода без авторизации; эксплуатация подтверждена. Исправлены 8.3.36, 8.4.27, 8.5.12. Проект требует PHP ≥ 8.3 и проверял только это.
- **Решение:** минимальные исправленные версии веток — в `config/php_security.php` (обычный массив без `env()`, читается и без Laravel). Его используют: `EnvironmentChecker` (`shop:doctor`, страница «Система» — ошибка; для сборок дистрибутивов с суффиксом версии — предупреждение, так как они вносят исправления без смены номера), `.github/scripts/php_security_check.php` в CI (шаг после установки PHP) и в деплое (проверка PHP на хостинге до загрузки файлов — деплой останавливается; флажок запуска `allow_vulnerable_php` позволяет выкатить срочное исправление, пока хостинг не выпустил исправленный PHP, — с предупреждением в журнале). Проверка деплоя намеренно строже `shop:doctor`: суффикс сборки дистрибутива она не учитывает, Beget собирает PHP без суффикса. CI дополнительно прогоняет тесты на PHP 8.4 и 8.5 (необязательная проверка `compat`). При следующем исправлении безопасности обновляется только этот файл. Регрессия SimpleXML в 8.4.27/8.5.12 проект не затрагивает: SimpleXML используется только в dev-инструментах.
- **Отвергнуто:** поднять ограничение в `composer.json` до `^8.3.36` — платформенная проверка Composer роняла бы сайт с фатальной ошибкой при уязвимом PHP вместо понятного сообщения; закреплять точную версию PHP в CI — setup-php и так ставит последнюю сборку ветки.

## D-107. Название магазина в письмах — из настроек

## D-108. Канонический email и привязка кода регистрации к сессии (ревью этапа 9)
- **Контекст:** независимое ревью этапа 9 нашло захват аккаунта на MySQL: сортировка `utf8mb4_unicode_ci` не различает регистр и диакритику, поэтому `victim@gmail.com` = `victim@gmáil.com` в `WHERE` и уникальном индексе, а почта уходит на punycode-домен злоумышленника (сброс пароля, вход по коду, привязка гостевых заказов). Второе — гонка CA-05: повторная регистрация неподтверждённого адреса подменяла пароль, и жертва подтверждала аккаунт с паролем злоумышленника.
- **Решение:** `EmailNormalizer` — единственная форма адреса: обрезка пробелов, нижний регистр, локальная часть только ASCII, домен в punycode (`idn_to_ascii`, UTS-46); иначе адрес отклоняется правилом `CanonicalEmail` во всех формах покупателя и в оформлении. Хранение и поиск — только в канонической форме, плюс проверка точного совпадения после выборки (`hash_equals`) и сравнение в PHP в `OrderLinker`; миграция приводит сохранённые адреса к канонической форме. Данные повторной регистрации (имя, телефон, хэш пароля) хранятся в записи кода и применяются только при подтверждении этого кода; код привязан к сессии, из которой шла регистрация (хэш случайного токена сессии), — код из другой сессии не принимается. Регрессионный тест — на MySQL.
- **Отвергнуто:** сменить сортировку колонок на `utf8mb4_bin` (зависит от драйвера, SQLite в тестах её не проверит, остаются расхождения регистра); только перенос данных в код без привязки к сессии (жертва всё равно вводит новый код, запрошенный злоумышленником).

## D-109. Несколько сайтов из одного репозитория: окружение GitHub на сайт
- **Контекст:** владельцу нужно разворачивать ещё сайты на Beget из этого же кода (тот же или другой аккаунт).
- **Решение:** каждый сайт — отдельное окружение GitHub (`production`, `shop2`, …) со своими секретами `BEGET_*` и своими правилами защиты (подтверждение владельца, только `main`). `deploy.yml` получает вход `site` (выбор из списка) и использует `environment: ${{ inputs.site }}`; группа concurrency — на сайт. Добавить сайт = создать окружение с секретами и дописать имя в список `options` (`docs/DEPLOY_BEGET.md`, раздел 13).
- **Отвергнуто:** копия `deploy.yml` на каждый сайт (расходятся правки и исправления деплоя); префиксы секретов на уровне репозитория (`SHOP2_BEGET_PATH` и т. п.) — секреты всех сайтов видны любому запуску, нет отдельного подтверждения на сайт.

## D-110. Подтверждение телефона: звонок-сброс основным способом, провайдер за интерфейсом (версия 2.2, PV)
- **Контекст:** владелец хочет подтверждать номера покупателей недорого для российских номеров. С 2026 года SMS с буквенным именем отправителя требуют регистрации имени у операторов и ежемесячной платы за каждое имя (порядка 1–4 тыс. ₽ у каждого оператора), а SMS без зарегистрированного имени часть операторов блокирует; сама SMS стоит ≈ 5–11 ₽. Звонок-сброс стоит ≈ 0,2–1,9 ₽ и не требует имени отправителя.
- **Решение:** основной способ — звонок-сброс (ввод последних 4 цифр номера звонящего), запасной — SMS (по умолчанию выключен), бесплатный путь — номер из Telegram (TG-09). Провайдер — за интерфейсом `PhoneVerificationGateway`; первым реализуется SMS Aero (звонок и SMS в одном API), остальные (SMSC.ru, SMS.ru, МТС Exolve) подключаются драйверами. Отправка — синхронно в запросе (очередь на Beget раз в минуту слишком медленна для ожидания звонка), с лимитами на номер, IP, сессию и дневным пределом магазина против «накрутки» платных звонков. Сценарии включаются владельцем. Пропуск проверки возможен только при сбое провайдера из закрытого списка (сеть, 5xx, ошибка ключа) и включён по умолчанию, чтобы не терять заказы; нулевой баланс и исчерпание дневного предела блокируют (их может вызвать злоумышленник); лимиты и неверный код никогда не пропускают. Звонок запускается только после проверки остальной формы, отдельной точки «позвонить на номер» нет.
- **Отвергнуто:** только SMS (дороже и с абонплатой за имя); Telegram Gateway основным каналом (оплата в иностранной валюте, ограничения Telegram в России) — «Позже»; сторонние SDK провайдеров (новые пакеты не нужны: несколько HTTP-вызовов).

## D-111. Деплой не привязан к Beget: имя корня сайта — переменная окружения
- **Контекст:** владелец хочет иметь возможность разместить магазин у другого провайдера (Timeweb, Sprinthost, REG.RU, VPS). В `deploy.yml` было жёстко зашито имя корня сайта `public_html` (так у Beget); у других хостингов это может быть `www`, а на VPS веб-сервер сразу смотрит в `public/`.
- **Решение:** переменная окружения GitHub `DEPLOY_DOCROOT` (не секрет): по умолчанию `public_html`, другое имя папки или `none` (ссылка не создаётся). Имя проверяется (латиница, цифры, `. _ -`; не `.`/`..`/`public`) и не может совпадать с файлом или папкой приложения. Секреты `BEGET_*` сохраняют имена (переименование сломало бы настроенные окружения) и означают любой SSH-сервер. Сравнение хостингов и пошаговые инструкции — `docs/HOSTING_ALTERNATIVES.md`.
- **Отвергнуто:** отдельный workflow на каждого провайдера (расходятся исправления деплоя); переименование секретов в `DEPLOY_*` (ручная перенастройка уже работающего окружения).

## D-112. Миграция характеристик из JSON: политика потерь, резервная копия, состояние, `option_type_id` без FK (этап 10, ревью PR #31)
- **Контекст:** переносу JSON → таблицы (FL-04) подходят не все значения (слово в числовой характеристике, второе значение одиночной, значение длиннее 255 знаков). Такие значения отбрасывались, а JSON — единственная копия v1 — пересобирался без них. Массовые «Задать/Снять характеристику» до конца миграции переписывали JSON товара, у которого есть только JSON, и мигратор потом его пропускал.
- **Политика потерь:** значения, не подходящие к типу, в таблицы не попадают, но не пропадают бесследно. (1) Перед записью пачки исходный `products.attributes` каждого затрагиваемого товара дописывается в JSONL-файл `storage/app/private/attribute-migration/backup-<run-id>.jsonl` (диск `local`, строка `{product_id, attributes}`, `run-id` берётся из состояния прогона); строка товара не перезаписывается — побеждает первый оригинал во всех прогонах и файлах (`AttributeJsonBackup`). (2) `shop:attributes-restore-json [--product=ID]` возвращает исходный JSON и удаляет строки товара в таблицах, чтобы повторный `shop:attributes-migrate` перенёс его заново; флаг завершения миграции не трогается. (3) Холостой прогон показывает число значений и товаров, которые потеряют данные, и до 10 примеров (товар, характеристика, значение); действие в админке при потерях > 0 требует отмеченного чекбокса. (4) JSON мигрированного товара всегда пересобирается из строк, в том числе когда все значения отброшены (иначе устаревший JSON молча стирался бы позднейшей синхронизацией); оригинал остаётся в резервной копии.
- **Блокировка массовых операций:** пока миграция не завершена, `AttributeService::setAttributeForProducts` и `removeAttributeFromProducts` отказывают (`AttributeException::migrationPending`), если среди товаров есть «только JSON» (есть характеристики в JSON, строк нет); в админке оба массовых действия отключены с пояснением, пока `AttributeMigrationState::isPending()`. Импорт и редактор товара уже обходят такие товары (`isJsonOnly`, `isLegacy`); форма, открытая в режиме JSON, не сохраняется, если к моменту сохранения товар перестал быть «только JSON» (`MapsProductFormData::$loadedLegacySpecs`), — иначе скрытый типизированный редактор сохранял бы пустой набор поверх строк.
- **Состояние миграции:** флаг завершения — `CatalogSettings::attributes_migrated_at` (spatie/laravel-settings); прогресс «N из M», `last_id`, `run_id` — запись в файловом кэше без TTL (`AttributeMigrationState::CACHE_KEY`), сбрасывается при завершении. Без новых таблиц; потеря кэша = следующий запуск начинает с первого товара, это безопасно (идемпотентно, товары со строками пропускаются).
- **`category_filters.option_type_id` без внешнего ключа до этапа 11:** таблица опций модификаций (`option_types`) появляется на этапе 11; пока колонка — обычное nullable `unsigned bigint` без индекса, целостность держит `CategoryFilterService`. Внешний ключ добавит миграция этапа 11.
- **Отвергнуто:** отказ от переноса при любых несоответствиях типу (блокирует магазин из-за одной ячейки); хранить оригинал в отдельной таблице БД (раздувает БД, файл проще удалить после проверки).

## D-113. Фасеты: выборка как производная таблица (FL-12, ревью PR #31)
- **Контекст:** на MySQL 8 при 20 000 товаров × 8 характеристик запрос min/max чисел шёл 200–270 мс, списки — 55–110 мс (цель FL-12 ≤ 100 мс). План: оптимизатор шёл диапазонным сканом индекса чисел (~100 тыс. строк) вместо selective-фильтров.
- **Решение:** `FacetService` строит выборку (`CatalogQuery::selection()` с теми же видимостью FL-21 и фильтрами) как производную таблицу `SELECT DISTINCT products.id … ) sel` (DISTINCT не даёт MySQL слить её во внешний запрос) и присоединяет `product_attribute_values` по `product_id`; один запрос на числа и один на каждый список, без CTE и оконных функций. Для запроса чисел сразу после `select` стоит оптимизаторная подсказка `/*+ JOIN_ORDER(sel, fv) NO_BNL(fv) NO_RANGE_OPTIMIZATION(fv) */` — SQLite и MariaDB до 11.x считают её комментарием; MySQL 5.7 не знает `JOIN_ORDER`, выдаёт предупреждение и выполняет запрос как обычно (ошибки нет); MariaDB 12.x также лишь предупреждает. Для списков подсказка не нужна и вредна. Замеры (20 000 × 8, MySQL 8.0.46, тёплые): числа 215 → 15 мс, списки 50–62 → 33–51 мс. `FACET_PERF_MAX_MS` по умолчанию 100.
- **Отвергнуто:** `STRAIGHT_JOIN` (не переносится на SQLite); `fv.product_id IN (подзапрос)` (110–150 мс); подсказка для списков (секунды).

## D-114. Карточка без активных модификаций распродана; агрегат цены в этом случае (VR-06, VR-07, VR-08, ревью PR #32)
- **Контекст:** по правилу 19.5 `stock_qty` карточки — `NULL`, если нет активных модификаций; но `NULL` во всей витрине значит «остаток не учитывается — товар доступен», поэтому скрытая или деактивированная полной синхронизацией карточка выглядела «в наличии» (в списке, фильтре «в наличии» и на кнопке), а дашборд (`NOT EXISTS`) считал её распроданной.
- **Решение:** у карточки с модификациями без единой активной модификации `stock_qty = 0` и `reserved_qty = 0` (распродана, VR-08); `NULL` остаётся только когда активная модификация не учитывается. Это же значение пишут `VariantAggregator`, `shop:variants-rollup` и проверка `shop:doctor`. Включение модификаций без «модификации из текущих данных» обнуляет остаток карточки до появления первых модификаций. Список, фильтр «в наличии» (по агрегату) и дашборд (`NOT EXISTS`) дают один и тот же ответ (тест на шесть сценариев). Цены: пока есть хотя бы одна живая (не удалённая) модификация, но ни одной активной, `final_price`/`final_price_max`/`display_old_price` считаются по всем живым модификациям (карточка не показывается как «без цены»; доступность определяют остатки); у карточки совсем без модификаций цены остаются прежними.
- **Отвергнуто:** оставлять `NULL` и учитывать модификации в `AvailabilityService`/фильтре (три места с разной логикой); обнулять цены карточки без активных модификаций (пропадает цена в админке и в карточке).

## D-115. Агрегаты модификаций считаются в транзакции под блокировкой карточки (VR-06, 19.5, ревью PR #32)
- **Контекст:** отложенный пересчёт после `commit` читал модификации без блокировки и мог затереть `stock_qty`/`reserved_qty` карточки устаревшими значениями, пока параллельное оформление держит строку карточки; в MySQL (REPEATABLE READ) обычный `SELECT` внутри транзакции к тому же показывает строки на момент её начала.
- **Решение:** `VariantAggregator::refreshNow()`, `rollupStock()` и `rollupAll()` работают в транзакции: сначала `SELECT … FOR UPDATE` строки карточки (порядок блокировок карточка → модификации сохраняется), затем модификации читаются блокирующим чтением (`FOR UPDATE`, актуальные данные, а не снимок транзакции), затем запись. `batch()` вызывается внутри транзакции (`create`/`update`/массовые операции/генератор), а не снаружи; при исключении отложенный пересчёт отбрасывается. Удалённые в корзину карточки не пересчитываются, при восстановлении агрегат остатка пересчитывается. Параллельность проверена на MySQL двумя процессами (последняя единица; скрытие модификации во время оформления), на SQLite — порядок запросов и уровень транзакции.
- **Отвергнуто:** повторять пересчёт «до совпадения» без блокировки; пересчитывать агрегат только по расписанию (расхождение видно покупателям до 24 часов).

## D-116. Выключение модификаций удаляет их безвозвратно (VR-25, ревью PR #32)
- **Контекст:** при выключении переключателя модификации и оси карточки удаляются физически (`forceDelete`): иначе их артикулы и сочетания навсегда блокировали бы создание заново, а позиции прошлых заказов хранят снимок и от модификации не зависят (`variant_id` → `NULL`).
- **Решение:** поведение сохранено; действие в админке предупреждает о необратимости и требует ввести артикул карточки (проверяется и в форме, и на сервере). Доступно только когда нет незавершённых обращений с товаром (VR-25). Остаток-агрегат переходит в собственный остаток карточки, цена возвращается к собственной.
- **Отвергнуто:** мягкое удаление при выключении (артикулы остаются занятыми, при повторном включении возникают «призрачные» сочетания); кнопка без подтверждения.

## D-117. Повторное создание сочетания удалённой модификации (VR-03, VR-04, VR-25, ревью PR #32)
- **Контекст:** индивидуально удалённая (мягко) модификация продолжает занимать `unique(product_id, combo_hash)` и артикул; чтобы сочетание можно было создать заново, старую строку удаляют физически.
- **Решение:** физическое удаление при повторном создании разрешено, только если на старую модификацию не ссылается ни одно незавершённое обращение (те же статусы и сообщение со списком номеров, что в VR-25); иначе создание отклоняется. Строки корзины с этой модификацией удаляются. Гонка уникальных индексов (артикул в одной таблице, `combo_hash`) превращается в обычную ошибку проверки (`SkuGuard::guard()`, форма товара, импорт строки), а не в 500.
- **Отвергнуто:** физически удалять всегда (теряется связь `variant_id` у открытого заказа и возврат остатка идёт мимо модификации).

## D-118. Внешний ключ `category_filters.option_type_id` только на MySQL (FL-05, VR-19, ревью PR #32)
- **Контекст:** SQLite (тесты) не умеет добавлять внешний ключ к существующей таблице; на MySQL значение без опции сорвало бы миграцию.
- **Решение:** миграция этапа 11 создаёт ключ только на MySQL (как `price_history.import_id`); перед этим очищает значения `option_type_id` без опции (`NULL`) и удаляет фильтры-опции, оставшиеся без опции, на обоих драйверах. Цель — продолжать вести схему SQLite для тестов, а реальную целостность обеспечивает MySQL.
- **Отвергнуто:** пересоздавать `category_filters` на SQLite ради ключа (лишний риск для данных тестов без пользы для продакшена).

## D-119. Заявка гостя не хранит снимок группы (CA-26, GP-12, GP-13, ревью PR #33)
- **Контекст:** у заказа под аккаунтом есть снимок группы (`customer_group_id`, `customer_group_name`); у гостя аккаунта нет.
- **Решение:** заказ гостя остаётся без снимка группы (поведение CA-26 не меняется). Цены гостю считаются для группы «Гость» (GP-13), а источник цены каждой позиции (`price_source`, `tier_min_qty`, `retail_price`) записывается в строку заказа и виден в админке.
- **Отвергнуто:** писать в заказ гостя id и название группы «Гость» (расходится с CA-26 и ломает фильтр заказов по группам: гость не покупатель группы).

## D-120. Хеш покупателя для лимита промокода — HMAC-SHA256, `char(64)` (PM-09, 22.5)
- **Контекст:** в 22.5 указан `customer_hash char(40)`, а HMAC-SHA256 в hex занимает 64 символа.
- **Решение:** `promo_redemptions.customer_hash char(64)` = HMAC-SHA256(APP_KEY, lower(email) + "|" + телефон) для гостя; у покупателя с аккаунтом лимит считается по `customer_id`. Погашенные (возвращённые) использования не учитываются. Лимит гостя проверяется только при оформлении: в корзине email и телефон ещё неизвестны.
- **Отвергнуто:** SHA-1 ради длины 40 (слабее, без выгоды).

## D-121. Неактивный код выглядит как несуществующий (PM-09, PM-14, 22.8)
- **Решение:** для отключённого кода покупатель видит то же «Промокод не найден», что и для неизвестного, чтобы перебор не выявлял существующие коды. Внутри сервиса причина остаётся `Inactive` (для журналов и тестов).

## D-122. Порог «минимальной суммы» и «бесплатной доставки от» (PM-02, PM-09, SF-45)
- **Решение:** минимальная сумма промокода сравнивается с суммой всех строк корзины после групповых цен и акций, до промокода (а не только с подходящими строками). Порог бесплатной доставки SF-45 по-прежнему считается от суммы товаров до промокода; код типа «бесплатная доставка» дополнительно обнуляет стоимость доставки.

## D-123. Корзина и промокод: ручное управление и автоприменение (PM-10)
- **Решение:** `carts.promo_applied_manually` = покупатель сам ввёл или сам удалил код. Код из cookie `shop_promo` применяется автоматически, только пока у корзины нет кода и флаг снят. При слиянии гостевой корзины с корзиной покупателя код гостя сохраняется, если у корзины покупателя своего кода нет. Если при оформлении код перестал проходить проверку (исчерпан, истёк, превышен личный лимит), он снимается с корзины, а покупатель возвращается к корзине с причиной (`CartChangedException`).

## D-124. Возврат кода и статистика промо-ссылок (PM-12, PM-24, PM-25)
- **Решение:** использование возвращается при переходе заявки в «Отменён» или «Истёк» и при удалении активной заявки; возврат идёт после возврата остатков, порядок блокировок: заявка → товары → модификации → промокод; повтор безопасен (`released_at`). В статистике ссылки заказом считается любая привязанная заявка (включая бронь и запрос), кроме отменённых, истёкших и удалённых; выручка = сумма `orders.total`. Значения UTM очищаются удалением символов вне `[A-Za-z0-9._-]`, пустое значение опускается; цель `catalog_filter` обязана начинаться с `/catalog`.

## D-125. Оформление из смешанной корзины: результат и связь заявок (MR-05, MR-11, MR-12)
- **Решение:** `OrderService::checkoutFromCart()` возвращает `CheckoutResult` (заказ и/или резерв); прежний `createFromCart()` возвращает одну заявку (заказ, иначе резерв) для совместимости. `orders.related_order_id` заполняется у обеих заявок (взаимная ссылка, `null on delete`), чтобы страница «Спасибо», значок «связан с …» и письмо находили пару с любой стороны. Дополнительное поле `orders.reserved_via_cart` (bool) нужно фильтру «Резерв из корзины», чтобы включать и резерв без связанного заказа.
- **Уведомления:** покупатель получает одно письмо (по первой из пары, со всеми заявками); магазину — письмо и Telegram по каждой заявке.

## D-126. Вид строки корзины и кнопки карточки (MR-02, MR-03, MR-07)
- **Решение:** режим «Резерв» — основная кнопка «В резерв» (в корзину) и ссылка «Зарезервировать только этот товар» (форма SF-50). Режим «Корзина и резерв» — основная «В корзину», та же ссылка; выбор заказ/резерв делается при оформлении (строки `flexible`). Строка `flexible` без остатка или при выключенной настройке становится `order` («Под заказ» не резервируется). Минимальная сумма (SF-43) проверяется по части «заказ» на сервере; со страницы корзины с `flexible`-строками можно перейти к оформлению и ниже минимума, чтобы выбрать резерв. При нехватке остатка для резерва корзина не меняется, а показывает строки с кнопкой «Уменьшить до доступного».

## D-127. Редактирование заказа: права, нехватка, промокод, уведомления (OE-02, OE-05, OE-06, OE-09, OE-12)
- **Права:** стоимость доставки — достаточно `orders.edit_items` (OE-02 перечисляет её отдельно от цен); цены позиций, «Пересчитать по прайсу» и общая скидка — `orders.edit_prices`, проверяется и в сервисе.
- **Нехватка:** `EditStockShortageException` с перечнем позиций и доступным количеством; полный откат.
- **Промокод:** повторное сохранение без изменения позиций не пересчитывает скидку (иначе закончившаяся акция меняла бы сумму без изменений состава); удалённый код — сохраняется прежняя скидка, не больше суммы позиций. Порог предупреждения — только по ручной скидке, в процентах от суммы позиций (0 — выкл.).
- **Уведомления:** письмо и запись в кабинет — по чекбоксу «Уведомить покупателя» (настройка задаёт его значение по умолчанию). Заказ из заявки: письмо покупателю о новом заказе по настройке и чекбоксу; событие `OrderCreated` не вызывается (магазин не уведомляется о действии собственного менеджера).
- **Версия:** увеличивается при смене статуса, продлении резерва, сохранении комментария менеджера и редактировании; сообщение о конфликте называет сотрудника (`orders.updated_by_user_id`), если известен.

## D-128. Резерв позиции, у которой отключили учёт остатка (OE-04, ревью PR #35)
- **Контекст:** 24.5 говорит «`stock_qty IS NULL` → остатки позиции не меняются». Но если товар успел удержать количество в резерве (`stock_applied_qty > 0`), а потом учёт остатка у него выключили, удаление или уменьшение такой позиции оставляло `reserved_qty` навсегда.
- **Решение:** для резерва редактор освобождает удержанное (`applied − newApplied`) так же, как `releaseReservation()` при отмене, даже если `stock_qty` сейчас NULL; новые удержания для такой позиции не делаются. Для заказа правило 24.5 остаётся как есть.
- **Отвергнуто:** оставлять `reserved_qty` (после возврата учёта доступный остаток занижен).

## D-129. Порядок блокировок при создании заказа из заявки и при выборе части оформления (OE-12, MR-02, ревью PR #35)
- **Решение:** номер нового заказа (`order_sequences`) выделяется после блокировки товаров и модификаций — как при оформлении корзины. Оформление запоминает показанное покупателю разделение «заказ / резерв»; если на сервере оно изменилось (режим товара сменили в админке), обращения не создаются, а покупатель видит причину и проверяет оформление заново.

## D-130. Пределы PDF-выгрузки снижены по замеру памяти (CX-05, раздел 2)
- **Контекст:** замер dompdf на этапе 15: ≈ 0,15 МБ на строку таблицы. 1 000 обращений без состава — 7,1 с и ≈ 171 МБ сверх базовых ≈ 45 МБ процесса; 300 обращений × 5 позиций — 20,8 с и ≈ 182 МБ. Лимит памяти Beget — 128 МБ (раздел 2 приоритетнее раздела 18); CX-05 разрешает понижать пределы настройкой по результатам замера.
- **Решение:** значения по умолчанию — PDF не более 400 обращений без состава и 100 с составом, плюс общий предел 450 строк таблицы (`export_max_pdf_rows`); синхронно PDF строится только до 300 строк таблицы. Пороги синхронной генерации (Excel 300; PDF 200 / 50) и предел Excel 20 000 строк — как в ТЗ. Все значения меняются в «Покупатели и регистрация» → «Выгрузки». Замеры: 200 без состава — 33 МБ / 1,5 с; 50 × 5 — 40 МБ / 3 с; 400 без состава — 53 МБ / 3,5 с; 450 строк — 53 МБ / 5,2 с.
- **Отвергнуто:** оставить 1 000 / 300 (задача падает по памяти на Beget).

## D-131. Обновление зависимостей при приёмке версии 2.0 (NF-52, NF-54)
- **Решение:** перед этапом 15 выполнено `composer update laravel/framework symfony/* --with-dependencies` в пределах текущих ограничений версий (Laravel 13.38 → 13.42, Symfony 7.4.21 → 7.4.23) — закрыты опубликованные уязвимости; `composer audit` чистый. Добавлен `barryvdh/laravel-dompdf` ^3.1 (D-079). Шаблоны PDF: удалённые ресурсы, PHP и JS выключены, chroot — `resources/views/pdf`, кэш шрифтов — `storage/fonts` (каталог создаётся при деплое).

## D-132. Мобильная вёрстка: оверлеи, безопасные зоны, нижняя панель (MB-02, MB-03, MB-12)
- **Решение:** нижние листы и выдвижные панели открываются через Alpine-директиву `x-overlay`: на телефоне она добавляет запись в историю, поэтому «Назад» закрывает окно, а не уходит со страницы; закрытие вручную удаляет запись. Отступы задаются CSS-переменными `--shop-safe-*`, `--shop-nav-total`, `--shop-sticky-h` на `:root` (по умолчанию `env(safe-area-inset-*)`), чтобы режим Telegram переопределил их значениями `safeAreaInset` (TM-07). Нижняя панель скрывается атрибутом `html[data-kb]`, пока в текстовом поле фокус; страница отключает панель секцией `no_bottom_nav`. Плашка возраста на телефоне — нижний лист без закрытия жестом «назад» (нужен ответ).
- **Кнопки связи (MB-10):** имя бота для «Написать в Telegram» берётся из `config('shop.telegram_bot_username')` до появления настроек бота (этап 17 переведёт на `TelegramSettings`); WhatsApp — ссылка `wa.me`/`whatsapp.com` из социальных ссылок «Основных» настроек.

## D-133. Установка на телефон и канал обращения (MB-20…MB-24, TM-14)
- **Решение:** иконки PWA (192, 512, 512 maskable с полями 10 % на цвете фона, 180 для iOS) создаются `AppIconGenerator` в `storage/app/public/app-icons/` с хешем набора в имени (`pwa_icons_hash`); ошибка генерации выключает PWA с уведомлением, а не срывает сохранение. Ключ кэша манифеста — хеш входных настроек, поэтому сохранение видно сразу. Канал `pwa` принимается от клиента только из перечисления и только вне режима Telegram; `telegram` с клиента не принимается никогда — его ставит сервер по флагу сессии `App\Support\TelegramMode::SESSION_KEY` (этап 17).

## D-134. Скилл Hallmark в репозитории как инструмент разработки (TH-33, А.10)
- **Решение:** скилл Hallmark (github.com/Nutlope/hallmark, лицензия MIT) установлен командой `npx skills add nutlope/hallmark --agent claude-code` без ключа `-g`: файлы лежат в `.claude/skills/hallmark/`, отпечаток версии — `skills-lock.json` в корне. Это инструмент разработки для сессий Claude Code (материал тем, `sloplint`, `/hallmark audit`), а не зависимость приложения: не входит в `composer.json` / `package.json`, не попадает на хостинг (`/.claude/` и `/skills-lock.json` исключены из деплоя). Скрипты, обращающиеся к сети или меняющие настройки (`imagegen.mjs`, `theme.mjs photos --save`, `install-hook.mjs`), в проекте не запускаются. Обновление — повторной командой `npx skills add` отдельным PR.

## D-135. Хранение шрифтов тем (TH-18, TH-19, TH-21)
- **Решение:** 60 семейств лежат в `public/fonts/<slug>/` (slug — имя семейства в нижнем регистре, всё кроме `a-z0-9` заменено на `-`, например `golos-text`, `m-plus-rounded-1c`). Файлы `<slug>-<cyrillic|latin>-<вес>-normal.woff2` по каждому весу из `fonts.json`, у Fira Sans Extra Condensed ещё `-900-italic`; рядом `LICENSE` (OFL или Apache 2.0). Файлы один раз взяты из npm-пакетов `@fontsource/*` (58 пакетов версии 5.3.0, 2 — 5.3.1; кириллица — набор `cyrillic`, латиница — `latin`) и закоммичены как есть: ни во время работы, ни при сборке зависимости от npm нет, поэтому TH-21 (dev-зависимости) не нужен, `package.json` не менялся. Диапазоны `unicode-range` — стандартные для этих наборов (`FontFamily::RANGES`, одинаковы у всех пакетов). Витрина отдаёт шрифты только со своего домена; `font-display: swap`, предзагрузка кириллического начертания заголовков и текста. Тема `default` использует системный стек (`"family": "system"` — имя вне реестра, файлы не грузятся).

## D-136. Хранение темы и переопределений (TH-03, TH-04)
- **Решение:** поля `theme_id` (по умолчанию `default`) и `theme_overrides` добавлены в `AppearanceSettings` (группа `appearance`), а не в новую группу: страница «Оформление» и права `settings.appearance.*` те же. `theme_overrides` — JSON вида `{<id темы>: {colors: {bg, surface, ink, primary, accent}, fonts: {display, body}}}`, каждый ключ необязателен; при чтении проходит `ThemeResolver::sanitizeOverrides` (цвет — `#RRGGBB`/`#RGB`, шрифт — из реестра, шрифт текста — не «только для заголовков»). Миграция настроек переносит заданные ранее `primary_color` / `accent_color` (SF-04) в `theme_overrides['default']`, если они отличались от прежних значений по умолчанию (`#2563eb`, `#f59e0b`) — вид витрины не меняется. Старые поля остаются в классе как зеркало: `ThemeManager` записывает в них итоговые основной и акцентный цвета активной темы для кода вне системы тем (страницы ошибок до перевода на токены); `down()` удаляет только новые поля. Письма и печатные формы вне охвата (TH-15).

## D-137. Кэш CSS темы и ключ кэша главной (TH-12, TH-19)
- **Решение:** сгенерированный CSS (`:root` + `@font-face`) кэшируется в файловом кэше под ключом `theme-css:<FORMAT>:<версия реестра>:<id темы>:<хеш переопределений>`; `FORMAT` — константа `ThemeCss::FORMAT`, её нужно увеличивать при каждом изменении генерируемого CSS (иначе после деплоя отдаётся устаревший блок из кэша); версия — хеш файлов `resources/themes/*.json`, поэтому правка реестра при деплое и сохранение настроек дают новый ключ, а прежний `ThemeManager` сбрасывает перед сохранением. Предупреждение о неизвестном id темы пишется в лог один раз в сутки на id (флаг в кэше). В ключ кэша главной добавлено `<id темы>-<хеш переопределений>` (`home:{группа}:{версия каталога}:{тема}`).

- **Шрифт заголовков:** `h1`–`h3` и `.font-display` берут токены `--shop-font-display`, `--shop-display-style/case/scale` в правиле без слоя в `app.css`; вес, межстрочный интервал и трекинг применяются только если тема печатает `--shop-display-weight-set` (вес не 700), `--shop-display-line-height`, `--shop-display-tracking` (иначе `revert-layer`, и работают классы шаблона). Поэтому тема `default` не меняется ни на пиксель. Названия товаров (заголовок `h3` карточки) выходят из правила классом `font-body` (`:not(.font-body)`): как в макетах, они набираются шрифтом текста, весом 500, без регистра и курсива темы.

## D-138. Предпросмотр темы (TH-27…TH-30)
- **Решение:** предпросмотр — флаг `theme_preview` (`theme_id` и несохранённые `overrides`) в сессии сотрудника. Админка и витрина используют одну веб-сессию и одну cookie (панель Filament подключает те же `StartSession` и guard `web`), отдельных токенов нет. `ActiveTheme` использует флаг, только если запрос несёт вошедшего активного сотрудника с правом `settings.appearance.update`; иначе флаг игнорируется и показывается включённая тема, поэтому подделанная сессия гостя ничего не меняет. Кнопки плашки («Предыдущая», «Следующая», «Применить», «Выйти») — POST с CSRF и повторной проверкой права; «Применить» сохраняет тему и переопределения через `ThemeManager` (с записью в журнал). Ответ в предпросмотре получает `Cache-Control: private, no-store` и `X-Robots-Tag: noindex` (`ThemePreviewHeaders`); кэш главной в предпросмотре обходится. Режим «Телефон» — страница админки `ThemePhonePreview` с `iframe` 390 × 844, загружающим витрину в той же сессии. Предпросмотр темы формы берёт несохранённые цвета и шрифты формы, другой темы — её сохранённые переопределения.

## D-139. Производные цвета (TH-07, TH-08)
- **Решение:** при переопределении `ink` или `bg` пересчитываются `muted` (72 % текста + 28 % фона), `line` (16 % + 84 %) и `tile` (6 % + 94 %): доли — медианы по 50 темам реестра. При переопределении `primary` / `accent` текст на них (`onPrimary` / `onAccent`) — белый или чёрный с лучшим контрастом по WCAG. `surface` производных не имеет, `heroBg` / `heroInk` остаются значениями темы (пара самодостаточна). Предупреждение о контрасте — для пар `ink/bg`, `ink/surface`, `onPrimary/primary`, `onAccent/accent` ниже 4,5:1; сохранение не блокируется.
- **Обновление реестра:** источник правды — `docs/themes/themes.json` и `fonts.json`; рабочие копии в `resources/themes/` обновляются копированием (`cp docs/themes/{themes,fonts}.json resources/themes/`), тест сверяет их побайтно. Тема `default` живёт только в `resources/themes/default.json`.

## D-140. Тема `default`: системный шрифт и ярлык «Хит» на акцентном цвете (TH-03, TH-05)
- **Шрифт:** нынешняя витрина использует системный шрифтовой стек Tailwind, которого нет в `fonts.json`. В `resources/themes/default.json` для заголовков и текста записано `"family": "system"`: такой шрифт не подключается через `@font-face` и не предзагружается, токены `--shop-font-*` получают системный стек. Администратор может заменить его любым шрифтом из списка (TH-20).
- **Ярлык «Хит»:** раньше был залит цветом палитры Tailwind (amber-500), теперь — `--shop-accent`, потому что по контракту TH-05 акцент предназначен для ярлыков и меток. В теме `default` отличие — несколько оттенков (#F59E0B вместо amber-500 в oklch); если администратор раньше менял акцентный цвет, ярлык теперь следует ему. Остальные страницы по сравнению скриншотов до и после совпадают попиксельно (9 страниц × 1280 и 390 px).
- **Цвета статусов** (успех, ошибка, предупреждение) — фиксированные семантические токены в блоке токенов `app.css` (значения палитры Tailwind в oklch), а не производные темы: так пары «текст / фон» статусов остаются читаемыми в любой теме.

## D-141. Знак «₽» и цвет текста на кнопках после переноса цветов (TH-18, TH-03, TH-07; ревью PR #39)
- **«₽»:** в проект входят только наборы `cyrillic` и `latin` (TH-18); у fontsource символ U+20BD лежит в наборе `latin-ext`, поэтому знак рубля в ценах рисуется резервным системным шрифтом того же начертания. Наборы `-ext` не добавляются, чтобы не увеличивать вес страниц; если владелец захочет «₽» в шрифте темы, добавляется набор `latin-ext` только для U+20BD (отдельное решение).
- **Текст на кнопках:** заданные до обновления основной и акцентный цвета (SF-04) становятся переопределениями темы `default`, а для переопределённого цвета `onPrimary` / `onAccent` выбирается по контрасту (TH-07). Магазин со светлым основным цветом (например, жёлтым) после обновления получит на кнопках чёрный текст вместо белого — это осознанный выбор в пользу читаемости (контраст TH-08); при необходимости владелец выбирает другой основной цвет.

## D-142. Варианты шапки H1–H4 и проверка особенностей шапки и первого экрана (TH-10, TH-12, TH-14)
- **Решение:** шапки лежат в `partials/header/h1…h4`, выбор — `BlockExtras::header($theme)`; меню, контакты MB-10 и кнопка установки общие. H1 — прежняя разметка без изменений классов (тема `default`). Особенности, попадающие в атрибут `style` (`heroButton`, `heroImage`, `headerRule`), проверяются в `BlockExtras`; неверное значение считается незаданным.
- **Поиск в H2/H4:** поле всегда в DOM, но визуально скрыто до нажатия на иконку или фокуса, чтобы «Поиск» в нижней панели продолжал работать; без JavaScript иконка — обычная ссылка на `/search`. В H3 «Каталог» — нативный `<details>`, работает без JavaScript.

## D-143. Первый экран главной G1–G4 (TH-12)
- **Решение:** вариант меняет только подачу блоков конструктора «Слайдер», «Баннер», «Категории». G2 и G4 — полоса во всю ширину на `heroBg` / `heroInk`; G3 собирается в `HomePageRenderer::build()` из баннера или слайдера и идущего следом блока категорий (первые три категории — в бенто-сетке, остальные — обычными плитками). Если блоков нет, первый экран не выводится. Ключ кэша главной уже содержит тему и хеш переопределений (D-137).

## D-144. Карточки C1–C6 и листинги L1–L3 (TH-11, TH-13)
- **Решение:** один диспетчер `partials/product-card` выбирает `partials/cards/c1…c6`; варианты используют общие части `_media` (фото) и `_actions` (кнопки по режиму продаж), поэтому данные и действия во всех вариантах одинаковы (тест сценариев корзины, резерва, заявки и оформления для C1–C6). У корня карточки `data-card`, у плитки фото `data-tile` и `data-tile-index` — к ним привязаны особенности тем.
- **C4:** две строки — первые две непустые характеристики товара «название: значение» (данные уже загружены с карточкой, без лишних запросов). **C5:** строка прайса при ширине карточки от 42rem (container query), иначе компактный столбик; до трёх ступеней цены группы. **C6:** ячейки без зазоров, нумерация — позиция в листинге (продолжается после «Показать ещё»).
- **L2 и L3:** фильтры-чипы сверху и та же форма фильтров панелью под ними; на телефоне — прежняя выдвижная панель и лист сортировки. L3 — на колонку больше настройки «Колонок в сетке» и фильтры сверху (как в эталонах). Панель фильтров скрыта по умолчанию только при включённом JavaScript (`@media (scripting: enabled)`).
- **Сетка главной:** компонент `card-grid` сам читает `homeGridColumns` (тема «Маркет» — 5 колонок).

## D-145. Поверхности, особенности плиток и состояния элементов (TH-14, TH-16, TH-17)
- **Решение:** стиль поверхностей задаётся атрибутом `html[data-surface]` (плюс `data-bw`, `data-tile-shape`, `data-dashed`, `data-crop-marks`, `data-bg-image`); правила, меняющие вид, действуют только для поверхностей, отличных от `line`, поэтому тема `default` не меняется. Цвета тени и кромки (`shadowColor`, `shadowTint`, `pressColor`) выводятся токенами только у тем, где они заданы: hex или `rgba()` по строгому шаблону. Градиенты (`tilePatterns`, `backgroundImage`) проверяет `CssValue::gradient()` по белому списку функций и ключевых слов — без `url()`, кавычек, `;` и `{}` (TH-09). `tileColors` и `tilePatterns` — правила по `[data-tile-index]` по кругу.
- **Состояния:** фокус-кольцо из токена `--shop-focus`, нажатие, недоступность, загрузка (`data-loading` Livewire или `aria-busy`), ошибка (`aria-invalid`) — в `@layer components`, явные утилиты имеют приоритет; исключение — рамка поля при наведении (не для поверхности `line`) и при ошибке: правила вне слоёв, иначе утилита `border-line-strong` их перебивает. При `prefers-reduced-motion` анимации и переходы отключены; содержимое сворачиваемых блоков видно без JavaScript (`<noscript>`-правило).

## D-146. Временная служебная тема `debug-blocks` (этап 21; удалена на этапе 23, D-163)
- **Решение:** тема существует только при `THEME_DEBUG=true` (`config('shop.theme_debug')`), не попадает в галерею и сохранённые настройки, доступна только сотруднику в предпросмотре: `?theme=debug-blocks&blocks=H3,C5,G2,L3`. Значения проверяются по допустимым наборам и хранятся в сессии сотрудника.

## D-147. Плашка предпросмотра на телефоне (TH-27)
- **Решение:** уже 640 px плашка занимает два ряда (название темы, затем кнопки); переключатель «Компьютер / Телефон» на узком экране скрыт — режим «Телефон» и так открывается в рамке 390 px.

## D-148. Настройки и подключение бота (TG-01, TG-02, TG-04, TG-11)
- **Решение:** поля бота перенесены из `notifications` в группу `telegram` (`telegram_enabled` → `enabled`, `telegram_bot_token` → `bot_token`, `telegram_chat_id` → `work_chat_id`) обратимой миграцией с сохранением зашифрованного значения. Mini App, автовход и уведомления покупателю по умолчанию включены; кнопки действий в рабочем чате и «Рабочее место» — выключены (привилегированные функции). Секрет вебхука генерируется заново при каждом «Подключить бота» и сохраняется только после успешного `setWebhook`; токен и секрет никогда не попадают в состояние формы. Новый токен сохраняется только после того, как его принял `getMe`.
- **Вебхук:** маршрут в `routes/web.php` с `withoutMiddleware('web')` — без сессии, cookie и CSRF; режим «Магазин закрыт» на него не действует (тест).

## D-149. Привязка Telegram и исходящие сообщения (TG-07, TG-08, TG-10)
- **Решение:** подтверждение привязки — кнопки с `callback_data` `lc:{id}:{hash8}` / `ln:{id}:{hash8}`; «Это не я» сжигает токен. Перерисовка вопроса — единственный синхронный исходящий вызов (NF-60), ответ — `answerCallbackQuery` в теле ответа вебхука. Ссылка «Получать статус» выдаётся при каждом показе страницы «Спасибо» и скрыта для обращений, уже привязанных к Telegram, и внутри Mini App.
- **Очередь:** задачи Telegram используют `retryUntil` (2 ч) и `maxExceptions = 3` вместо `tries`, чтобы откладывание по лимиту частоты не расходовало попытки. В тестах лимиты выключены флагом `TELEGRAM_RATE_LIMITS=false` (синхронная очередь не умеет откладывать), тесты лимитов их включают.
- **Сотрудник:** привязка — страница `/admin/my-telegram` в меню пользователя (ссылка, состояние, отключение); полный TS-02 — этап 18. Проверки `shop:doctor` для Telegram зелёные, пока бот не подключён (NF-63).

## D-150. Mini App: макет, сессия, cookie (TM-01, TM-03, TM-06, TM-12)
- **Решение:** `layouts/app` — диспетчер: в режиме Telegram (только по флагу сессии) — `layouts.telegram`, иначе — `layouts.site` (прежний макет), поэтому шаблоны страниц не менялись. `/tg/session` возвращает JSON с адресом, а параметр запуска разбирает следующий запрос `GET /tg/start` — так `/tg/session` укладывается в 5 SQL (TM-13). `TelegramCookieMode` выставляет `SameSite=None; Partitioned` только на HTTPS и восстанавливает настройки на следующем обычном запросе; все cookie витрины создаются фабрикой `StorefrontCookie`. Скрипт `telegram-web-app.js` и `resources/js/telegram.js` (отдельная точка входа сборки, 2,6 КБ gzip) подключаются только на `/tg` и в режиме Telegram — бюджет NF-03 не меняется.
- **Вход:** в Mini App страница входа предлагает только код из письма; вход кодом и подтверждённая регистрация привязывают Telegram (`TelegramSessionService::linkSessionAccount()`); вход паролем на сайте Telegram не привязывает. «Выйти» в Mini App снимает привязку.
- **Оформление:** `telegram_account_id` записывается в `OrderService::createRecord` для канала `telegram`; дополнительный лимит 5 отправок в минуту на `telegram_user_id` (`FormGuard`). Ответ `requestWriteAccess()` клиента — заявление: если бот всё же не сможет написать, первая отправка отметит чат заблокированным (D-149).
- **Сайт → Telegram:** базовая ссылка «Открыть в Telegram» хранится в кэше и обновляется при сохранении настроек Telegram — страницы сайта не делают лишнего запроса (NF-02). Параметры `staff` / `staff_o_{id}` до этапа 18 ведут на главную.

## D-151. Уведомления покупателю в Telegram: условия, дедупликация, получатель (TN-01…TN-07)
- **Решение:** если функция, событие или бот выключены, получателя нет или ключ дедупликации уже есть — строка в `telegram_messages` не пишется и запросов к Telegram нет (NF-63). Если получатель есть, но писать ему нельзя (чат не начат, бот заблокирован, `/stop`, событие выключено покупателем), пишется строка `skipped` с кодом причины, который карточка обращения показывает по-русски.
- **Дедупликация:** строка с уникальным `dedupe_key` создаётся до постановки задачи, задача отправляет только строку в статусе `queued`; ключи: `created:{order}`, `status:{order}:{status}:{version}`, `reservation-ended:{order}:{status}`, `expiring:{order}:{reserved_until}`, `items:{order}:{batch}`, `wholesale:{app}:{status}:{decided_at}`, `export:{id}`. Задача перепроверяет `canMessage()` при отправке (нажатый в очереди `/stop` отменяет сообщение); 403 → `bot_blocked_at`, без повторов.
- **Получатель (NF-62):** если покупатель обращения и покупатель, привязанный к Telegram, различаются, сообщение не отправляется; обезличенному покупателю — ничего; гостевое обращение из Mini App — в свой `telegram_account_id`. Смешанная корзина (MR) — по сообщению «принят» на каждое обращение. Для резерва «истёк» и «отменён» — событие «резерв истёк или снят», остальные переходы — «статус изменён»; переход в `new` сообщения не даёт (его покрывает «принят»).
- **Кнопки:** «Открыть заказ» — `web_app` на `{APP_URL}/tg?to=o_{uuid}` (без Mini App — обычная ссылка на страницу обращения); «Позвонить в магазин» — ссылка на страницу «Контакты» (tel: в кнопках Telegram не поддерживается). Отписка — `tn:stop` под каждым сообщением, ответ во всплывающем окне.

## D-152. Telegram для сотрудников: кнопки, отдельный guard, идемпотентность (TS-01…TS-08)
- **Guard:** `telegram_staff` (сессия, провайдер users) проверяется middleware `EnsureTelegramStaff` на каждом запросе: привязка, `is_active`, `orders.view`, функция включена, срок 8 ч. `Auth::shouldUse('telegram_staff')` действует только на время запроса (восстанавливается в `finally`); компоненты Livewire «Рабочего места» дополнительно перепроверяют доступ при монтировании и каждом действии. Внутри действия Livewire (`/livewire/update`) гард по умолчанию снова `web` (persistent-middleware восстанавливает его до вызова метода), поэтому компоненты и сервисы всегда получают сотрудника явно из `StaffSessionService::valid()`; `auth()->user()` / `allowsCurrent()` в них не используются (закреплено тестом). Вход сотрудника не создаёт корзину и кабинет покупателя; выход из режима не вызывает `logout()` (не меняет remember-токен).
- **Кнопки:** коды действий `cf`, `rd`, `ip`, `ex`, `cl`, `cx` в `o:{action}:{id}:{version}`; кнопки показываются только для переходов, разрешённых приложением B. «Рабочее место» (TS-06) показывает все ручные переходы приложения B, включая «Отправлен» (`sh`) и «Выполнен» / «Выкуплен» (`co`) через `OrderService::changeStatus` с источником `telegram`; в чате эти два кода отклоняются (в TS-01 таких кнопок нет). «Отменить» — два нажатия, ключ `tg-staff-confirm:{action}:{order}:{version}:{staff}` на 30 с серверного времени (версия в ключе: устаревшее подтверждение не превращает следующее нажатие в отмену). Все функции сотрудников требуют подключённого бота (`StaffAccess::botReady()` = `TelegramBotSetup::isConnected()`, NF-63), а не только токена; переключатель «Отправлять уведомления в рабочий чат» (`enabled`) не главный выключатель: он влияет только на сообщения и кнопки рабочего чата (`buttonsEnabled()`), но не на «Рабочее место» (TS-05/TS-06) и личные уведомления (TS-08). Кнопки личных копий (TS-08) зависят только от `work_chat_buttons_enabled` и подключённого бота: `StaffOrderMessage::markup($order, $cancelArmed, $forWorkChat)` и `StaffAccess::buttonsEnabled($forWorkChat)` (для рабочего чата дополнительно нужен `enabled`); обработчик нажатий определяет тип чата (private — личная копия), перерисовка копий строит клавиатуру отдельно для рабочего чата и личных чатов (TD-29). Версия проверяется дважды: до действия и под `lockForUpdate` в одной транзакции с вызовом `OrderService` — два одновременных нажатия не выполнят действие дважды.
- **Перерисовка:** нажатое сообщение — синхронный `editMessageText` с таймаутом 2 с и запасной задачей; копии в рабочем и личных чатах (журнал `telegram_messages`) — задачами очереди. Изменения из админки старые кнопки не перерисовывают заранее: устаревшая кнопка отвечает «Обращение уже изменено» и перерисовывает своё сообщение.
- **Журнал:** действия из Telegram пишутся в `admin_audit_log` с источником `telegram` (смена статуса, продление резерва, комментарий менеджера); в истории статусов — источник `telegram`. Личные уведомления сотрудника (TS-08) — только при включённом переключателе в профиле, привязке и праве `orders.view` (перепроверяется в задаче); отвязка сбрасывает переключатель.

## D-153 (A-1). Данные подтверждения телефона: `cost` decimal(12,4), поле `note`, какие записи пишутся (PV-08)
- **Контекст:** PV-08 задаёт колонки `phone_verifications`; нужно решить, какие обращения оставляют запись и как хранить причину пропуска.
- **Решение:** `cost` — `decimal(12,4)`: явное исключение из правила `decimal(12,2)` (провайдеры указывают доли копейки; в итогах округляется). Добавлено поле `note` (до 40 символов): причина пропуска или блокировки (`network`, `timeout`, `server`, `auth`, `daily_limit`, `balance`, `refused`) для журнала («пропущено: сбой провайдера»). `code_hash` допускает NULL: у записей `skipped_provider` и `blocked` кода нет. Запись создаётся для каждого обращения к провайдеру и для пропуска/блокировки после сбоя и предела дня; отказы по лимитам номера/IP/сессии (429) записей не создают — иначе их количество росло бы без ограничения. Дневной предел считает только строки с `provider_request_id`. Старый открытый код того же номера, назначения и сессии при выдаче нового получает итог `expired`; просроченные `pending` переводятся в `expired` в `shop:cleanup` перед удалением старше 90 дней.
- **Отвергнуто:** писать строку на каждый отказ по лимиту (рост таблицы при атаке); хранить код в открытом виде (PV-03 — только HMAC).

## D-154 (A-2). Привязка кода к сессии и «подтверждён в этой сессии» (PV-03, PV-06, PV-07)
- **Контекст:** D-108 привязывает код регистрации к сессии хэшем случайного токена; тот же подход нужен кодам телефона.
- **Решение:** при первом обращении в сессию кладётся случайный токен (`phone_verification.binding`); в записи хранится его SHA-256 (`session_hash`), он же входит в HMAC кода (`id|назначение|номер|привязка|код`): код из другой сессии не принимается ни по записи, ни по хэшу. Токен, а не id сессии, потому что id меняется при входе (`regenerate`). Лимит «на сессию» считается по тому же хэшу. После успеха в сессии хранится `назначение → {HMAC номера, срок 24 ч}`: номер в сессии не лежит открытым, на одно назначение — один подтверждённый номер (смена номера затирает прежний, `forget()` сбрасывает). Ограничение подбора и лимиты — RateLimiter на файловом кэше (NF-53), IPv6 — по подсети /64 (IPv4-mapped IPv6 — как IPv4).
- **Отвергнуто:** привязка к id сессии (ломается при входе покупателя); хранение открытого номера в сессии.

## D-155 (A-3). SMS Aero API v2: допущения, которые владелец должен сверить с личным кабинетом
- **Контекст:** сети к документации в сессии нет; драйвер написан по известной форме API v2, примеры ответов — `tests/Fixtures/sms_aero/*.json` (составлены по описанию, не сняты с боевого аккаунта).
- **Допущения (проверить при первом подключении, кнопками «Проверить подключение» и «Отправить тест на мой номер»):** базовый адрес `https://gate.smsaero.ru/v2`; HTTP Basic (логин = e-mail кабинета, пароль = API-ключ); звонок-сброс — `POST /flashcall/send` с полями `phone` (без «+») и `code` (4 цифры), ответ `{"success":true,"data":{"id":…,"code":"…","cost":"…"}}`; SMS — `POST /sms/send` с `number`, `text`, `sign` (имя отправителя, если задано); баланс — `GET /balance`, `data.balance` числом; стоимость — `data.cost`. Классификация: сеть и таймаут (`ConnectionException`), HTTP 5xx, HTTP 401/403 и ответ `success:false` с текстом про авторизацию/ключ — сбой (PV-05); HTTP 402 и текст «недостаточно средств/баланс» — нулевой баланс, всегда блокирует; любой другой отказ (валидация номера, ответ без `id`, нечитаемый ответ) — отказ провайдера, тоже блокирует, но сбоем не считается. Тексты распознаются по шаблонам в `SmsAeroGateway::AUTH_PATTERN` / `BALANCE_PATTERN`: при расхождении с реальными текстами поправить их там.
- **Ключ в ошибках:** из текстов исключений вырезаются логин, ключ и их base64 (заголовок Basic); тексты обрезаются до 300 символов.

## D-156 (A-4). Порядок проверок и лимиты (PV-05, PV-06)
- **Решение:** в `send()`: блокировка номера → лимиты (сначала проверка всех пяти — пауза 60 с, 3/ч, 6/сутки на номер, 10/ч на IP и на сессию, затем учёт всех: отказанный запрос квоту не тратит) → дневной предел магазина из БД → один вызов провайдера. SMS по кнопке проходит те же лимиты и считается в тех же счётчиках; кнопка доступна только для номера, которому в этой сессии звонили (открытый код-звонок), не раньше 60 с и один раз на звонок; новый код заменяет предыдущий (звонок после SMS перестаёт действовать). Неверные вводы считаются и когда кода нет, код просрочен или попытки исчерпаны (15 в сутки на номер → блок 24 ч; 20 вводов в час на IP). Дневной предел проверяется до вызова без блокировки таблицы: при параллельных запросах возможен перерасход на число одновременных запросов (ограничено лимитами IP/сессии/номера); ради блокировки на время HTTP-вызова (до 5 с) не жертвуем.
- **Назначение `test`** («Отправить тест на мой номер»): те же лимиты и предел; сбой провайдера и предел дня всегда сообщаются администратору, не «пропускаются»; действие пишется в журнал (`phone_verification.test`, в данных только результат и способ, без номера).
- **Предупреждения магазину** (`ShopAlerts`): сбой провайдера, нулевой баланс, дневной предел — не чаще раза в час на тему (`Cache::add`), письмо на адреса «Настройки → Уведомления» и Telegram в рабочий чат по тем же переключателям `notify_shop_email` / `notify_shop_telegram`; задания очереди `SendPhoneVerificationAlert`. Ежедневная проверка баланса — `shop:phone-verification-balance` в 05:10.

## D-157 (A-5). Номера других стран +7 (Казахстан) и нормализация
- **Контекст:** PV-06 допускает добавить префикс `+77`, но `PhoneNormalizer` (SF-44) принимает только первую цифру 3, 4, 8, 9 и отвергает `+77…`.
- **Решение:** `PhoneVerificationService::canonical()` — сначала `PhoneNormalizer`, затем запасное правило `+7` + 10 цифр с первой цифрой 3–9; допустимость задают префиксы настроек (по умолчанию `+79`). `PhoneNormalizer` и формы SF-44 не менялись, поэтому при встраивании (часть B) форма оформления/регистрации всё ещё отвергнет `+77…` до собственной проверки: чтобы казахстанские номера работали, нужно либо расширить правило SF-44, либо использовать `canonical()` в этих формах. Решение за владельцем/оркестратором.

## D-158. Встраивание подтверждения телефона: где решается и как проверяется (PV-07, PV-13)
- **Решение:** одно место решает, нужно ли подтверждение, — `PhoneVerificationGate`: сценарии гостевого оформления, блокировка «обязательно» после регистрации, правила «уже подтверждён» (подтверждённый телефон профиля вошедшего покупателя, подтверждённый номер из Telegram TG-09, номер, подтверждённый в этой сессии для этого назначения) и отметка пропуска. Отметка пропуска (30 минут, привязана к номеру) — единственный путь создать обращение без подтверждения и ставится только сервером после сбоя провайдера при настройке «пропускать». `OrderService` вызывает проверку внутри транзакции оформления, резерва и заявки до создания обращения и сам ставит `orders.phone_verified`: формы только спрашивают, решает сервер.
- **Формы:** оформление, резерв и заявка (Livewire) — общий трейт и компонент шага подтверждения; звонок — только после прохождения проверки остальной формы; изменение телефона отменяет шаг и забывает подтверждённый номер (PV-13 г). Смена телефона в профиле и заявка на опт — «отложенное действие»: контроллер проверяет форму и откладывает действие в сессии, звонок запускается на странице `/account/phone` по кнопке покупателя, действие выполняется после кода (или без подтверждения только при пропуске из-за сбоя).
- **Сценарии гостя:** «все» — все обращения, включая заявки; «только резервы» — часть «резерв», в том числе в смешанной корзине; «заказы от суммы» — сумма части «заказ» `>=` порога. Смешанное оформление — одно подтверждение, оба обращения получают `phone_verified = true`. Вошедших покупателей покрывают блокировка «обязательно» и правило «подтверждён без звонка».

## D-159. Отметка подтверждения у покупателя и в админке (PV-09, PV-10, PV-13 е)
- **Решение:** `customers.phone_verified_at` ставится при подтверждении своего телефона (регистрация, смена в профиле) и кнопкой «Сохранить номер из Telegram в профиль» (только в Mini App при подтверждённом номере Telegram); сбрасывается при смене телефона, повторной регистрации неподтверждённого аккаунта (CA-05) и обезличивании. Подтверждение в заявке на опт отдельной колонки не имеет — свидетельство в журнале `phone_verifications` (назначение `wholesale`).
- **Админка:** значок и фильтр «Телефон подтверждён» в списках и карточках покупателей и обращений; страница «Подтверждения телефона» (право `settings.phone_verification.view`) — журнал за 30 дней с маскированными номерами и итоги месяца (только принятые провайдером запросы; стоимость округляется до копеек через bcmath).
- **Персональные данные:** абзац о провайдере (обработчик ПДн по поручению) добавлен в шаблоны политики и согласия только для новых установок; на работающем сайте страницы правятся вручную (`docs/DEPLOY_BEGET.md`, 10.8) — текст проверить у юриста.

Правила контраста действуют только в 50 темах; тема `default` не меняется ни на пиксель (решение владельца; 15.11.2026 владелец решил, что `default` получает и правила контраста только для Telegram под `html[data-tg]`, вид сайта не меняется, см. D-188). ## D-188. Mini App в тёмной схеме Telegram, бейдж корзины, пагинация, hover (TH-08, TH-15, TH-16, TH-34; ревью этапов 22–23, замечания 1, 2, 4, 5, 6)
- **Контекст:** правила контраста этапа 22 печатали фиксированные hex-значения (`--shop-focus`, `--shop-*-text`), рассчитанные по палитре сайта. В Mini App `telegram.js` (`applyTheme()`) подменяет `--shop-bg / surface / ink / muted / line` цветами Telegram, и в тёмной схеме эти значения оставались тёмными (текст основного цвета у «Опалубки» 1,52:1, кольцо фокуса 1,04:1).
- **Решение:** `ThemeCss::telegramRules()` (`FORMAT` = 7) печатает для всех тем, включая `default` (решение владельца от 15.11.2026), правила под `html[data-tg]` (светлая схема) и `html[data-tg][data-tg-scheme="dark"]` (тёмная; атрибут ставит `applyTheme()`). Значения — `color-mix(in srgb, <цвет темы> N%, var(--shop-ink))` с долей N, рассчитанной на типичных фонах Telegram (светлая: `#FFFFFF`, `#EFEFF3`, `#E6E6EA` с текстом `#000`; тёмная: `#212121`, `#2C2C2C`, `#383838` с текстом `#FFF`), либо сам цвет / `var(--shop-ink)`; основной цвет в миксе — `var(--shop-primary)` (в режиме «цвета Telegram» это кнопка Telegram). Кольцо фокуса — `var(--shop-primary)` или `var(--shop-ink)` по 3:1 на тех же фонах; у полосы G2/G4 свой цвет, как на сайте. Правила печатаются, когда на сайте есть своё правило или цвет не читается в одной из схем. Значения сайта (`:root`) не меняются, поэтому результаты контраста сайта прежние. Расчёт доли — на эталонных фонах, а не на реальных `themeParams` (сервер их не знает): нестандартные тёмные схемы Telegram близки к ним по светлоте.
- **Бейдж корзины:** число на `bg-accent` — `text-on-accent` (`mini-cart`, `mini-cart-bar`); других пар `bg-accent` / `bg-primary` с `text-ink` в витрине нет (проверено по шаблонам и тестом по отрисованным страницам). У `default` `onAccent` = `ink`, вид тот же.
- **Пагинация:** недоступный шаг (`aria-disabled`) в темах получает пунктирную рамку (`[data-page-disabled]` под `html[data-contrast]`) и `cursor-not-allowed`; цвет `ink-high` остаётся (читаемость), `default` без изменений по пикселям.
- **Hover:** переопределения `hover:text-*` печатаются внутри `@media (hover: hover)`, как утилиты Tailwind 4 (на телефоне нет «залипшего» наведения).
- **Последствия:** встроенный CSS тем на 1–2 КБ больше там, где печатаются правила Telegram (у `default` — с 780 до ~2 500 байт, ~350 байт после gzip); блок отдаётся и на страницах сайта, но там не срабатывает (атрибут `data-tg` ставит только макет Mini App), поэтому отрисовка сайта не меняется ни в одной теме, а у `default` вне блока `html[data-tg]` CSS побайтно прежний (проверяет `ThemeTelegramModeTest`). Отдавать блок только в Mini App — возможная оптимизация, не нужная при таком размере. Контраст Telegram проверяется для 51 темы.

## D-176. Надгробие выгрузки покупателя: просроченная ссылка отвечает 410 после очистки (CX-07, 18.7; техдолг TD-25)

## D-177. Лимит частоты запросов выгрузки: слот берётся атомарным увеличением счётчика (CX-09; техдолг TD-26)
- **Контекст:** `ensureCanRequest()` проверял лимит, а `hitRequest()` учитывал запрос позже, поэтому параллельные запросы проходили проверку по одному и тому же устаревшему значению.
- **Решение:** `ensureCanRequest()` сначала делает `AtomicRateLimiter::hit()` (счётчик меняется под блокировкой кэша этого счётчика, D-199) и сравнивает результат с лимитом: превысившие лимит запросы получают 429 и остаются в счётчике. Запрос, отклонённый по другой причине (нет заказов за период, превышен предел раздела 18.6, слишком много необработанных), возвращает слот `releaseRequestSlot()` (`AtomicRateLimiter::decrement()`), как и раньше такие запросы не расходуют лимит. Лимит скачиваний (`hitDownload()`) устроен так же.
- **Отвергнуто:** `RateLimiter::attempt()` (внутри та же пара «проверка, затем hit», окно гонки остаётся).
- **Последствия (исправлено после ревью PR #51):** `RateLimiter::hit()` сам по себе не атомарен на `CACHE_STORE=file` (чтение и запись счётчика не защищены), 12 параллельных процессов получали одинаковые значения. Теперь счётчик меняет `App\Support\AtomicRateLimiter` под `Cache::lock` этого счётчика (на файловом кэше — `flock`); проверено на файловом кэше 12 параллельными процессами: всегда 12 различных подряд идущих значений. Не получив блокировку за 3 с, запрос считается превысившим лимит (отказ по умолчанию, 429). Это же закрывает и лимит скачиваний. Возврат слота при отказе по иной причине допускает расхождение не больше чем на единицу.

## D-178. Снимок реквизитов плательщика в заказе (CX-10, CX-11; техдолг TD-27)
- **Контекст:** `OrderPdfRenderer::document()` брал плательщика из текущих реквизитов компании покупателя, поэтому повторная печать старого счёта показывала новые реквизиты.
- **Решение:** колонка `orders.payer_snapshot` (json, nullable, новая миграция) со структурой `{"company": null | {name, inn, kpp, ogrn, legal_address}}`. Снимок пишется в момент создания обращения под аккаунтом (`OrderService`, рядом со снимком группы по CA-26, счёт датирован днём заказа), при привязке гостевых обращений к покупателю (`OrderLinker`, самый ранний момент, когда реквизиты известны) и при создании заказа из заявки (берётся снимок заявки или текущие реквизиты). Значение «компании нет» тоже сохраняется: реквизиты, добавленные позже, не попадают в старый счёт. Печать (`PayerSnapshot::companyFor()`) берёт снимок, а для заказов без снимка (до миграции, гостевые) — текущие реквизиты. Анонимизация покупателя обнуляет снимок.
- **Отвергнуто:** снимок в момент подтверждения заказа (счёт выставляется по заказу, а не по его статусу, и заявка/резерв тоже печатаются); отдельная таблица реквизитов заказа (лишняя связь ради одного блока).
- **Последствия:** существующие заказы остаются без снимка и печатаются по текущим реквизитам, как раньше.

## D-179. Флаг `price_touched` в редакторе состава заказа (OE-03; техдолг TD-21, TD-22)
- **Контекст:** строка, где администратор ввёл цену, равную цене по прайсу для 1 шт., считалась «нетронутой» по сравнению значений и пересчитывалась по ступени при росте количества.
- **Решение:** скрытое поле строки `price_touched` ставится при любом ручном изменении поля цены. Пока оно ложно, новая строка следует прайсу по количеству (показ) и уходит на сервер без цены; когда истинно, цена уходит как ручная. «+1» на существующей новой строке через поиск также обновляет показанную цену по ступени (`repriceNewRowData()`). Итоговую цену по-прежнему определяет сервер при сохранении.
- **Последствия:** ручная цена, совпавшая с розничной, остаётся ручной (источник `manual`).

## D-164. Режим «все, кроме» всегда фильтрует `NOT IN`; переключение «по короткому списку» не делается (CG-04; долг TD-06)
- **Контекст:** в 25.6 запрос листинга описан как `category_id IN (:product_category_ids)` и «`NOT IN (:hidden)`, когда список скрытых короче». Сейчас `AccessSet::applyToProducts()` для режимов «все» и «все, кроме» использует `NOT IN (скрытые)`, для «только выбранные» — `IN`.
- **Решение:** переключение на `IN (все − скрытые)` для длинного списка скрытых не реализуется. Выигрыша нет: условие одно, по индексу `category_id`, длина списка в обоих вариантах определяется числом категорий (десятки, не тысячи). Риск есть: `IN (видимые)` нужно строить из кэшированного дерева, и категория, созданная после построения набора, до смены версии каталога пропала бы из выдачи, тогда как `NOT IN` показывает её сразу, как и должен режим «все, кроме».
- **Последствия:** поведение 25.6 выполняется по смыслу (результат одинаков); если на реальном каталоге с сотнями скрытых категорий запрос окажется медленным, переключение добавляется в `AccessSet::applyToProducts()` (набор `productCategoryIds` для режима «все, кроме» тогда считается в `CatalogAccess`).

## D-165. Прогрев фасетов категорий без фильтров фоновой задачей (FL-11, FL-12; долг TD-16)
- **Контекст:** на MySQL при 20 000 × 8 фасеты страницы категории без фильтров с пустым кэшем строятся 129–154 мс (числа) и 52–118 мс (списки), что выше 100 мс FL-12. Ключ кэша содержит версию каталога, поэтому более долгий срок хранения не помогает после её смены, а срок в 10 минут задан FL-11.
- **Решение:** `FacetWarmer` (`App\Services\Catalog`) строит эти фасеты через `FacetService::forCategory()` (тот же ключ, что у страницы) для групп «Гость» и «Розница»; остальные группы кэшируются по запросу. Прогреваются только категории, где фасеты без фильтров могут быть медленными: видимые, с набором фильтров и не менее `FacetWarmer::MIN_PRODUCTS` (1000) видимых товаров в поддереве, крупные первыми, не более `FacetWarmer::MAX_CATEGORIES` (100) за проход; счётчики товаров — одним сгруппированным запросом. Меньшие категории строят фасеты заметно быстрее 100 мс, их первый посетитель не ждёт, и они не прогреваются (кэшируются по запросу). Команда `shop:warm-facets` раз в минуту ничего не делает (несколько чтений кэша и один запрос), если не выполнено всё: кэш фасетов включён (`facets_cache_minutes > 0`); не идёт импорт (`Import::anyRunning()`, импорт без активности больше часа считается зависшим); нет цепочки в работе (флаг в кэше, ставится командой, продлевается каждым шагом, снимается в конце, TTL 5 минут на случай гибели воркера); версия каталога «устоялась» (ей не меньше 3 минут: возраст берётся из микросекундной метки токена, непонятный токен считается устоявшимся), так что серии заказов и движений остатков не запускают пересборку; и версия отличается от версии последнего завершённого прохода либо записи того прохода уже истекли (проход старше `facets_cache_minutes + 1` минут; более ранний проход только прочитал бы живые записи из кэша). Задача `WarmCategoryFacets` работает шагами по 30 секунд (лимит 40 с), блокировка кэша не пускает две задачи сразу, остаток списка — следующей задачей со смещением; цепочка помнит версию и останавливается, если версия сменилась (новую начнёт первая устоявшаяся минута). В конце цепочки в кэш пишется последний завершённый проход (версия и время). Только cron и очередь `database`, без демонов.
- **Последствия:** нагрузка — не более одного прохода на устоявшуюся версию каталога и не чаще одного раза в `facets_cache_minutes + 1` минут, только по крупным категориям; во время импорта и серий изменений прогрева нет. Без посетителей запись крупной категории холодна не дольше минуты из каждых `facets_cache_minutes + 1`. Пока цепочка не отработала, первый посетитель крупной категории строит фасеты сам (FL-12 для неё нарушается не дольше нескольких минут после изменения каталога). Проверка времени страницы без фильтров добавлена в `FacetPerformanceTest` (группа `perf`; на MySQL при 20 000 × 8 с холодным кэшем может показать 129–154 мс — это то, что прогрев убирает со страницы).

## D-166. Единая точка пересборки sitemap и подавление во время импорта (SF-82, CG-15; долги TD-02…TD-04)
- **Решение:** `SitemapRebuild::request()` (`App\Services\Seo`) — единственное место, где ставится `GenerateSitemap` после изменений видимости: его вызывают слушатели моделей (`SeoServiceProvider`) и массовые действия «Активировать / Скрыть / Переместить в категорию» в таблице товаров, которые пишут запросом без событий модели. Пока идёт импорт (статусы `analyzing`, `queued`, `processing` с активностью за последний час, `Import::anyRunning()`), задача не ставится, а в кэше ставится флаг «пересборка отложена». `ImportFinished` вызывает `SitemapRebuild::afterImport()`: успешный импорт пересобирает sitemap один раз, упавший или отменённый — только если флаг стоял; флаг снимается, двойной постановки нет. Импорт без активности больше часа считается зависшим и ничего не задерживает.
- **Последствия:** при импорте, идущем параллельно с ручным изменением видимости, пересборка этого изменения откладывается до конца импорта. Тест «одна задача на серию изменений» считает строки таблицы `jobs` при драйвере `database` (уникальность до начала обработки).

## D-193. Вход по паролю: счётчик неудач на IP независимо от адреса (SEC-02)
- **Контекст:** правило CA-06 (5 неудач на пару email + IP) не замедляет перебор «один-два пароля на много аккаунтов»; ограничивал только bcrypt.
- **Решение:** во второй счётчик (`customer-login:ip-fail:<ClientIpKey>`) пишутся только неудачные входы, 20 за 15 минут на «ключ IP» (IPv4 как есть, IPv6 — /64). Он проверяется до `Hash::check` и даёт ту же `CustomerThrottledException` (429), что и пара. Верный вход при счётчике ниже 20 работает и счётчик не сбрасывает (иначе нападающий сбрасывал бы его собственным аккаунтом). Правило пары сохранено; ключи пары теперь тоже строятся от `ClientIpKey`.
- **Последствия:** покупатели за общим адресом (офис, CGNAT) делят 20 неудач за 15 минут; обычные ошибки пароля до этого предела не доходят. Повторное ревью PR #51: проверка до bcrypt теперь тоже считает первой (`AtomicRateLimiter::hit($ipFailKey) > 20` → 429), слот отдаётся обратно (`decrement`) при успешном входе и когда запрос отклонён лимитом пары «email + IP» до проверки пароля; неудача остаётся посчитанной. Поэтому параллельный всплеск не превысит предел 20 за 15 минут (раньше мог — на число воркеров PHP). Отклонённые запросы окно не продлевают (`hit()` ставит срок только на первом попадании). Потерянных обновлений на файловом кэше нет (D-194). Вход по паролю в неподтверждённый аккаунт отвечает точно как неверный пароль (считается неудачей, то же сообщение; D-197).

## D-194. Коды email и защита форм: «сначала посчитать, потом решить» (SEC-03)
- **Контекст:** `VerificationCodeService::request()` и `FormGuard::check()` сначала проверяли лимиты, потом считали.
- **Решение:** каждый лимит — `AtomicRateLimiter::hit() > max`. `RateLimiter::hit()` сам не атомарен на `CACHE_STORE=file` (хостинг, раздел 2 ТЗ): он читает значение и пишет его отдельным шагом, параллельные запросы получают один и тот же счёт (замер ревью PR #51: 12 процессов, 11 из 12 увидели «1»). Поэтому `App\Support\AtomicRateLimiter` меняет каждый счётчик под блокировкой кэша этого счётчика (на файловом кэше это `flock`, исключающий и другие процессы PHP); проверено на файловом кэше 12 параллельными процессами. Если блокировку не удалось получить за 3 с, хелпер возвращает `AtomicRateLimiter::REFUSED` (больше любого лимита): запрос отклоняется, то есть система «закрывается при сбое» и не пропускает лишнего. Тот же хелпер использует вход по паролю, регистрация, проверки текущего пароля, `FormGuard`, лимиты кодов телефона и выгрузки. В `request()` счётчики считаются подряд: сначала IP запрашивающего, и только если он прошёл, — email/час и email/сутки; запрос, отклонённый по собственному IP, не тратит квоты чужого адреса. Отказ по любому из них оставляет свой счёт потраченным. Исключение, как и раньше: слишком ранний повтор (пауза между кодами) квоту не тратит: пауза считается последней, и при её отказе три предыдущих счётчика возвращаются `AtomicRateLimiter::decrement()` (тесты «повторный клик ничего не стоит», TD-15). В `FormGuard::check()` считаются все ключи (IP и Telegram-пользователь), отказ тратит квоту; ключ IP теперь от `ClientIpKey`. `assertPauseOver()` остаётся чистым чтением для вызывающих, которым нужен ранний отказ без трат.
- **Тесты:** счётчик после отказанного вызова равен лимиту + 1 (`VerificationCodeServiceTest`, `FormGuardCountFirstTest`); занятая блокировка счётчика даёт отказ (`VerificationCodeServiceTest`, «fails closed»); запрос, отклонённый по IP, не тратит квоту адреса. Саму гонку на файловом кэше юнит-тест на `array`-кэше не показывает; её проверяют вручную несколькими параллельными процессами на файловом кэше.

## D-195. Коды email: привязка к сессии, счёт только по открытому коду, блокировка на запрашивающего, суточный предел (SEC-04)
- **Контекст:** любой, кто знал email, мог 20 неверными вводами (даже без выданного кода) закрыть вход по коду и сброс пароля этого адреса на 24 часа.
- **Решение:** (1) неверный ввод считается и тогда, когда для адреса и назначения нет открытого кода этой сессии (не истёк, не использован, не аннулирован): иначе блокировка запрашивающего показывала бы, существует ли аккаунт (код в сессии есть только у существующего аккаунта; найдено ревью PR #51, CA-05). Счётчик и блокировка принадлежат паре «адрес + `ClientIpKey`», так что считать ввод без кода безопасно: он блокирует только того, кто вводит, и SEC-04 не открывается. (2) Новый столбец `customer_verification_codes.session_hash` (SHA-256 токена сессии, тот же токен `RegisterController::bindingToken`, что у регистрации) во всех назначениях (вход, сброс пароля, смена email, регистрация, удаление аккаунта): код вводится только из сессии, запросившей его; чужая сессия его не находит, не тратит попытки и не аннулирует. Коды без привязки (выданные персоналом из админки, строки до изменения) принимаются из любой сессии. (3) Счётчик неверных вводов (20 в сутки) и 24-часовая блокировка — на пару «адрес + `ClientIpKey`»: нападающий блокирует только себя, `request()` владельца с другого адреса работает; письмо владельцу «были попытки угадать код» уходит при блокировке только существующему аккаунту и не чаще одного раза в сутки на адрес (`Cache::add`), сколько бы запрашивающих себя ни заблокировало. Глобальная граница подбора — не более 10 выданных кодов на адрес за 24 часа (`REQUESTS_PER_EMAIL_PER_DAY`) от всех запрашивающих вместе, сверх 5 в час и паузы между кодами; запрос сверх предела — тот же 429. Предел считается и для адресов без аккаунта (ответы одинаковы, CA-05).
- **Расчёт (обновлён повторным аудитом, RE-01):** пространство кодов 10^6; попыток на код `code_max_attempts` = 5 (по умолчанию); суточный предел на адрес для всех запрашивающих вместе — 30 кодов (было 10), значит за сутки на адрес не больше 30 × 5 = 150 догадок: 150 ÷ 1 000 000 = 0,015 % на адрес в сутки (при любом числе IP и сессий); коды разных сессий открыты одновременно, но каждый проверяется только из своей сессии и тратит только свои 5 попыток. Чужой код (запрошенный владельцем из его сессии) нападающий проверить не может вовсе.
- **Отступления от ТЗ (принять владельцу продукта):** (1) CA-12 «20 неверных вводов в сутки на email, затем блокировка»: предел на адрес теперь не больше 30 кодов × 5 попыток = 150 неверных вводов в сутки на адрес (при любом числе запрашивающих), плюс блокировка запрашивающего после 20 его неверных вводов; блокировка всего адреса позволяла любому закрыть вход владельцу (SEC-04). (2) CA-12 «запросы кода — 5 в час на email»: после RE-01 это 5 в час на пару «адрес + сеть `ClientIpKey`»; с 6 сетей на один адрес можно получить до 30 кодов за час, суточная граница — 30 на адрес. (3) CA-04 «старый код при новой отправке аннулируется»: теперь новый код аннулирует предыдущие открытые коды только той же сессии; коды других сессий остаются действительными (иначе чужой запрос аннулировал бы код владельца); код без привязки (персонал) по-прежнему аннулирует все.
- **SEC-04 смягчена, а не закрыта полностью:** любой по-прежнему может израсходовать 30 суточных кодов адреса (см. «Повторный аудит, RE-01» ниже: не быстрее 5 в час с одного IP); вход по паролю при этом работает. Быстрого подбора кода при этом нет.
- **Повторный аудит, RE-01 (пересмотр лимитов):** прежние лимиты (общие на адрес: 5 в час и 10 в сутки, новый код аннулирует открытые коды всех сессий, общая пауза) позволяли постороннему за пять запросов с одного IP закрыть владельцу вход по коду и сброс пароля на час, а десятью запросами на сутки. Решение: (1) узкий предел принадлежит запрашивающему: 5 кодов в час на пару «адрес + `ClientIpKey`» (счётчик `customer-code:email:` теперь хеш `адрес|ключ IP`); (2) широкая общая граница на адрес для всех запрашивающих: 30 кодов в сутки (`REQUESTS_PER_EMAIL_PER_DAY`), граница подбора 30 × 5 ÷ 10^6 = 0,015 % в сутки; (3) предел 10 кодов в час на IP (по всем адресам) сохранён; (4) пауза между кодами одного назначения тоже на запрашивающего: ключ «назначение + адрес + `ClientIpKey`» (выбрана пара «адрес + IP», а не сессия: у запроса персонала и у повторной регистрации токена сессии нет, а сессию нападающий меняет бесплатно; `assertPauseOver()` получил параметр IP); чужой запрос больше не запускает паузу владельца; (5) новый код аннулирует только открытые коды той же сессии (`session_hash`); код без привязки (персонал) по-прежнему аннулирует все открытые коды адреса и назначения. `verify()` берёт код сессии вызывающего (или без привязки) с наибольшим id, так что при нескольких открытых кодах разных сессий каждая сессия видит свой. Все лимиты считаются одинаково для адресов без аккаунта (CA-05, D-197): `deliver: false` проходит те же проверки.
- **Остаточный риск после RE-01:** постороннему остаются 30 запросов в сутки на адрес. Один IPv4-адрес набирает 30 кодов не быстрее чем за 6 часов (5 в час), но IPv6-хост с маршрутизируемой сетью /56–/48 владеет сотнями и тысячами сетей /64 и исчерпывает 30 кодов за секунды (как 6 IPv4-адресов); поэтому остающаяся граница — именно 30 кодов (то есть 30 писем владельцу) в сутки на адрес. Каждый запрос присылает владельцу письмо с кодом; при исчерпании 30 кодов до конца суток недоступны вход по коду, сброс пароля и подтверждение этого адреса, вход по паролю не затронут. Пока предел не исчерпан, владелец (другой IP и сессия) может запросить свой код, и его код не аннулируется чужими запросами. Остаток принять владельцу продукта.

## D-196. Смена email требует текущий пароль; путь без пароля не нужен (SEC-05)
- **Контекст:** сессия на чужом устройстве или Mini App давала смену email, а затем сброс пароля на новый адрес.
- **Решение:** `POST /account/profile/email` требует `current_password` (`ChangeEmailRequest`, `CustomerAuthService::requestEmailChange()`); неверный или пустой — ошибка поля, код не выдаётся. Проверка текущего пароля (смена пароля и смена email) использует один общий счётчик на покупателя: 5 проверок в минуту и 20 в сутки (`AtomicRateLimiter`, считается до сравнения, верный пароль возвращает попытку; суточный счётчик считает только проверки, прошедшие минутный предел, поэтому запросы, отклонённые по минуте, не тратят 20 суточных проверок владельца), сверх этого 429. «Отправить код ещё раз» (`resendEmailChangeCode()`) пароль не спрашивает: смена уже начата в этой сессии. Письмо `CustomerEmailChangedMail` на старый адрес получило подсказку «если это были не вы»: восстановление теперь придёт на новый адрес, нужно срочно связаться с магазином. Вариант «код на текущий адрес» для аккаунтов без пароля не реализован: `customers.password` не допускает NULL, аккаунт создаёт только регистрация с паролем, Telegram-аккаунты — отдельная таблица `telegram_accounts` и лишь связаны с покупателем, поэтому аккаунтов без пароля нет.
- **Последствия:** покупатель в Mini App, вошедший по коду из письма, должен знать пароль (при необходимости — восстановить его).

## D-197. Регистрация не выдаёт, что email уже зарегистрирован (SEC-06)
- **Контекст:** форма отвечала «Этот email уже зарегистрирован» для известных адресов и редиректом на страницу кода для новых.
- **Решение:** для подтверждённого (или обезличенного) аккаунта `CustomerAuthService::register()` ничего не создаёт и не меняет, тратит те же лимиты (IP регистраций, лимиты кодов с `deliver: false`, хеширует пароль, как для нового), возвращает null; вместо кода на адрес уходит письмо `CustomerAccountExistsMail` («У вас уже есть аккаунт»: ссылки «Войти» и «Восстановить пароль»), в очереди, как письма с кодом. Контроллер отвечает одинаково: тот же редирект на `customer.confirm` и тот же текст «Мы отправили код на ваш email.». Страница кода для такого адреса: открытого кода нет, любой ввод даёт нейтральное «Неверный код…» и не считается (D-195). Для нового адреса выдаётся код, привязанный к сессии, как раньше. Пароль нового неподтверждённого аккаунта в базе не хранится: в `customers.password` лежит хеш случайной строки, которую никто не знает, а настоящий хеш едет в данных кода (как уже делала повторная регистрация, CA-05) и записывается только при подтверждении (`confirmRegistration()`). Вход по паролю в неподтверждённый аккаунт отвечает ровно как неверные данные и тратит те же счётчики неудач (`authenticateByPassword()`), иначе вход с выбранным при регистрации паролем показывал бы новый адрес (редирект на `/account/confirm`) и зарегистрированный (ошибка данных) по-разному (повторное ревью PR #51). Путь «вошёл с верным паролем, но email не подтверждён → страница подтверждения» убран; неподтверждённый покупатель возвращается на страницу кода по ссылке регистрации или регистрируется заново (код придёт снова). Вход по коду и сброс пароля неподтверждённому аккаунту недоступны, как и раньше. Чтобы покупатель не остался без пути назад, на странице входа всегда (для любого адреса, поэтому ничего не выдаёт; при включённой регистрации) показана подсказка «Регистрировались, но не ввели код из письма? Зарегистрируйтесь ещё раз с тем же email — мы пришлём новый код.» со ссылкой на регистрацию (`account.login.unconfirmed_hint`); повторная регистрация неподтверждённого адреса присылает новый код (тест RegistrationTest, CA-05). Тексты `account.errors.email_registered` и `not_verified` удалены как неиспользуемые. Код, который персонал отправляет повторно из админки, привязывается к сессии регистрации (`session_hash` из `payload['binding']`), как у витрины, чтобы посторонний не мог перебирать его.
- **Отступление от ТЗ (CA-05):** ТЗ говорит, что регистрация на подтверждённый email «сообщает «email уже зарегистрирован»»; теперь ответ нейтральный («Мы отправили код…»), а о существующем аккаунте владельцу сообщает письмо. Это сознательное решение ради SEC-06 (перебор адресов через форму); владелец продукта должен его принять.
- **Последствия:** повтор регистрации того же адреса внутри паузы между кодами получает один и тот же отказ в обоих случаях. Владелец адреса получает не больше 5 писем «уже есть аккаунт» в час и 10 в сутки (общие лимиты кодов). Различие по времени ответа сведено к минимуму (хеш пароля вычисляется в обоих случаях), но не исключено полностью.

## D-198. Подтверждение телефона: дневной предел на IP и доля бюджета для гостей (SEC-01)
- **Контекст:** аудит SEC-01: один посторонний мог потратить весь `daily_limit` (по умолчанию 200) и при `on_daily_limit = block` остановить гостевое оформление до полуночи.
- **Решение:** (а) в `consumeLimits()` рядом с лимитом 10/час на IP добавлен суточный: `PER_IP_PER_DAY = 15` запусков за 24 часа на «ключ IP» (`ClientIpKey::of()`: IPv4 как есть, IPv6 — подсеть /64, IPv4-mapped — как IPv4). 15 — это 1,5 звонка в час на адрес: покупатель делает 1–3 запуска (повтор, смена номера), офис или оператор с общим адресом (CGNAT) редко подтверждает больше 15 разных номеров за сутки, а злоумышленнику с одного адреса остаётся 15 из 200 (7,5 % бюджета). (б) `dailyBudgetExhausted()`: гость (запуск без вошедшего покупателя) может занять не более `GUEST_SHARE_PERCENT = 80` % `daily_limit` (минимум 1 при ненулевом пределе), остальные 20 % доступны вошедшему покупателю и номеру с выполненным заказом. «Выполненный» — заказ с `OrderStatus::Completed` («Выполнен» / «Выкуплен») и тем же `customer_phone`; отменённые, просроченные, закрытые обращения (`Closed`), новые и промежуточные статусы (`Confirmed`, `Ready`, `Shipped`, `Reserved`, `InProgress`) не считаются: их можно создать, не потратив ничего. Кнопка «Отправить тест» (`Test`) расходует весь бюджет. Отказ гостю — тот же исход, что и при исчерпанном пределе (запись `blocked`/`skipped`, `note = daily_limit`, письмо владельцу, настройка `on_daily_limit`). Новой настройки нет: доля — константа. (в) Сессии с номером, подтверждённым через Telegram (TG-09, `PhoneVerificationGate::isTelegramVerified`), звонка и SMS не запрашивают: `start()` не вызывается, строка `phone_verifications` не пишется, счётчики не растут — проверено тестом.
- **Письмо владельцу (ревью PR #51):** при достижении только доли гостей (80 %) владелец получает не «дневной предел исчерпан» с полным `daily_limit`, а отдельное более лёгкое уведомление `guest_share` («доля гостей исчерпана: :cap из :limit», `ShopAlerts::guestShare()`), не чаще раза в сутки (полное — не чаще раза в час, как раньше). Исход для гостя прежний.
- **Последствия:** 80 % — общая планка суммарного расхода за день (учитываются и строки покупателей), поэтому гости не могут довести расход выше 80 %. Небольшой магазин с `daily_limit = 10` оставляет гостям 8. Покупатель за общим адресом с 15 другими запусками получает «слишком много запросов» до следующих суток.

## D-199. Подтверждение телефона: «сначала посчитать, потом решить» и какие счётчики тратит отказ (SEC-03)
- **Контекст:** `consumeLimits()` сначала проверял все лимиты, потом считал; параллельные запросы проходили проверку до того, как кто-то посчитался.
- **Решение:** каждый лимит — `RateLimiter::hit($key, $decay) > $max` (счёт возвращает значение, решение принимается по нему). Сам `RateLimiter::hit()` на `CACHE_STORE=file` не атомарен (это показали 12 параллельных процессов), поэтому все счётчики идут через `App\Support\AtomicRateLimiter`: изменение счётчика делается под `Cache::lock` этого счётчика (на файловом кэше — `flock`, исключительно между процессами PHP); не получив блокировку за 3 с, запрос считается превысившим лимит (`AtomicRateLimiter::REFUSED`, отказ по умолчанию). Проверено на файловом кэше: 12 параллельных процессов всегда получают 12 различных подряд идущих значений. Так же устроены пауза номера, лимит вводов на IP (раньше «проверить, потом посчитать») и счётчик неверных вводов. Лимиты применяются тремя воротами, отказ останавливается на своих: (1) лимиты запрашивающего — IP в час, IP в сутки, сессия; (2) пауза номера 60 с; (3) номер в час и в сутки. Отказ ворот не трогает следующие: посторонний, упёршийся в свой лимит, не сжигает счётчики чужого номера, а повтор внутри паузы не тратит часовую и суточную квоту номера. Счётчики пройденных ворот остаются потраченными — это и делает всплеск запросов неуспешным. Общий дневной бюджет магазина — не счётчик, а число принятых провайдером строк в БД (D-156): отказанный запуск строки с `provider_request_id` не создаёт и бюджет не тратит. Это меняет D-156 («отказанный запрос квоту не тратит»): теперь тратит счётчики запрашивающего и пройденные ворота.
- **Тесты:** `PhoneVerificationAbuseTest` («counts the start before judging it…»): счётчик IP после отказа равен 11 (при «проверить, потом посчитать» остался бы 10), счётчики номера равны 0, бюджет не тронут. Саму гонку модульный тест показать не может; ручная проверка — `race_sms.py` из отчёта аудита (одна принятая строка из восьми одновременных запросов); отказ при невзятой блокировке покрыт тестом «fails closed».

## D-200. Подтверждение телефона: блокировка неверных вводов на запрашивающего, ввод только по открытой попытке (SEC-04)
- **Контекст:** 15 неверных вводов за сутки блокировали номер на 24 часа для всех, и считались даже вводы без выданного кода: посторонний мог закрыть номер покупателя.
- **Решение:** (1) ввод засчитывается только как настоящая догадка по открытому коду своей сессии; ответы «нет активного кода», «код просрочен» и «попытки исчерпаны» счётчик не увеличивают (подобрать там нечего). (2) Код принимается только из сессии, запросившей его: запрос по `session_hash` и HMAC с токеном сессии (D-154) — это уже было, проверено тестом (верный код из другой сессии даёт «нет активного кода» и ничего не считает). (3) Счётчик и блокировка — на пару «номер + `ClientIpKey`»: посторонний блокирует только себя; владелец номера с другого адреса продолжает работать. Глобальная граница — отправки на номер: 6 кодов в сутки (`PER_NUMBER_PER_DAY`), по 5 попыток на код (`MAX_ATTEMPTS`). Худший шанс угадать код номера за сутки: 5 × 6 ÷ 10 000 = 0,30 % (< 1 %), при смене IP счётчик блокировки не помогает, а лимит попыток на код и 6 кодов в сутки — не зависят от IP. Поэтому отдельный суточный предел запущенных подтверждений на номер не добавлен. (4) **Ревью PR #51:** блокировка на запрашивающего подняла худший случай с 15 до 30 догадок в сутки на номер (6 кодов × 5 попыток), то есть вдвое выше границы PV-03 («не больше 15 неверных вводов в сутки на номер»). Граница восстановлена: общий счётчик `phone-verification:guesses:<номер>` — не больше `WRONG_ENTRIES_PER_DAY = 15` настоящих догадок за 24 часа по всем запрашивающим вместе. Догадка настоящая, только если ввод пришёл к открытому коду своей сессии (счёт идёт после проверок «нет кода» и «просрочен», до расхода попытки кода, атомарно); верный ввод и ввод в исчерпанный код отдают слот обратно. Шестнадцатый ввод по любому коду этого номера получает `number_locked` до конца окна (24 ч с первой догадки). Ввод без кода не считается. Повторное ревью PR #51: номер, исчерпавший 15 догадок окна, и запуск нового кода не получает: `send()` читает счётчик (`assertGuessBudgetLeft()`, до любых счётчиков и до вызова провайдера) и отказывает тем же `number_locked`, платного звонка или SMS нет.
- **Какой отказ остаётся:** посторонний, потратив 3 запуска кода (в пределах 6 в сутки на номер) и 15 догадок, лишает владельца возможности ввести код до конца окна. Это тот же порядок, что и уже действующий предел 6 запусков в сутки на номер (он тоже закрывает номер, владелец видит «слишком много запросов»), а не новая возможность; цена — верхняя граница PV-03 строго соблюдена (15 ÷ 10 000 = 0,15 %). Требование «не блокировать владельца» не выполнено до конца, это сознательный размен в пользу границы ТЗ.
- **Последствия:** распределённый подбор (много адресов) упирается в 15 догадок на номер в сутки; блокировка по запрашивающему защищает от долгого перебора с одного адреса. Чужую сессию это не меняет: чужой код всё равно нельзя подтвердить без его токена.

## D-202. Заголовки HSTS и Content-Security-Policy (NF-13, TM-12; аудит безопасности, усиление S3-2)
- **Контекст:** `SecurityHeaders` отправлял только X-Frame-Options, nosniff и Referrer-Policy; в режиме Telegram добавлялся CSP только с `frame-ancestors`.
- **Решение:** на каждый ответ уходит один заголовок `Content-Security-Policy: object-src 'none'; base-uri 'self'`; в режиме Telegram (`/tg*`, сессия Mini App) к нему спереди добавляется `frame-ancestors 'self' https://web.telegram.org` (одна строка со всеми директивами, второго заголовка нет, админка по-прежнему не встраивается). `Strict-Transport-Security: max-age=15552000` (180 дней, без `includeSubDomains` и `preload`) отправляется только для запроса по HTTPS в рабочем окружении (`isSecure()` учитывает `X-Forwarded-Proto` от прокси Beget). Строка «Адрес посетителя, который видит приложение» добавлена на страницу «Система» и в `shop:doctor` (в консоли показывает подсказку открыть страницу): по ней владелец проверяет, что пределы по адресам не общие (раздел 8.2 и 9.1 `DEPLOY_BEGET.md`).
- **Отвергнуто:** `script-src`: на витрине есть встроенные скрипты и редактируемый администратором код в `<head>`, политика потребовала бы nonce и сломала бы счётчики; `includeSubDomains` и `preload`: магазин не управляет остальными поддоменами домена, отказ от HTTPS на них стал бы необратимым.
- **Последствия:** обычные страницы получают `object-src 'none'` (плагины запрещены) и `base-uri 'self'` (подмена `<base>` внедрённой разметкой не работает). HSTS нельзя включить на домене без рабочего HTTPS.
- **Ревью PR #51 (PDF):** ответ с `Content-Type: application/pdf` (заказ в PDF, показывается встроенным просмотром, `OrderPdfController`) не получает `object-src` и остальные директивы: `object-src 'none'` может остановить встроенный просмотрщик PDF в Chromium, а защищать в PDF нечего (разметки нет). Остальные заголовки (nosniff, Referrer-Policy) остаются. Повторное ревью: в режиме Telegram, где X-Frame-Options снят, PDF получает CSP только с `frame-ancestors 'self' https://web.telegram.org`; вне режима Telegram остаётся `X-Frame-Options: SAMEORIGIN`.

## D-203. Закреплённый ключ SSH-сервера в деплое и запрет PHP в `public/storage` (аудит, S3-3, S3-5)
- **Контекст:** деплой при пустом `BEGET_KNOWN_HOSTS` запрашивал ключ хоста через `ssh-keyscan` на каждом запуске, то есть доверял любому серверу. Загрузки сайта лежат в `public/storage` и не должны выполняться как код ни при каких условиях.
- **Решение:** секрет `BEGET_KNOWN_HOSTS` обязателен: пустой секрет останавливает задачу с понятной ошибкой до любой работы с сервером; сообщение об ошибке SSH называет и несовпадение ключа хоста (имя хоста в строке должно совпадать с `BEGET_HOST`), `ssh-keyscan` удалён (`DEPLOY_BEGET.md`, раздел 5.1, описывает безопасное получение строки). В `public/.htaccess` добавлено правило `RewriteRule ^storage/.*\.(php\d*|pht|phps|phar|phtml)(/|$) - [F,L,NC]` (403; без учёта регистра, с PATH_INFO вида `x.php/a.jpg`, после ревью PR #51). Директивы `php_flag`/`php_admin_flag` не применяются: на PHP-FPM/CGI общего хостинга они дают ошибку 500.
- **Последствия:** владельцу нужно один раз записать строку known_hosts в секрет окружения (`production`, при втором сайте и его окружение); без этого выкладка не пойдёт. Правило `.htaccess` проверяется тестом по тексту файла (Apache в тестах недоступен).

## D-204. Локальные аватары админки (аудит, S3-4)
- **Контекст:** стандартный провайдер Filament на каждой странице админки запрашивал `ui-avatars.com/api/?name=…` с именем сотрудника (передача персональных данных третьей стороне).
- **Решение:** `App\Filament\Avatars\InitialsAvatarProvider` возвращает SVG в виде `data:`-адреса (base64) с одной-двумя заглавными буквами имени; цвет фона берётся из основного цвета темы админки, текст экранируется.
- **Последствия:** запросов к внешним сервисам для аватаров нет; загруженные фото сотрудников не используются (их и раньше не было).

## D-205. Предупреждение о правах, равных администратору (аудит, S3-6)
- **Контекст:** право `settings.seo.update` позволяет вставлять скрипты на каждую страницу витрины (код счётчиков выводится как есть), а сотрудники открывают витрину в том же источнике, что и админку, поэтому право равносильно администраторскому. Подсказки у `html_block.edit` не было.
- **Решение:** в редакторе ролей у раздела «SEO» (настройки) и у «Блок HTML главной» показывается предупреждение с этим пояснением (`roles.form.script_right_seo`, `script_right_html`). Сами права и их выдача не меняются.
- **Последствия:** только подсказка, ограничений в логике не добавлено.

## D-206. Персональные данные в ошибках базы и тестовое письмо (NF-15; аудит, S3-8, S3-9)
- **Контекст:** сообщение `QueryException` содержит подставленные значения, а текст драйвера может повторять значение («Duplicate entry '…' for key»); необработанная ошибка вставки заказа попала бы в журнал с именем, телефоном и e-mail. Кнопка «Отправить тестовое письмо» не проверяла право изменения страницы и показывала текст ошибки почтового драйвера (в нём бывают адреса).
- **Решение:** в `bootstrap/app.php` `QueryException` преобразуется (`$exceptions->map`, действует при отчёте, журнале и показе) в `App\Support\SanitizedQueryException`: SQLSTATE, код драйвера, SQL с `?` и безопасная часть текста драйвера: имена таблиц, столбцов, ключей и внешних ключей (MySQL `for key '…'`, «Unknown column», «Table … doesn't exist», «Data too long for column», внешний ключ; SQLite `UNIQUE constraint failed: table.column`, `no such table`) и ошибки соединения («Connection refused», «Access denied for user '…'@'…'» без пароля, «Unknown database»); значения в кавычках («Duplicate entry '…'», «Incorrect integer value: '…'») не копируются никогда, остальной текст драйвера отбрасывается, исходное исключение не цепляется (иначе его сообщение попало бы в журнал как «Next»); файл, строка и трассировка сохраняются. Преобразование действует только при `APP_DEBUG=false`: на машине разработчика (демо-данные) полное сообщение нужно для отладки, а включённый отладочный режим в рабочем окружении и так считается ошибкой `shop:doctor`. Кнопка теста письма видна и разрешена только при праве изменения страницы (`canEdit()`), метод повторно проверяет право, при ошибке показывается общий текст, в журнал пишется только класс исключения.
- **Таблица `failed_jobs` (ревью PR #51):** очередь записывает `(string) $exception` исходного исключения, то есть со значениями. Выбран самый малый надёжный путь: `queue.failer` расширен подклассом `App\Support\SanitizingFailedJobProvider` (`AppServiceProvider::register`), который при `APP_DEBUG=false` заменяет `QueryException` на `SanitizedQueryException` перед записью; трассировка остаётся. `QueryException`, завёрнутый в чужое исключение (повторный аудит, усиление 1): исключение, у которого в цепочке `previous` есть `QueryException` (например, `ViewException`, повторяющий текст запроса со значениями в своём сообщении), заменяется `SanitizedQueryException::sanitize()`: сообщение «класс внешнего исключения: безопасная причина запроса», файл, строка и трассировка внешнего, цепочка не сохраняется. Это делают второй `$exceptions->map(Throwable)` в `bootstrap/app.php` (HTTP-исключения с их кодом ответа не трогаются) и `SanitizingFailedJobProvider`; только при `APP_DEBUG=false`. Ревью PR #52: `CustomerThrottledException::report()` и `PhoneVerificationException::report()` теперь возвращают `true` (в Laravel `false` означает «отчитаться обычным способом», и каждый 429/422 покупателя писался в журнал со стеком); отображающий `map(Throwable)` в `bootstrap/app.php` обязан оставаться последним.
- **Последствия:** по журналу видно, какой запрос и какой индекс упали, но не значения; чтобы узнать запись, нужно действовать по времени и контексту запроса.

## D-207. Подтверждение привязки Telegram к аккаунту покупателя (TG-07; аудит, S3-7)
- **Контекст:** покупатель может отправить свою ссылку `c_…` другому человеку; если тот нажмёт «Подключить» (бот показывал только скрытый e-mail), его Telegram войдёт в аккаунт отправителя.
- **Решение:** сообщение бота показывает, кроме скрытого e-mail, имя владельца аккаунта (первое слово имени, не более 40 символов) и строку «Подключайте, только если вы сами нажали кнопку на сайте магазина.» Для покупателя без имени имя опускается. Протокол привязки не менялся.
- **Отвергнуто:** требование открыть ссылку из той же сессии браузера или код из письма: меняет протокол и усложняет сценарий «открыл ссылку в Telegram на телефоне».
- **Последствия:** это подсказка пользователю, а не техническая защита: человек, которому сознательно отправили ссылку, всё ещё может её подтвердить.

## D-208. Ограничения по IP: IPv6 считается по сети /64 во всех ограничителях маршрутов (аудит, ревью PR #51)
- **Контекст:** ограничители `telegram-webhook`, `tg-*` и числовые `throttle:N,M` ключевались полным адресом IPv6, один хост с сетью /64 обходил их сменой адреса.
- **Решение:** именованные ограничители ключуются `ClientIpKey::of($request->ip())`; псевдоним `throttle` в `bootstrap/app.php` указывает на `App\Http\Middleware\ThrottleByClientNetwork` (наследник `ThrottleRequests`, отличается только подписью запроса: маршрут (имя, а без имени — uri) и вошедший пользователь, а для остальных — домен, маршрут и `ClientIpKey`). Маршрут входит в подпись (повторный аудит, усиление 4): у числовых `throttle:N,M` в Laravel подпись без маршрута, и все такие маршруты клиента делили один счётчик (набор текста в поиске расходовал лимит добавления в корзину); теперь у каждого маршрута свой счётчик. Маршруты не менялись.
- **Последствия:** посетители одной сети /64 делят лимит маршрута, как и посетители IPv4 за одним адресом. Ревью PR #52: `retryAfter()` и `hit()` удалены (оставляли пару «проверить, потом посчитать»), тесты переведены на `attempt()`; в production приложение само включает `zend.exception_ignore_args` при запуске (`AppServiceProvider::hideExceptionArguments()`, параметр INI_ALL), так что строка в «Системе» показывает действующее значение и обычно «включено»; `shop:doctor` по SSH может читать другой php.ini, чем веб-сервер.

## D-209. Перебор промокодов по сети /64 и строка «zend.exception_ignore_args» в «Системе» (повторный аудит, RE-02, усиление 2)
- **Контекст:** `PromoAttemptGuard` ключевал IP полным адресом (хост IPv6 обходил 10 в минуту и 50 в час сменой адреса) и проверял лимит отдельно от подсчёта.
- **Решение:** ключ IP — `ClientIpKey::of($ip)`; новый метод `attempt()` сначала считает попытку атомарно (`AtomicRateLimiter::hit()`), затем сравнивает с 10 в минуту и 50 в час (на IP-сеть и на сессию) и проверяет паузу после 5 неудач; `HandlesPromoCode::applyPromo()` вызывает его вместо пары `retryAfter()` и `hit()`. Отклонённая попытка сохраняет свой счёт. Для проверки `shop:doctor` и страницы «Система» добавлена строка `zend.exception_ignore_args`: предупреждение, если в production параметр выключен (в журнал попали бы значения аргументов в трассировках, например телефоны, NF-15), с подсказкой попросить хостинг или задать `zend.exception_ignore_args = On` в php.ini или .user.ini.
- **Последствия:** посетители одной сети /64 делят лимит попыток промокода; на хостинге, где параметр нельзя изменить, строка остаётся предупреждением.

## D-210. Карточки галереи тем с миниатюрой и предпросмотр в окне поверх страницы (TH-22, TH-27…TH-29)
- **Контекст:** карточка темы показывала пять цветных квадратов и строку шрифтов; по цветам трудно понять, как выглядит витрина. «Предпросмотр» открывал новую вкладку, и о ней легко было забыть.
- **Решение (миниатюра):** верх карточки — схематичная витрина из HTML и CSS: шапка (название, поиск, корзина), баннер с кнопкой и ряд из четырёх карточек товаров. Всё рисуется переменными `--c-*` в `style` карточки; значения берёт `ThemeMiniature` из `ResolvedTheme` (`ThemeResolver`), поэтому цвета всегда `#rrggbb`, радиусы — целые числа (уменьшены втрое), название шрифта очищено до букв, цифр, пробела и дефиса. Для редактируемой темы берутся несохранённые цвета и шрифты формы, для остальных — `ThemeManager::overridesFor()`. Миниатюра — декоративная (`aria-hidden`); пять квадратов убраны. Сетка: 3 колонки, на планшете 2, на телефоне 1. Отклонено: живой `iframe` витрины в каждой карточке (51 запрос страницы и весь CSS витрины 51 раз) и сохранённые скриншоты (их нужно перегенерировать при каждом изменении тем и они не показывают несохранённые цвета).
- **Решение (шрифты):** `@font-face` пишутся один раз на странице и только для шрифтов, которые показывают карточки: заголовочный (его насыщенность) и текстовый (400), две подгруппы (кириллица, латиница) с `unicode-range` и `font-display: swap`, файлы `woff2` из `public/fonts`. Браузер скачивает начертание, только когда на нём выводится текст, а `content-visibility: auto` с `contain-intrinsic-size` у миниатюры не даёт загружать шрифты карточек вне экрана. Запасной вариант — системный шрифт.
- **Решение (предпросмотр):** «Предпросмотр» вызывает `previewTheme()`, она запускает `ThemePreview::start()` и отправляет событие `theme-preview-open`; окно (Alpine, `wire:ignore`, `x-trap` для фокуса, возврат фокуса на кнопку, закрытие по ✕, Esc и клику по фону) загружает в `iframe` `route('home')`. В заголовке окна: название, номер, ← / → (`previewStep()`, `ThemePreview::neighbour()`, перезагрузка `iframe`), «Компьютер / Телефон» (рамка 390 × 844, только от 1024 px, как в D-147), «Выбрать» (`applyPreview($id)` вызывает `selectTheme()`, завершает предпросмотр, закрывает окно) и ✕ (`closePreview()` завершает предпросмотр, чтобы собственные вкладки витрины сотрудника не остались в предпросмотре). Все методы проверяют право `settings.appearance.update`. Esc внутри `iframe` ловится в фазе перехвата: если на витрине открыт слой (`aria-modal="true"`, `x-overlay`, мобильное меню), Esc закрывает его, а не окно. Плашка витрины в новой вкладке (TH-27) не менялась; страница «Телефон» (TH-29) лишь снимает признак `embed` (см. «Последствия»).
- **Решение (плашка внутри окна):** `ThemePreview::start(..., embed: true)` кладёт в состояние сессии признак `embed`. `ThemeComposer` не показывает плашку, только если одновременно признак `embed` есть и браузер сообщает `Sec-Fetch-Dest: iframe`; вкладка того же сотрудника или браузер без заголовка получают плашку как раньше, предпросмотр вне окна (страница «Телефон») — тоже. Признак действует, только когда `ThemePreview::state()` признал сессию сотрудника (TH-30), у посетителей и в кэше главной ничего не меняется, ответы остаются `private, no-store`. Кнопки плашки при переключении темы сохраняют признак.
- **Последствия:** `X-Frame-Options: SAMEORIGIN` не менялся (окно и витрина — один origin). Если окно закрыто без `closePreview()` (вкладка закрыта), признак `embed` остаётся в сессии и влияет на любой вложенный документ витрины, поэтому `ThemePhonePreview::mount()` перезапускает такой предпросмотр без `embed`: рамка страницы «Телефон» всегда с плашкой. «Выбрать» в окне передаёт id показанной темы (`applyPreview($id)`) и включает её, только если он совпадает с предпросмотром в сессии, иначе показывает предупреждение. Признак `embed` один на сессию: если одновременно открыты окно предпросмотра и страница «Телефон» в разных вкладках, они перезапускают предпросмотр друг у друга и плашка в окне может появиться (косметика, отдельный признак на вкладку не заводился). Решение заменяет в TH-22 «пять образцов цвета» миниатюрой (формулировка ТЗ обновлена).
