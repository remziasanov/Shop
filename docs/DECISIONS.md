# Журнал решений

Формат: контекст → решение → отвергнутые варианты.

## D-001. Версии стека (Этап 0)
- **Контекст:** ТЗ раздел 3 — Laravel 13.x, Filament 5.x, Livewire 4; резервы Laravel 12 / Filament 4.
- **Решение:** Laravel 13, Filament 5, Livewire 4 (через Filament), Pest, Larastan 3 (уровень 5). Все поддерживают PHP 8.3. Резервные версии не понадобились.
- **Отвергнуто:** Laravel 12 / Filament 4 — нет причин.

## D-002. intervention/image версии 3
- **Контекст:** в Packagist доступна 4.x, ТЗ требует 3.x с драйвером GD.
- **Решение:** `intervention/image:^3`, драйвер GD.
- **Отвергнуто:** 4.x — расходится с ТЗ, нет выигрыша для задачи.

## D-003. Роли пользователей
- **Контекст:** ТЗ 6.13 — роль в `users.role`, права через политики, без пакетов ролей.
- **Решение:** enum `App\Enums\UserRole` (`admin`, `manager`), колонки `users.role` (varchar, default `manager`) и `users.is_active`. Доступ в панель — `User::canAccessPanel()` (активен + есть роль). Страницы настроек, пользователи и «Система» — только `admin` (`canAccess()` / политики).

## D-004. Путь админки
- **Решение:** `config('shop.admin_path')` из `ADMIN_PATH` (по умолчанию `admin`), передаётся в `->path()` панели Filament.

## D-005. Отметка планировщика (heartbeat, AD-11)
- **Контекст:** нужна отметка последнего запуска планировщика, без Redis.
- **Решение:** `shop:heartbeat` пишет время в файл `storage/app/heartbeat` (не зависит от драйвера кэша и очищения кэша при деплое `optimize:clear`). Чтение — через сервис `App\Services\System\Heartbeat`.
- **Отвергнуто:** кэш (сбрасывается при `optimize:clear`/`cache:clear`), отдельная таблица (лишняя миграция ради одного значения).

## D-006. Деньги
- **Решение:** в БД `decimal(12,2)`; в коде — целые копейки (`int`) через value-объект/хелпер `App\Support\Money`, форматирование `1 290 ₽`. Без float.

## D-007. Composer в песочнице
- **Контекст:** скачивание dist-архивов с GitHub через прокси песочницы возвращает 403.
- **Решение:** Composer автоматически переходит на git-клоны; установка медленнее, но работает. На CI (GitHub Actions) ограничения нет.

## D-008. Alpine.js на витрине
- **Контекст:** витрина использует Livewire 4 (корзина, формы), а Livewire поставляет Alpine.js в своём бандле.
- **Решение:** не ставить `alpinejs` отдельно из npm; на всех страницах витрины подключать скрипты Livewire (`@livewireScripts`), Alpine берётся оттуда. Так нет двойной инициализации, а JS витрины меньше (NF-03).
- **Отвергнуто:** отдельный пакет `alpinejs` в Vite — конфликт двух экземпляров Alpine.

## D-009. Деньги в настройках — целые копейки
- **Контекст:** настройки (spatie/laravel-settings) хранятся в JSON; float в JSON и в форме ведёт к ошибкам округления (D-006).
- **Решение:** все денежные значения в настройках — `int` в копейках (`min_order_amount`, `price` и `free_from` способов получения). В формах Filament сумма вводится в рублях (допустимы `1 290,50`, `1290.5`, `1 290 ₽`; правило `App\Rules\RublesAmount`); перевод рубли ↔ копейки — только через `App\Support\Money` (`fromRubles`, `toRubles`, `format`) в `mutateFormDataBeforeFill/Save` страницы. Разбор строки — через bcmath, дробные копейки округляются half-up.
- **Отвергнуто:** строки `"0.00"` в настройках (приходится парсить при каждом расчёте); float.

## D-010. Настройки: кэш, миграции, секреты
- **Решение:** кэш пакета включён (`SETTINGS_CACHE_ENABLED`, по умолчанию `true`, хранилище — `CACHE_STORE`, т.е. `file`); при сохранении кэш группы сбрасывается пакетом. Миграция таблицы `settings` лежит в `database/migrations`, значения по умолчанию — в `database/settings/*` (путь в `settings.migrations_paths`), так что `php artisan migrate` создаёт всё одной командой. Токен Telegram хранится зашифрованным (`NotificationSettings::encrypted()`), в миграции значение `null`, реальные значения не засеиваются. Для шифрования нужен `APP_KEY` — в `phpunit.xml` задан тестовый ключ.
- **Ограничение пакета:** `phpdocumentor/type-resolver` не разбирает array shapes (`array{...}`) и `mixed` в `@var` — у свойств-массивов с вложенными массивами (`delivery_methods`, `payment_methods`, `social_links`, `blocks`) `@var` не указывается, структура описана обычным комментарием.

## D-011. Админка: формат дат, пароль, навигация
- **Решение:** форматы Filament задаются глобально в `AppServiceProvider` (`Table`, `Schema`, `DateTimePicker`): `d.m.Y`, `d.m.Y H:i`, `H:i`, валюта `rub`. Минимальная длина пароля 10 (NF-12) — через `Password::defaults()`, действует и в форме пользователя, и при сбросе пароля Filament. Порядок групп меню (AD-03) задан в `AdminPanelProvider::navigationGroups()` строками из `lang/ru/shop.php`; страницы и ресурсы возвращают ту же строку из `getNavigationGroup()`. Название бренда берётся из `GeneralSettings::shop_name` (при недоступной таблице — `config('app.name')`).
- **Доступ:** `canAccessPanel()` = `is_active`; страницы настроек и `UserResource` — только администратор (трейт `AdminOnlySettingsPage`, `UserPolicy`); администратор не может удалить сам себя. Менеджер получает 403 и не видит пункты в меню.

## D-012. Сессия, логи, тесты Livewire
- **Решение:** `SESSION_LIFETIME` по умолчанию 480 минут (NF-12); лог по умолчанию `daily`, хранение 14 дней (NF-21); `APP_TIMEZONE` (по умолчанию `Europe/Moscow`), локаль `ru`, faker `ru_RU`. Livewire-компоненты в тестах вызываются через `Livewire\Livewire::test()` — пакет `pest-plugin-livewire` не добавлялся (правило «пакеты только из раздела 3»).
- **Формат денег на витрине:** `Money::format()` — разряды узким неразрывным пробелом (U+202F), перед `₽` обычный неразрывный пробел (U+00A0), копейки показываются только если не нули: `1 290 ₽`, `1 290,50 ₽`.

## D-013. Шрифты витрины
- **Контекст:** шаблон Laravel подключал шрифт Instrument Sans с fonts.bunny.net через Vite-плагин; сборка зависит от внешнего хоста, а витрина — от стороннего CDN (NF-03, приватность).
- **Решение:** системный стек шрифтов, без внешних шрифтов.
- **Отвергнуто:** самостоятельный хостинг веб-шрифта — лишний вес для NF-03; можно добавить позже.

## D-014. CI на MySQL
- **Решение:** в `ci.yml` отдельная задача с сервисом `mysql:8.0`; переменные `DB_*` заданы на уровне задачи и имеют приоритет над `<env>` из `phpunit.xml` (без `force="true"`). Тесты не требуют сборки Vite (`withoutVite()`).

## D-015. Итоговая цена до Этапа 2
- **Контекст:** витрина и админка Этапа 1 используют `products.final_price`, а калькулятор цен (PR-01) появится на Этапе 2.
- **Решение:** сервис `App\Services\Pricing\ProductPriceUpdater` уже сейчас пишет `final_price`/`display_old_price`/`price_calculated_at` при сохранении товара по упрощённому правилу: `final = fixed_price ?? base_price`, `old = compare_at_price`, если он больше `final`. На Этапе 2 внутренняя логика заменяется на `PriceCalculator`, точка вызова остаётся.

## D-016. SalesModeResolver на Этапе 1
- **Контекст:** карточке товара в списке (SF-15) и колонке «Режим» (AD-40) нужен действующий режим продаж, а продажи реализуются на Этапе 4.
- **Решение:** на Этапе 1 создаётся `App\Services\Sales\SalesModeResolver` с определением режима (цена по запросу → товар → ближайшая категория → магазин) и источника. Поправки на наличие и рабочие кнопки появятся на Этапе 4; пока кнопки ведут на карточку товара.

## D-017. Разделение AD-42
- **Решение:** массовое изменение базовой цены (±% / ±₽ с предпросмотром) реализуется на Этапе 2 вместе с историей цен (PR-06) и правом «только администратор». Экспорт выбранных товаров в Excel — на Этапе 3 вместе с экспортом каталога (EX-01). Остальные массовые действия — на Этапе 1.

## D-018. Редиректы при смене slug (SF-80)
- **Решение:** при смене slug товара/категории в `redirects` пишется `from_path` (старый путь) → `to_path` (новый). Существующие редиректы, ведущие на старый путь, переписываются на новый (без цепочек); редирект, у которого `from_path` совпал с новым путём, удаляется. Проверка выполняется только для 404 на витрине (обработчик исключений / fallback), поэтому обычные запросы не платят лишним SQL-запросом.

## D-019. Поиск (SF-20)
- **Решение:** `products.search_text` = нормализованные (нижний регистр, ё→е, одиночные пробелы) название + артикул + бренд. Запрос нормализуется так же, разбивается на слова, для каждого слова `search_text LIKE %слово%` (AND). Точное совпадение артикула поднимается первым через `ORDER BY CASE WHEN LOWER(sku) = ? THEN 0 ELSE 1 END`. Спецсимволы `%`/`_` экранируются. Без полнотекстовых индексов (переносимость SQLite/MySQL 5.7).

## D-020. Обработка фото (AD-50…53)
- **Решение:** `App\Services\Media\ImageProcessor` (intervention/image 3, GD): ориентация по EXIF, варианты 1600/800/400 px по длинной стороне (без увеличения), WebP 80, если `imagetypes() & IMG_WEBP`, иначе JPEG 85. Пути `products/{product_id}/{uuid}-{size}.webp|jpg` на диске `public`. Исходник после обработки удаляется. В админке файлы загружаются во временный каталог Livewire и обрабатываются при сохранении товара; ошибка одного файла не мешает остальным (уведомление с именем файла).

## D-021. Подсчёт товаров в дереве категорий (AD-30)
- **Решение:** одним запросом получаем число товаров по `category_id`, затем суммируем по материализованным путям в PHP (без N+1 и без CTE). Дерево категорий кэшируется (NF-04) и сбрасывается при изменении категорий.

## D-022. Ассеты Filament
- **Решение:** `php artisan filament:upgrade` выполняется в `post-autoload-dump` Composer; опубликованные ассеты (`public/css|js|fonts/filament`) не хранятся в git и создаются при `composer install` — локально и в CI-сборке релиза перед загрузкой на Beget (на сервере Composer не нужен).

## D-023. Фильтр «Режим» в таблице товаров (AD-41)
- **Решение:** фильтр «Режим» использует собственную настройку режима продаж товара (`inherit` = `null`), а не действующий режим: действующий режим зависит от дерева категорий и настроек магазина и не хранится в таблице. Колонка «Режим» при этом показывает действующий режим (с источником).

## D-024. Арифметика PriceCalculator (PR-01)
- **Решение:** все суммы — целые копейки (`int`). Процент: `round_half_up(price * value / 100)` через bcmath (value — `decimal(12,4)` строкой), результат каждого шага сразу округляется до копейки. Фиксированные наценки/скидки — в копейках. Цена после фазы скидок не ниже 0.
- Округление: шаг в рублях (1/10/50/100), направление вверх/к ближайшему (половина — вверх)/вниз; «психологическая» −1 ₽ только при шаге ≥ 10 и если результат > 0. Округление применяется, если сработало хотя бы одно правило или в настройках выбрано «ко всем»; без правил при «только изменённые» цена не округляется.
- `cost_markup_percent` у товара без закупочной цены пропускается (в объяснении — шаг «пропущено: нет закупочной цены»).

## D-025. Старая цена и настройки показа
- **Решение:** `display_old_price` всегда считается по алгоритму 6.8 (и используется фильтром «Со скидкой» и меткой «Скидка»). Настройки «показывать старую цену / % скидки» влияют только на вывод на витрине.

## D-026. Загрузка правил и кэш
- **Решение:** `PriceRuleRepository` один раз загружает все активные правила с целями (2 запроса) и держит их в памяти процесса и в кэше (`pricing.rules`, сбрасывается при изменении правил); отбор по периоду — по переданному времени внутри калькулятора. Совпадение по категориям — через `CategoryTree::descendantIds` (флаг «включая подкатегории»).

## D-027. Пересчёт при изменении правил и прогресс (PR-02, PR-05)
- **Решение:** при сохранении/удалении/включении правила вычисляется множество затронутых товаров = товары, подходящие под область правила до изменения ∪ после изменения (для области «все» — все товары). Id ставятся в очередь задачами `RecalculatePrices` по 500 штук. Прогресс хранится в кэше (`pricing.recalc`: total/done), баннер в админке читает его; по завершении ключ удаляется.
- `--boundaries`: правила, у которых `starts_at` или `ends_at` попали в интервал (последний запуск, сейчас], последний запуск хранится в кэше (по умолчанию окно 16 минут).

## D-028. История цен (PR-06)
- **Решение:** `PriceHistoryRecorder` пишет изменения `base_price`, `cost_price`, `fixed_price`, `compare_at_price` из наблюдателя товара. Источник и `import_id` задаются контекстом (`PriceChangeContext`, по умолчанию «вручную» + текущий пользователь); массовое действие и импорт оборачивают изменения в свой контекст. Изменения `final_price` от правил не пишутся.

## D-029. PR-07 на Этапе 2
- **Решение:** на Этапе 2 гарантируется, что `final_price` — единственный источник итоговой цены (витрина, админка). Фиксация цены в корзине и сравнение при оформлении реализуются вместе с корзиной на Этапе 4.

## D-030. Пересчёт цен при «сырых» изменениях входных данных (PR-02)
- **Решение:** всё, что пишет `category_id`, `is_featured`, `is_new` или `path` категорий мимо наблюдателя товара, ставит пересчёт затронутых товаров в очередь через `PriceRuleRecalculator::dispatch()` (задачи по 500): массовые «Перенести в категорию» и «Задать/снять метки»; перенос ветки категорий (`CategoryObserver::saved` — товары категории и всех её потомков); удаление категории с переносом товаров (`CategoryTree::deleteMovingToParent`). Всегда без проверки, есть ли правила по категориям (простота важнее оптимизации). Настройки «Цены»: при смене округления/психологической цены ставится пересчёт всех товаров (`PriceRuleRecalculator::dispatchAll()`, тот же код, что у `shop:recalc-prices --all`); переключатели показа старой цены/% скидки пересчёта не требуют. Восстановление товара из корзины пересчитывает цену в наблюдателе (`needsUpdate`).
- Черновик нового правила в предпросмотре получает id `PHP_INT_MAX` (новое правило получит наибольший id и применится последним при равном приоритете); у редактируемого правила — настоящий id.
- Прогресс (`RecalculationProgress`) — необязательные данные: при `LockTimeoutException` пишем предупреждение в лог и пропускаем обновление. Отметка последнего запуска `--boundaries` хранится в файле `storage/app/pricing-boundaries-last-run` (переживает `optimize:clear` при деплое).

## D-031. Границы значений и диапазон дат (PR-01)
- **Решение:** наценка в процентах (`markup_percent`, `cost_markup_percent`) ≤ 1000 %; фиксированные суммы правила ≤ 99 999 999,99 ₽ — предел колонки `price_rules.value decimal(12,4)` (8 цифр в целой части; значение 9 999 999 999,99 в неё не помещается). `PriceCalculator` после каждого шага и после округления ограничивает цену максимумом `decimal(12,2)` (999 999 999 999 коп.).
- Колонки `price_rules.starts_at/ends_at`, `products.price_calculated_at`, `price_history.created_at` — `dateTime` вместо `timestamp` (у MySQL `timestamp` кончается в 2038 году). Миграции этапа 2 ещё не выпущены, поэтому правятся на месте.

## D-032. Массовое изменение цены — в очереди (AD-42)
- **Решение:** действие не меняет цены в HTTP-запросе. `BulkPriceChanger::computeTargets()` считает для выбранных товаров (пачками по 100) `id => [old, new]` в копейках; `dispatch()` режет их на задачи `ApplyBulkPriceChange` по ≤ 200 товаров (≈ 4 мс на товар — укладывается в 40 с). Задача получает автора действия явно (в очереди нет сессии) и выполняет `applyTargets()` в контексте «bulk»: под `lockForUpdate` обновляет только товар, у которого `base_price` по-прежнему равен ожидаемому «старому», остальные пропускает и считает — повтор или ретрай не применит изменение дважды. Источник истории — `bulk`, пользователь — автор.
- Жёсткий лимит выделения — 20 000 товаров (`config('shop.bulk_price_max_selection')`), больше — отказ с сообщением. Пользователь получает уведомление «Изменение цен поставлено в очередь: N товаров». Серверная проверка `changePrices` (`abort_unless`) сохраняется и покрыта тестом на прямой вызов Livewire от менеджера.

## D-033. Конвейер импорта (IM-01…IM-15)
- **Контекст:** Beget — только cron + database-очередь, задача ≤ 40 с, память ≤ 128 МБ; повторное чтение .xlsx для каждой пачки дорого.
- **Решение:**
  1. Загрузка: исходный файл (и ZIP) на приватный диск `local` в `imports/{id}/`; запись `imports` со статусом `uploaded`.
  2. Сопоставление колонок: `ColumnMapper` по заголовкам (без регистра/пробелов/знаков, синонимы приложения A, `Х:`/`Характеристика:` → характеристики); последнее сопоставление берётся из предыдущего импорта по совпадающим заголовкам.
  3. Анализ (задача `AnalyzeImport`): один потоковый проход по файлу — строки нормализуются и пишутся в промежуточный файл `imports/{id}/rows.jsonl`, параллельно считаются сводка «создано/обновлено/пропущено/ошибки» (без записи в каталог) и первые 20 строк для предпросмотра. Лист «Категории» — в отдельный `categories.jsonl`.
  4. Обработка: пачка = 200 строк промежуточного файла (смещение в байтах хранится в `imports`), каждая пачка — своя транзакция. Захват пачки атомарный (`UPDATE imports SET next_chunk = n+1 WHERE id = ? AND next_chunk = n`), поэтому очередь и резервный режим из браузера (IM-10) не обрабатывают одну пачку дважды. Повтор безопасен: идемпотентность по артикулу.
  5. Фото обрабатываются после коммита данных пачки, вне транзакции, с бюджетом времени; если бюджет исчерпан, оставшиеся фото уходят в следующую задачу.
  6. Завершение: полная синхронизация (деактивация отсутствующих), пересчёт цен затронутых товаров, сброс кэшей, событие `ImportFinished` (на него подпишется генерация sitemap на Этапе 5), уведомление в колокольчик Filament.
- **Отвергнуто:** перечитывание исходного файла для каждой пачки (O(n²) по времени для .xlsx); таблица строк в БД (лишний объём в MySQL на shared-хостинге).

## D-034. CSV: кодировка и разделитель (IM-01)

## D-035. Загрузка фото по URL (IM-11)

Таймаут 15 с, ≤ 10 МБ (обрыв по превышению), `Content-Type: image/*` и проверка содержимого, одна повторная попытка. Кэш «URL → файл» в рамках импорта. Ошибка фото — предупреждение в отчёте.

## D-039. Фоновый экспорт каталога одним проходом (EX-03)

- **Решение:** `ExportCatalog` пишет файл целиком в одной задаче (timeout 40, без повторов). Если на Beget время приблизится к лимиту — разбить на части с дозаписью (техдолг при необходимости).

## D-040. Фото на собственном хранилище и счётчик «без изменений» (EX-01, IM-06, IM-12)
- **Контекст:** экспорт пишет в ячейку «Фото» полные URL собственного хранилища (`{APP_URL}/storage/products/{id}/{file}`); повторный импорт скачивал их по HTTP, удалял старые снимки и создавал новые (другие uuid, на каждом цикле), а фото категорий пересоздавались при каждом импорте. Строка без реальных изменений считалась «обновлённой».
- **Решение:**
  1. `OwnMediaLocator` узнаёт «свою» ссылку: относительный путь под URL публичного диска (`/storage/…`) или абсолютный URL с хостом из `APP_URL` / URL диска `public`. Для товара ищется `ProductImage` по `path_large|medium|small` (с ограничением по `product_id` из пути).
  2. Снимок того же товара считается уже имеющимся: не скачивается, не удаляется в режиме «заменить» (входит в «новый набор»), порядок строки применяется как обычно. Снимок другого товара копируется с локального файла через `ImageProcessor` (без HTTP; `source_hash = sha1('own:'.path_large)`, поэтому повтор не создаёт копий). Ссылка на ещё не существующий файл — обычная ссылка (скачивание/ошибка).
  3. Категория: ячейка равна URL текущего `image_path` — картинка не трогается; чужой собственный файл копируется локально.
  4. «Обновлено» считается только если изменился товар (`isDirty()` до сохранения) или его фото (добавлены/удалены/переставлены). Остальные строки — новый счётчик `imports.unchanged_count` (также `analysis.result.unchanged`, отчёт «Без изменений», уведомление). Строки с фото классифицирует шаг фото (задача несёт флаг `unchanged`), поэтому повторный импорт демо-файла даёт `updated = 0`, `unchanged = 50`, а `updated_at` товаров не меняется.

## D-041. Фото последней пачки не теряются при конкурентном завершении (IM-09, IM-10)
- **Контекст:** задачи фото жили в памяти после снятия блокировки; второй исполнитель (очередь + резервный режим браузера) видел «нет файлов фото» и завершал импорт, удаляя `downloads/` и `media/`.
- **Решение:**
  1. Задачи фото пачки записываются в `imports/{id}/photos-working-{label}.json` ещё под блокировкой `run`, до её снятия; после работы файл удаляется, при исчерпании бюджета переименовывается в `photos-pending-{label}.json`, при исключении возвращается в pending.
  2. `finish()` берёт блокировку `run` (пока исполнитель между захватом пачки и записью файла — не завершаем) и требует отсутствия и pending-, и working-файлов.
  3. После каждого скачивания/снимка исполнитель делает `touch` файла и обновляет `last_activity_at` (кнопка резервного режима не появляется, пока фото идут). Working-файл без обновлений дольше `STALE_CLAIM_SECONDS` (120 с — как у захваченной пачки) считается брошенным и возвращается в pending. Обработка идемпотентна по `source_hash`, скачивания кэшируются на время импорта.

## D-042. Жёсткий дедлайн запроса и задачи (IM-10, раздел 2)
- **Решение:** бюджет передаётся вниз как дедлайн (`microtime(true)`): браузерный запрос — `ImportRunner::BROWSER_BUDGET` = 18 с (ТЗ: ≤ 20 с), задача очереди — `ProcessesImportSteps::BUDGET` = 30 с (лимит задачи 40 с).
  - `ImageFetcher::fetch(..., $deadline)`: загрузка не начинается, если до дедлайна меньше `MIN_WINDOW` = 4 с (бросает `ImageFetchDeadlineException` — это не ошибка фото: ничего не кэшируется и не пишется в отчёт); таймаут запроса = `min(15, остаток − 2)`.
  - `ImportPhotoProcessor` проверяет дедлайн перед каждой загрузкой и перед каждым прикреплением снимка; недоделанная задача возвращается в pending с отметками (`warned` — какие ссылки уже дали предупреждение, `photos_changed`), продолжение не создаёт дублей.
  - Шаг данных пачки (200 строк) дедлайном не прерывается — он быстрый: замер на 10 000 строк (50 пачек, SQLite) — ≈ 0,6 с на пачку вместе с созданием категорий; MySQL — ≈ 0,7 с. Запрос браузера = шаг данных (≤ ~1 с) + фото до 18 с + хвост одного снимка в GD (≈ 1 с).
- Прокси из окружения (`HTTP_PROXY`/`HTTPS_PROXY`) для загрузки фото отключены явно (`proxy => ''`, `CURLOPT_PROXY => ''`): иначе закрепление IP (`CURLOPT_RESOLVE`, D-035) не действует.

## D-043. Анализ и резервный режим: блокировка и повторы
- **Анализ:** `ImportAnalyzer::analyze()` выполняется под `Cache::lock("import:{id}:analyze")` (120 с) и проверкой статуса под ней (`uploaded|analyzing` → `analyzing`; условный `UPDATE` не годится — MySQL возвращает число изменённых, а не найденных строк); проигравший (задача очереди и «Проверить сейчас» одновременно, либо повторный вызов для уже проанализированного импорта) ничего не делает и не переписывает `rows.jsonl`.
- **Резервный режим браузера:** исключение шага не останавливает импорт сразу (очередь даёт 3 попытки): пачка откатывается и освобождается, клиенту уходит `503 {retry: true, more: true}`, JS повторяет запрос с паузой 2 с → 4 с → 8 с. Счётчик ошибок подряд — в кэше (`import:{id}:browser_failures`), сбрасывается успешным шагом; на 3-й ошибке подряд импорт получает статус «ошибка».

## D-044. Лимит временной загрузки Livewire 50 МБ — глобальный
- **Контекст:** файл импорта (IM-01) может быть до 50 МБ, а Livewire применяет правило `temporary_file_upload.rules` ко всем компонентам; настроить его для одного компонента нельзя (оно проверяется на общем маршруте `livewire/upload-file` до создания компонента).
- **Решение:** оставляем `max:51200` в `config/livewire.php` глобально. Реальные ограничения задаёт каждое поле загрузки: фото товара и категории — `PhotoUpload::effectiveMaxBytes()` (≤ 10 МБ), логотип/OG/заглушка — 2 МБ, favicon — 512 КБ, файл импорта и ZIP — `ImportWizard::maxUploadBytes()`; тест `tests/Unit/UploadLimitsTest.php` проверяет, что у каждого `FileUpload` в `app/Filament` есть `maxSize`. Практический предел зависит от `upload_max_filesize`/`post_max_size` хостинга (`shop:doctor`).

## D-045. Номера обращений

## D-046. Остатки и «под заказ» (StockService, приложение B)
- **Решение:** все изменения `stock_qty`/`reserved_qty` — только через `StockService` в транзакции с `lockForUpdate()` строк товаров (в порядке id, чтобы исключить взаимоблокировки). Учёт выполняется, если включён в настройках и у товара `stock_qty IS NOT NULL`.
- Фактически списанное/зарезервированное количество хранится в технических полях позиции `order_items.stock_applied_qty` (и флаг `orders.stock_applied`), возврат при отмене/истечении — ровно на это количество (идемпотентно).
- Без «под заказ» остаток не может уйти в минус: при нехватке обращение не создаётся. С «под заказ» списывается только доступное количество (остаток не уходит ниже 0), недостающее — «под заказ».
- Импорт пишет остатки через `StockService::setStock()` (абсолютное значение под блокировкой).

## D-050. Детали ядра продаж (Этап 4)
- Ключи способов получения/оплаты — `Str::slug(name)` с суффиксами `-2`, `-3` для дублей, вычисляются по всем строкам (деактивация не сдвигает ключи); в обращении хранится название способа (снимок).
- При разрешённом «под заказ» количество в корзине не ограничивается остатком (`maxQty = null`); резерв всегда ограничен доступным остатком (`maxReserveQty`).
- Возврат/снятие/выкуп резерва ориентируются на `orders.stock_applied` (а не на текущий переключатель учёта), чтобы корректно закрывать обращения, созданные при включённом учёте. Списание и удержание при выключенном учёте не выполняются. `setStock` пишет всегда (данные каталога).
- При оформлении недоступные позиции удаляются из корзины, количество сверх остатка уменьшается, изменённые цены обновляются; изменения фиксируются, затем покупатель получает `CartChangedException` со списком причин.
- Счётчик корзины в шапке — сумма количеств. Статус `expired` устанавливается только системой (`expireReservations`).

## D-051. Остатки при удалении обращения (OR-07)
- **Контекст:** мягко удалённый активный резерв/заказ выпадал из `shop:expire-reservations` (глобальный scope SoftDeletes), и `reserved_qty` / списанный `stock_qty` оставались занятыми навсегда.
- **Решение:** удаление идёт через `OrderService::delete(Order, ?User)`: в одной транзакции под блокировкой обращения — если `stock_applied` и статус не финальный (`completed`/`cancelled`/`expired`/`closed`), резерв снимается (`releaseReservation`), заказ возвращается на склад (`returnForOrder`) через `StockService::settleForDeletion()`; пишется строка истории «Удалено администратором»; затем мягкое удаление. Выполненный заказ и закрытые обращения остаток не меняют; повторное удаление ничего не делает. Действие «Удалить» на странице обращения и массовое удаление в списке используют сервис. Страховка: событие `deleting` модели `Order` вызывает `settleForDeletion()` (идемпотентно), поэтому прямой `$order->delete()` тоже не оставляет остаток занятым.

## D-052. Поле «Остаток» в карточке товара
- **Контекст:** форма отправляла значение `stock_qty`, загруженное при открытии страницы, и затирала списания заказов (lost update) в обход `StockService`.
- **Решение:** поле `stock_qty` — `dehydrated(false)`, в модель напрямую не пишется. Страницы `EditProduct`/`CreateProduct` запоминают значение при заполнении формы (`#[Locked] $loadedStockQty`) и после сохранения (`afterSave`/`afterCreate`) вызывают `StockService::setStock()` только если пользователь изменил поле относительно загруженного значения (очистка поля = перестать учитывать). Если поле не менялось, оно перечитывается из БД. «Зарезервировано» и «Доступно» — только для чтения, как раньше.

## D-053. Номера обращений: строки счётчиков и повтор при взаимоблокировке; лимиты количества
- **Контекст:** `INSERT IGNORE` по существующей строке `order_sequences` берёт S-блокировку, и две параллельные транзакции взаимно ждали X-блокировку (MySQL 1213).
- **Решение:** миграция `seed_order_sequences` создаёт строки `order`/`reservation`/`inquiry` (`insertOrIgnore` в `up()`, удаление в `down()`); `OrderNumberGenerator::next()` делает только `SELECT … FOR UPDATE` и `UPDATE`. Если строки нет (миграция не выполнялась): вне внешней транзакции она создаётся, внутри — исключение с понятным текстом (создание внутри чужой транзакции вернуло бы взаимоблокировку). Транзакции `createFromCart`/`createReservation`/`createInquiry` выполняются с 3 попытками (`DB::transaction($cb, 3)`): внутри только операции с БД, события — `afterCommit` (откатанная попытка их отбрасывает), `CartChangedException` бросается после коммита, поэтому повтор безопасен. Порядок блокировок: корзина → товары по id → `order_sequences` → строки заказа.
- `createFromCart` первым запросом блокирует строку корзины: второе параллельное оформление той же корзины ждёт и видит пустую корзину («Корзина пуста»), второй заказ не создаётся.
- Количество одной позиции ограничено `App\Support\QtyLimit::MAX = 999` везде: `CartService::add/update` (обрезка), `AddToCart`/`CartPage` (сообщение/обрезка), правила `ReservationForm`/`InquiryForm`, `OrderService::createReservation/createInquiry` (исключение). Переполнение `qty` и сумм невозможно, поэтому `QueryException` с привязками (имя, телефон, email) не возникает; наш код персональные данные не логирует.
- `$productId` в `AddToCart`, `ReservationForm`, `InquiryForm` — `#[Locked]`. `ReservationForm::product()` запоминает товар на время запроса.
- Все записи расписания (`shop:heartbeat`, `shop:recalc-prices`, `shop:expire-reservations`) — `withoutOverlapping(10)`: mutex истекает через 10 минут, а не через 24 часа, если процесс cron на хостинге был убит.
- Восстановление удалённых обращений не поддерживается (политика запрещает `restore`): при удалении остатки уже возвращены (дополнение к D-051).

## D-054. Главная страница (5.2, AD-20)
- **Решение:** блоки хранятся в `HomePageSettings::blocks` (JSON, формат Filament Builder: `type` + `data`, в `data` флаг `visible`). Рендер — `HomePageRenderer`, результат HTML кэшируется на 10 минут (`home.html`), кэш сбрасывается при сохранении конструктора, товаров, категорий, настроек оформления/общих. Блок «HTML» доступен только администратору (поле скрыто и отбрасывается при сохранении менеджером); его содержимое выводится без санитайзера (NF-10), остальной форматированный текст — через `HtmlSanitizer`.
- **Кэш и CSRF (дополнение):** в карточках товара на главной — обычные POST-формы с `@csrf`; токен привязан к сессии, поэтому в кэшируемом HTML он заменяется плейсхолдером, а в `HomePageRenderer::render()` подставляется токен текущей сессии (HTML кэшируется целиком, запросы к БД на тёплом кэше — только настройки). Кэш сбрасывается слушателями `HomePageServiceProvider`: `SettingsSaved` (любые настройки), `saved`/`deleted` у `Product`, `Category`, `ProductImage`, `restored`/`forceDeleted` у `Product`, `ImportFinished`. Массовые SQL-обновления мимо моделей (пересчёт цен, остатки) подхватываются по TTL 10 минут.
- **Изображения баннеров:** загрузка во временный приватный каталог `tmp/home-images`, при сохранении `ImageProcessor::processBannerImage` создаёт варианты 1600 и 800 px (WebP) в `public/home/`, в блоке хранится `{large, small, width, height}`; исходник не сохраняется, SVG и файлы > 10 МБ отклоняются. Заменённые, удалённые и осиротевшие (блок удалён) файлы удаляются после сохранения; ссылка на существующую картинку принимается, только если она уже есть в сохранённых настройках (подмена пути из браузера не даёт удалить чужие файлы).
- **Менеджер и блок HTML (6.13):** блоки `html` вырезаются из данных формы менеджера (исходный код не попадает в браузер) и при сохранении возвращаются на прежние позиции; отправленные менеджером блоки `html` отбрасываются.

## D-056. Sitemap и robots (SF-82)
- **Решение:** `shop:sitemap` пишет `public/sitemap.xml` (атомарно: временный файл + rename; при > 50 000 URL — индекс и части), ежедневно в 04:20 и после импорта (слушатель `ImportFinished` ставит задачу в очередь). Маршрут `/sitemap.xml` отдаёт файл, а если его нет — генерирует на лету. `/robots.txt` — маршрут из `SeoSettings` со строкой `Sitemap:`; статический `public/robots.txt` удаляется.
- **Блокировка (ревью PR #6):** `SitemapGenerator::generateLocked()` берёт `Cache::lock('sitemap:generate', shop.sitemap_lock_seconds)` (300 с) и дополнительно `flock` на `storage/framework/sitemap.lock` (переживает `cache:clear`, снимается ядром вместе с процессом); команда и задача `GenerateSitemap` при занятой блокировке пропускаются, а `/sitemap.xml` без файла отдаёт 503 + `Retry-After: 60` вместо параллельной генерации. Даже если обе блокировки пропали, параллельные запуски безвредны: каждый пишет в свой временный файл (`tempnam`, уникальное имя) и публикует его атомарным `rename()`, поэтому `sitemap.xml` всегда целый корректный файл (в худшем случае индекс на миг расходится с частями; следующий запуск это исправит). Задача `GenerateSitemap`: 5 попыток, `backoff` 60/120/300/600 с после исключения; занятая блокировка освобождает задачу с собственной задержкой 120 с.
- **robots.txt в закрытом режиме:** правила остаются обычными (без `Disallow: /`). Страницы витрины отвечают 503 + `Retry-After`, это поисковики считают временным; `Disallow: /` при долгом закрытии мог бы выбить страницы из выдачи.

## D-057. Хост и закрытый режим (ревью PR #6)
- **Контекст:** кэш главной хранил абсолютные URL с хостом и схемой первого запроса (отравление кэша, `www.`-алиас Beget, http/https); закрытый режим не действовал на действия Livewire-компонентов витрины, так как `livewire*` исключён из `StorefrontOpen`.
- **Решение (хост):** два слоя. (а) В production `AppServiceProvider::forceCanonicalUrl()` вызывает `URL::forceRootUrl(APP_URL)` и `URL::forceScheme('https')` при https в `APP_URL`; в `bootstrap/app.php` включён `TrustHosts` с хостом из `APP_URL` и его `www.`-вариантом (`subdomains: false`, список вычисляется на запрос, поэтому работает и с кэшем конфигурации; в local и тестах middleware не действует). Каноникал, OG и sitemap по-прежнему строятся от `APP_URL`. (б) Кэшируемый фрагмент главной не зависит от хоста: ссылки на товары (`ProductPresenter::present(..., absolute: false)`), «Смотреть все», плитки категорий и `action` формы «В корзину» — относительные (`route(..., absolute: false)`).
- **Решение (закрытый режим):** трейт `App\Livewire\Storefront\Concerns\RequiresOpenShop` (хук `bootRequiresOpenShop`) во всех компонентах витрины (`AddToCart`, `CartPage`, `CheckoutForm`, `ReservationForm`, `InquiryForm`, `MiniCart`) отвечает 503, если магазин закрыт, а пользователь не активный сотрудник; проверка на монтировании и на каждом следующем запросе. Обычный `POST /cart/add` закрыт middleware.
- **Решение (www., раунд 2):** `www.`-вариант (или голый домен, если `APP_URL` с `www.`) не обслуживается: global middleware `CanonicalHost` в production отвечает 301 (GET/HEAD) или 308 (прочие методы) на тот же путь и query на схему и хост `APP_URL`; иначе ассеты, Livewire и подписанные URL указывали бы на другой origin. Отключается `shop.canonical_host_redirect`. Остальные хосты отсекает `TrustHosts` (400).
- **Решение (SHOP_EXTRA_HOSTS, техдолг):** хосты из `SHOP_EXTRA_HOSTS` тоже перенаправляются `CanonicalHost` на хост `APP_URL` (так же, как `www.`-двойник: 301/308, в production), иначе страница технического домена тянула бы ассеты и Livewire с другого origin и JS ломался. Порядок работы: пока свой домен не привязан, в `APP_URL` стоит технический домен; после привязки `APP_URL` меняется на настоящий домен, а технический остаётся в `SHOP_EXTRA_HOSTS` (он принимается и перенаправляется).
- **Технический домен Beget:** `*.beget.tech` не входит в доверенные и отвечает 400, пока он не добавлен в `APP_URL` или в необязательную переменную `SHOP_EXTRA_HOSTS` (через запятую, `config('shop.extra_hosts')`). Список шаблонов строит `App\Support\TrustedHosts`.
- **Закрытый режим в Livewire:** `RequiresOpenShop` бросает `HttpResponseException` с тем же ответом 503 (view `errors.shop-closed` с текстом из настроек), что и `StorefrontOpen::closedResponse()`.
- **Отвергнуто:** разбор snapshot в middleware (хрупко); исключение `livewire*` нельзя убрать целиком — им пользуется вход в админку.

## D-058. Страницы согласия и политики включены по умолчанию (SF-71)
- **Решение:** миграция-сидер создаёт страницы политики и согласия активными (чекбоксу согласия нужна ссылка на документ, неактивная страница даёт 404), остальные три страницы остаются черновиками. Отметка «Шаблон — проверить у юриста» остаётся вверху текста. **Перед запуском владелец обязан заменить текст на согласованный юристом и удалить отметку.** Миграция ещё не выпускалась, поэтому изменена на месте.
- **Отвергнуто:** оставить черновики (нет ссылки у согласия); показывать текст согласия во всплывающем блоке (дублирование источника).

## D-059. Уведомления (раздел 9, NT-01…NT-04)
- **Решение:** слушатели `OrderCreated`/`OrderStatusChanged` (в `NotificationServiceProvider`) только ставят в очередь задачу `SendOrderNotifications` (3 попытки, backoff) — создание обращения никогда не зависит от почты/Telegram (NT-01). Письма — Markdown-шаблоны Laravel (`resources/views/mail/*`) с логотипом и названием магазина; SMTP — только в `.env` (NT-03). Telegram — Bot API `sendMessage`, `parse_mode=HTML`, все подставляемые значения через `htmlspecialchars` (NT-02); токен хранится зашифрованным в настройках (D-010).
- Повторная отправка при ретрае не дублирует каналы: задача отправки — отдельная на каждый канал/получателя.
- Уведомление «резерв истекает в течение 6 ч» отправляется один раз (`orders.expiring_notified_at`).
- В логи не пишутся телефоны и email целиком (NF-15): маскирование `+7******4567`, `i***@example.ru`.
- **Ревью PR #7, раунд 1:**
  - Письма — Markdown, поэтому текст покупателя (имя, адрес, комментарий, email, телефон, названия позиций и способов) проходит через `App\Support\MarkdownEscaper` (директивы `@md` для многострочного и `@mdi` для однострочного текста, вывод «сырой»: HTML-экранирование и экранирование Markdown делаются одним шагом, `{{ }}` для таких значений не используется). Ломается и автоссылка GFM (`https://`, `www.`, email).
  - Telegram: сообщение строится в пределах 4000 видимых символов (`OrderMessage::compose`): шапка, клиент, итог, срок резерва и ссылка в админку остаются всегда, позиции сокращаются строкой «…и ещё N поз.». Готовый HTML не режется; в `TelegramNotifier` остался только последний рубеж — простой экранированный текст, обрезанный по видимым символам.
  - Исключения почтового транспорта содержат адрес получателя: задача бросает `MailDeliveryException` без `previous` и с маскированными адресами (NF-15). SMTP-таймаут — `MAIL_TIMEOUT` (по умолчанию 20 с, меньше лимита задачи в 40 с).
  - Разветвление уведомлений и «отметка + постановка» в `shop:notify-expiring-reservations` выполняются в одной транзакции (`JobFanOut`): очередь `database` использует то же соединение, поэтому вставки откатываются вместе с отметкой. Дочерние задачи ставятся с `beforeCommit()` — с `afterCommit()` вставка произошла бы после коммита и откат стал бы невозможен. Если `JobFanOut::dispatch()` не поставил ни одной задачи (0), команда бросает исключение внутри транзакции и отметка `expiring_notified_at` откатывается (повтор при следующем запуске). Дочерние задачи — `ShouldBeUnique` (заказ + канал + получатель + событие, `uniqueFor` 1 час); при ошибке блокировки снимаются, иначе ретрай был бы пропущен.
  - `OrderStatusChanged` несёт явный флаг `bySystem` (его выставляет `expireReservations`), «истёк автоматически» больше не выводится из `user === null`.
  - Отметка планировщика (`storage/app/heartbeat`) — один файл, перезаписываемый каждую минуту, чистить нечего; пункта «старые отметки» в `shop:cleanup` нет. Шаги `carts` и `exports` проверяют бюджет времени, исчезнувшие файлы пропускаются.
  - `schedule:run` выполняет задачи одной минуты последовательно, фоновых процессов (`runInBackground`) не используем. Тяжёлые ежедневные задачи разнесены по времени и каждая укладывается в ~50 с: 03:10 пересчёт цен, 04:20 sitemap, 04:40 cleanup, 04:50 `queue:prune-failed` (перенесён с 00:00, где совпадали пять задач).

## D-060. Остатки скелета Laravel: пакеты и скрипт `dev` (техдолг этапа 0)

## D-070. Возрастное ограничение: оба режима, cookie и размытие на клиенте (AG-01…AG-14)
- **Контекст:** владелец продаёт часть товаров с ограничением 16+/18+ и хочет и «плашку для всего сайта», и «только для ограниченных товаров». Главная и подборки кэшируются на 10 минут (общий кэш без привязки к посетителю), поисковые роботы блокироваться не должны.
- **Решение:** режим выбирается в настройках (`AgeGateSettings`: `site` / `restricted`). Ограничение `null/16/18` у категории и товара (varchar(2), enum `AgeRestriction`), действующее значение — собственное у товара, иначе ближайшая категория (по кэшированному дереву, без запросов). Подтверждение хранится в cookie `shop_age` (уровень, N дней из настроек), cookie не шифруется. Размытие и показ плашки решает CSS/мелкий скрипт по `data-age` и cookie, поэтому кэш фрагментов не зависит от посетителя; без JS работает обычная форма `POST /age-gate/confirm`. Страница всегда отдаётся полностью (плашка — оверлей), роботы получают 200 без `noindex`. «Нет» → 302 на главную с сообщением. В оформлении с такими товарами обязателен чекбокс возраста, уровень пишется в `orders.age_confirmed_level`.
- **Отвергнуто:** серверная подмена контента по cookie (ломает кэш и выглядит как клоакинг); блокировка по User-Agent; хранение возраста в сессии (теряется между визитами); защита файлов изображений на сервере (владелец принял «добросовестное» подтверждение).

## D-071. Покупатели: отдельная таблица `customers` и guard `customer`; заказ без регистрации по настройке (CA-01…CA-28)
- **Контекст:** сотрудники живут в `users` и Filament; нужен кабинет покупателя, при этом гостевой заказ должен остаться.
- **Решение:** таблица `customers` + guard `customer` (session), сотрудники остаются в `users`/`web`. Причины: исключение эскалации в админку, разные политики паролей и сессий, разный объём и режим ПДн (обезличивание покупателей), независимость кода v1. Настройка «Разрешить заказ без регистрации» (по умолчанию вкл.), у группы покупателей — флаг «Заказ только после входа». Существующие заказы остаются гостевыми; после подтверждения email гостевые обращения с тем же email привязываются (`OrderLinker`).
- **Отвергнуто:** единая `users` с признаком (риск доступа в админку, смешение политик); отдельный пакет мультиаутентификации; обязательная регистрация.

## D-072. Подтверждение email 6-значным кодом: хранение и лимиты (CA-04, CA-12)
- **Решение:** код — `random_int`, в БД хранится HMAC-SHA256 с ключом приложения (не открытый код), TTL 15 мин, 5 попыток на код, не более 20 неверных вводов в сутки на email (затем блокировка на сутки и письмо владельцу), повторная отправка не чаще раза в 60 с, новый код аннулирует старый, использование атомарно (`UPDATE … WHERE consumed_at IS NULL`). Лимиты на email и IP через `RateLimiter` (файловый кэш). Запросы кода входа/сброса отвечают одинаково для существующих и несуществующих аккаунтов. Все параметры — в настройке «Покупатели и регистрация». Вход по паролю или по коду; сброс пароля и смена email — через код (ссылок с токенами нет).
- **Отвергнуто:** `Hash::make` для кода (медленно и не нужно для одноразового короткоживущего значения); «ссылки подтверждения» (требуют токен в URL, почтовые сканеры их «прокликивают»).

## D-073. Группа покупателей — роль покупателя; «Гость» и «Розница» — системные (CG-01…CG-19)
- **Контекст:** нужны видимость разделов и категорий, показ цен, режимы, доставка, оплата, скидки и ступени; владелец хочет настраивать и гостя.
- **Решение:** одна сущность `customer_groups` для доступа и цен. Системные группы `guest` и `retail` (нельзя удалить и менять код), гость настраивается как любая; значения по умолчанию воспроизводят поведение v1. Доступ к категориям — `all / all_except / only` с подкатегориями через `customer_group_categories`; в режиме `only` родители выбранных доступны как навигационные. Режимы продаж группы зажимают результат `SalesModeResolver`; скрытые цены (`login`/`request`) понижают режим до заявки. Принудительное применение — единый сервис `CatalogAccess` в каталоге, поиске, подсказках, меню, страницах, фасетах, sitemap, корзине и оформлении; скрытое → 404; sitemap и robots строятся для «Гостя»; контент, видимый только вошедшим, отдаётся с `noindex` и `Cache-Control: private`. Кэши ключуются `группа + версия каталога`. Поля, действие которых реализуется позже, создаются миграцией того этапа.
- **Отвергнуто:** отдельные «ценовые группы» и «группы доступа» (двойная сущность); хранение доступа флагами у категорий (непрозрачно для нескольких групп); кэш без ключа группы.

## D-074. Роли сотрудников и права: таблицы `roles`/`role_permissions`, `PermissionService` (RB-01…RB-16)
- **Контекст:** v1 хранит `users.role` (admin/manager). Владелец хочет настраиваемые роли с галочками прав; пакеты ролей запрещены (CLAUDE.md, раздел 3).
- **Решение:** `roles` + `role_permissions(role, permission)`, реестр прав `PermissionRegistry` в коде (`{раздел}.{действие}` плюс специальные: `prices.bulk`, `imports.full_sync`, `orders.delete`, `orders.edit_items`, `orders.edit_prices`, `html_block.edit`, `settings.<страница>.update`, `users.*`, `roles.*`, `system.*`). «Администратор» разрешает всё и не редактируется (в том числе будущие права), «Менеджер» создаётся по матрице 6.13. Политики, `canAccess()` страниц и сервисы вызывают `PermissionService::allows()`; проверки обязательны на сервере. Миграция: `role_id` по значению `role`, затем колонка `role` удаляется (`down()` восстанавливает). Защита последнего активного администратора (закрывает техдолг этапа 0), неизменяемость системных ролей, запрет выдавать права, которых нет у выдающего, журнал `admin_audit_log`. Кэш прав — по роли с версией.
- **Отвергнуто:** spatie/laravel-permission и аналоги (лишний пакет, чужая модель); хранение прав JSON-полем роли (нельзя индексировать и мигрировать); оставить enum и добавить флаги.

## D-075. Оптовый доступ по заявке (CG-20…CG-24)
- **Решение:** заявка `wholesale_applications` от вошедшего покупателя с подтверждённым email (компания, ИНН с контрольной суммой, контакт, комментарий, согласие); уведомление магазина (email/Telegram); менеджер одобряет с обязательным выбором группы (реквизиты копируются в профиль) или отклоняет с причиной; письмо и уведомление в кабинете; повторное решение запрещено; лимиты, предупреждение о дубле ИНН; всё в журнале действий.
- **Отвергнуто:** заявка от гостя без аккаунта (нечего привязывать к группе); автоматическое одобрение по ИНН (нет проверки контрагента).

## D-076. Характеристики: нормализация с числовой колонкой; JSON — кэш для показа (FL-01…FL-22)
- **Контекст:** `products.attributes` (JSON `[{name,value}]`) не индексируется; нужны фильтры, диапазоны и счётчики в пределах 30 SQL на страницу.
- **Решение:** `attributes` (list/number/boolean, единица), `attribute_values`, `product_attribute_values` (+ `value_number decimal(14,4)`, `value_bool`), `category_filters` (набор и порядок на категорию, наследование от ближайшего родителя с собственным набором). JSON-поле **сохраняется как кэш показа** и пересобирается при каждом сохранении характеристик (`AttributeSyncService`): карточка и экспорт не получают дополнительных запросов, старый код остаётся рабочим; источник истины — нормализованные таблицы. Миграция выполняется из админки (действие «Перенести характеристики из JSON»: предпросмотр → фоновая задача `MigrateAttributesFromJson` пачками по 500 с прогрессом), команда `shop:attributes-migrate --dry-run` — запасной вариант; обязательных ручных шагов по SSH нет. Авто-типы: boolean/number при ≥ 95 % числовых значений, иначе list; характеристики с > 200 значениями — нефильтруемые; повторный запуск безопасен. Колонки «Х: имя, ед.» разбираются по порядку: полная подпись → полное имя (совместимость с v1) → разбор суффикса. Импорт «Х: …» пишет в справочник (новые — нефильтруемые).
- **Отвергнуто:** оставить только JSON (нет индексов и диапазонов); полная замена JSON без кэша (+запросы на карточке, переписывание экспорта); EAV в одной таблице значений-строк (нет числового индекса).

## D-077. Фасеты, URL и SEO фильтров (FL-07…FL-14)
- **Решение:** GET-параметры `a[slug][]`, `a[slug][min|max]`, `o[slug][]` с нормализацией и белым списком. Логика — ИЛИ внутри характеристики, И между характеристиками. Выборка — коррелированные `EXISTS` по `product_attribute_values`; счётчики — по одному сгруппированному запросу на характеристику при применённых остальных фильтрах (без своего), числовые min/max — одним запросом; без CTE и оконных функций (MySQL 5.7). Индексы `(attribute_id, attribute_value_id, product_id)` и `(attribute_id, value_number, product_id)`. Кэш фасетов 10 мин по ключу с группой и версией каталога (файловый кэш без тегов). Максимум 9 настраиваемых фильтров и ≤ 10 фасетных запросов на страницу (9 списочных/опционных + 1 числовой). SEO: индексируется страница без фильтров и (при флаге характеристики `index_single_value`) страница с одним фильтром и одним значением; остальные комбинации — `noindex,follow` и canonical на категорию; `robots.txt` параметры не закрывает (роботы должны видеть `noindex`).
- **Отвергнуто:** `Disallow` для параметров (роботы не увидят `noindex`); кэш самих списков под фильтры (дорого и бесполезно при быстрых индексированных запросах); ползунки с гистограммой («Позже»).

## D-078. Модификации: карточка + варианты; `StockService` работает с stockable (VR-01…VR-29)
- **Контекст:** размер/цвет как на маркетплейсах; остатки, цены, импорт и фильтры уже существуют на уровне товара.
- **Решение:** справочник опций (`option_types`, `option_values`), оси карточки (`product_options`, ≤ 3), `product_variants` со своими SKU, штрихкодом, остатком, резервом и необязательными ценами (наследуют карточку), значения в `product_variant_values`, `combo_hash` против дублей, мягкое удаление. `StockService` оперирует «stockable» (товар без модификаций или модификация); порядок блокировок во всех операциях: товары, затем модификации, по возрастанию id (нет взаимоблокировок); `stock_qty`/`reserved_qty`/`final_price` карточки — агрегаты по активным модификациям (min/max цены, сумма остатков; если хотя бы одна активная модификация не учитывается — карточка «не учитывается»), поэтому сортировка, фильтры и «в наличии» каталога не меняются; сверка `shop:variants-rollup`. Режим продаж — на уровне карточки, наличие — модификации. Поиск по артикулу и штрихкоду модификаций — `OR EXISTS` по `product_variants` (индексы `sku`, `barcode`), `products.search_text` не расширяется (поле varchar(1000)). Цена карточки в списках — «от X»; URL карточки прежний, `?variant=` с canonical на карточку. Составные уникальные ключи — через `variant_key = COALESCE(variant_id, 0)` (NULL не уникализируется ни в MySQL, ни в SQLite). Включение и выключение модификаций запрещено при незавершённых обращениях товара. Импорт: строка = модификация, «Артикул карточки» + «Опция: …», карточка должна быть выше в файле.
- **Отвергнуто:** каждая комбинация — отдельный товар (дубли карточек и SEO); хранить остатки модификаций в JSON; пересчитывать агрегат на чтении (медленно для сортировки).

## D-079. PDF-выгрузки: пакет `barryvdh/laravel-dompdf` (CX-01…CX-14)
- **Контекст:** нужна выгрузка истории заказов и бланка/счёта в PDF на Beget (без Node, бинарников, SaaS); CLAUDE.md требует обоснования нового пакета.
- **Решение:** `barryvdh/laravel-dompdf` (чистый PHP, кириллица через DejaVu, внешние ресурсы и PHP в шаблонах отключены). Excel — прежний `spatie/simple-excel`. Синхронные пороги: Excel ≤ 300 обращений, PDF ≤ 200 без состава / ≤ 50 с составом, иначе задача очереди и ссылка в кабинете, файл 24 часа на приватном диске, скачивание через контроллер с проверкой владельца; жёсткие лимиты PDF (1 000 без состава / 300 с составом) и Excel (20 000 строк) настраиваются; формирование чанками по 100 заказов. Один шаблон для истории, печатной формы в админке и «счёта / бланка заказа» оптовика. Символ «₽» проверяется на приёмке, при отсутствии глифа — «руб.». Если обёртка не поддерживает Laravel 13, подключается `dompdf/dompdf` напрямую.
- **Отвергнуто:** mPDF и TCPDF (тяжелее или ручная вёрстка), wkhtmltopdf и headless Chrome (нет на shared-хостинге), внешние сервисы генерации (запрещены разделом 2).

## D-080. Цены групп и ступеней: `PriceResolver` и денормализация (GP-01…GP-23)
- **Решение:** порядок для (группа, количество): ступень (`min_qty ≥ 2`, наибольшая ≤ qty) → точная цена группы (`min_qty = 1`) → розничная `final_price` (с правилами, привязанными к группе, `price_rule_groups`) × (1 − скидка группы), округление — по настройке. Ступени и точные цены — одна таблица `product_price_tiers` (товар или модификация, группа, `min_qty`, цена). Итог шагов 2–3 заранее считается задачей `RecalculatePrices` в `product_group_prices_final` (только когда отличается от розницы; у карточки с модификациями — минимум), чтобы сортировка и фильтр по цене работали по группе зрителя (`COALESCE` + LEFT JOIN, индекс `(customer_group_id, final_price)`). Ступень определяется в момент действия (корзина, оформление) единым `PriceResolver`; в заказ пишутся группа, источник цены, ступень и розничная цена. Импорт/экспорт: «Цена: <код>» и «Цена: <код> от <N>»; история цен получает группу и `min_qty`. Розничная цена зачёркнутой — флаг группы.
- **Отвергнуто:** вычислять цену группы в SQL при каждом запросе; хранить строки для всех групп всех товаров (раздувает таблицу); суммировать ступени по карточке («Позже»).

## D-081. Промокоды: условия, «лучшая цена», атомарный учёт (PM-01…PM-20)
- **Решение:** типы `percent / fixed / free_delivery`, области `all / categories / products / brands`, минимальная сумма, период, общий и персональный лимиты, «только для зарегистрированных», допустимые группы (по умолчанию «Гость» и «Розница»), флаги «действует на товары со скидкой» и «суммируется с акциями» (по умолчанию выкл.: покупателю достаётся лучшая цена, а не две скидки), один код на заказ. Фиксированная сумма распределяется по строкам методом наибольших остатков в копейках. Повторная валидация и увеличение счётчика (`UPDATE … WHERE usage_count < usage_limit`, проверка затронутых строк) — внутри транзакции создания заказа под `lockForUpdate()`; освобождение при отмене (идемпотентно). Массовая генерация одноразовых кодов (префикс, алфавит без похожих знаков, ≤ 5 000, пачки по 500) с экспортом. Перебор кодов ограничен. Лимит гостя считается по HMAC-хэшу email и телефона (не по sha1); «товар со скидкой» определяется полем строки `promo_old_price` (только старая цена правил цен или `compare_at_price`, без зачёркнутой розницы группы); порядок блокировок: заказ → товары → модификации → промокод. Скидка хранится в заказе и в позициях (`promo_discount`), `total = items_total − promo_discount − manual_discount + delivery_price`.
- **Отвергнуто:** считать скидки на клиенте; суммировать акцию и код по умолчанию; хранить использование только счётчиком без журнала применений (нет персонального лимита и освобождения).

## D-082. Промо-ссылки `/go/{slug}` и атрибуция (PM-21…PM-28)
- **Решение:** короткая ссылка ведёт 302 (не 301) на товар / модификацию / категорию / отфильтрованный каталог / внутренний путь (внешние адреса запрещены), добавляет UTM, при наличии промокода ставит cookie `shop_promo` (30 дней), корзина применяет код автоматически и показывает его. Атрибуция «последний клик» через cookie `shop_pl` (30 дней) → `orders.promo_link_id`. Клики — агрегат по дням (`promo_link_stats`, без построчных логов, без ботов), заказы и выручка считаются запросом по `orders.promo_link_id` (нет денормализованных счётчиков, которые могли бы разойтись). `/go/` закрыт в `robots.txt` и отдаёт `X-Robots-Tag: noindex`. QR-код — «Позже»: генерация QR на PHP без нового пакета (GD её не умеет) нецелесообразна; временно — внешний генератор.
- **Отвергнуто:** построчное логирование кликов (ПДн и объём); 301 (кэшируется браузерами, ломает смену цели и срока); добавление QR-пакета ради необязательной функции.

## D-083. Резерв нескольких товаров через корзину (MR-01…MR-13)
- **Решение:** корзина принимает режимы `cart`, `both`, `reservation`. Для строки определяется вид оформления (`order` / `reservation` / `flexible`), на оформлении покупатель выбирает «Оформить заказ» или «Зарезервировать» для гибких строк; смешанная корзина создаёт два обращения (заказ и резерв, `related_order_id`) в одной транзакции с общим порядком блокировок и понятным пояснением. Один `reserved_until` на резерв, «всё или ничего» по остаткам, срок продлевается и истекает целиком, `StockService` удерживает позиции поштучно. Частичного подтверждения и выкупа нет — используется редактирование состава (D-084). Настройка `reservation_via_cart` (по умолчанию вкл.) возвращает поведение v1 при выключении; форма резерва одного товара остаётся.
- **Отвергнуто:** частичный выкуп резерва (усложняет приложение B и статусы); отдельная «корзина резерва» (двойной интерфейс).

## D-084. Редактирование состава заказа: журнал и оптимистичная блокировка (OE-01…OE-16)
- **Решение:** полное редактирование «до выдачи» в статусах `new/confirmed/ready` (заказы) и `new/reserved` (резервы) (владелец: «полное редактирование до выдачи»; `shipped` и `completed` — «Позже»): позиции (включая модификации), количества, цены (право `orders.edit_prices`), доставка, общая скидка (`manual_discount`), контакты. Остатки меняет только `StockService::applyItemChanges()` в одной транзакции с блокировками; дельта считается от прежнего количества позиции (см. D-090), поэтому повторное сохранение ничего не списывает. Каждое изменение пишется в `order_changes` (поле или позиция, было → стало, пользователь, время, `batch_uuid`) в той же транзакции. Оптимистичная блокировка: `orders.version`, `UPDATE … WHERE version = ?`, версия растёт и при смене статуса. Промокод пересчитывается на новом составе (период и лимиты не проверяются). Письмо «Состав заказа изменён» (настройка, по умолчанию вкл.) и уведомление в кабинете. Заявка-запрос превращается в заказ действием «Создать заказ из заявки».
- **Отвергнуто:** блокировка заказа «на время редактирования» (зависшие блокировки на shared-хостинге); пересчёт цены существующей позиции при смене количества (неожиданное изменение суммы); хранение журнала в `order_status_history`.

## D-085. Порядок этапов 8–15 и правило «поле создаётся там, где начинает действовать»
- **Решение:** 8 — роли и группы (опора для остального) + возраст; 9 — кабинет (назначает группы); 10 — характеристики; 11 — модификации; 12 — цены групп; 13 — промокоды и ссылки; 14 — резерв нескольких и редактирование; 15 — выгрузка и приёмка. Фильтры (10) идут до модификаций, а фильтры по опциям включаются на 11 (набор фильтров с источником `attribute|option`); цены групп (12) после модификаций; промокоды (13) после цен и кабинета; редактирование (14) после промокодов и модификаций; PDF (15) последним, чтобы показывать финальную структуру заказа. Поля групп с эффектом позже создаются миграцией своего этапа (скидка — 12, бланк/счёт — 15, «заказ только после входа» и группа по умолчанию для новых — 9); прайс-лист группы — этап 12.
- **Отвергнуто:** делить по темам в порядке пожеланий владельца (кабинет раньше групп — некуда назначать группу; PDF раньше заказов — переделка шаблона).

## D-086. Обезличивание покупателей по запросу (CA-16, CA-17)
- **Решение:** запрос на удаление подтверждается кодом, аккаунт блокируется, через срок отмены (3 дня) команда `shop:anonymize-customers` обезличивает: имя, email (`deleted-{id}@anonymous.invalid`), телефон, адреса, компания, заявки, уведомления, корзины; в обращениях стираются имя, телефон, email, адрес, комментарий, user agent, IP согласия — состав, суммы и статусы остаются для учёта. Администратор может обезличить сразу; операция идемпотентна и пишется в журнал без ПДн.
- **Отвергнуто:** физическое удаление заказов (теряется учёт); удаление покупателя с каскадом на заказы.

## D-087. Уникальность SKU среди товаров и модификаций — на уровне приложения (VR-04)
- **Решение:** уникальные индексы в обеих таблицах + сервис `SkuGuard` проверяет пересечение в транзакции (форма, импорт, дублирование); редкая гонка между параллельным созданием товара и модификации с одним SKU ловится `shop:doctor` («коллизии артикулов»). Таблица-реестр артикулов не вводится.
- **Отвергнуто:** общая таблица `skus` с триггерами или наблюдателями (усложняет импорт и откат); именованные блокировки MySQL (недоступны в SQLite-тестах).

## D-088. Ответы владельца на вопросы ТЗ v2 (раздел 15, CG-21, CG-27)
- **Решено владельцем:** PDF по умолчанию «Бланк заказа»; при заполненных банковских реквизитах продавца в «Юридическое» (банк, БИК, р/с, к/с — поля `LegalSettings`) оптовик может скачать «Счёт на оплату» со своими реквизитами как плательщика. При обновлении создаются группы «Гость» (системная), «Розница» (системная, по умолчанию для новых) и «Опт» (скидка 0 %, заказ только после входа; создаётся миграцией этапа 9, когда появляется поле). Магазин уведомляется только о заявках на опт (email + Telegram, два переключателя в настройках уведомлений); о регистрациях уведомлений нет — они видны в админке и на дашборде.
- **Решено по умолчанию:** возрастная плашка — только добровольное подтверждение, соответствие закону при продаже алкоголя и табака — ответственность владельца; заказы обезличенных покупателей хранятся бессрочно без ПДн; QR промо-ссылок — «Позже».

## D-089. Завершение прочих сессий покупателя: `customers.auth_version` и раздельные сессии (CA-31, CA-32)
- **Контекст:** при `SESSION_DRIVER=file` сессии нельзя перечислить; сброс `remember_token` гасит только cookie «запомнить меня»; `AuthenticateSession` не помогает при смене email (пароль тот же).
- **Решение:** поле `auth_version` увеличивается при смене/сбросе пароля, смене email, блокировке и запросе удаления; значение хранится в сессии, middleware guard-а `customer` сверяет его на каждом запросе. Сессии покупателя и сотрудника делят один файловый драйвер, но используют раздельные ключи guard-ов; выход покупателя — `logout()` + `regenerateToken()` без `session()->invalidate()`, пока активен guard `web`.
- **Отвергнуто:** сессии в БД (допустимо, но меняет раздел 2 и нагрузку); перечисление файлов сессий.

## D-090. Дельта остатков при редактировании заказа считается от прежнего количества (OE-04)
- **Контекст:** формула `new_qty − stock_applied_qty` неверна для позиций «под заказ» и обращений, созданных при выключенном учёте: любое сохранение списывало бы «недостающую» часть.
- **Решение:** `Δ = new_qty − old_qty`; без изменения количества остатки не трогаются; при уменьшении сначала снимается неприменённая часть (`qty − stock_applied_qty`), затем возвращается применённая; `stock_applied_qty ≤ new_qty`; при `orders.stock_applied = false` или `stock_qty IS NULL` остатки позиции не меняются. Порядок блокировок: заказ → товары → модификации → промокод.
- **Отвергнуто:** пересчёт «до целевого applied = new_qty» при каждом сохранении (ломает идемпотентность и «под заказ»).

## D-091. Защита публичного репозитория и CI
- **Контекст:** репозиторий стал публичным: код, история, PR и логи Actions видны всем, а pull request из форка может запустить CI.
- **Решение:** действия в `ci.yml` и `deploy.yml` закреплены по SHA коммита с тегом в комментарии (Dependabot обновляет оба); токен CI только на чтение (`permissions: contents: read`); `actions/checkout` с `persist-credentials: false`, чтобы токен не оставался в `.git/config` на время шагов со сторонним кодом (composer, npm); деплой идёт через окружение `production`, где владелец задаёт обязательное подтверждение и ветку `main`, а секреты Beget хранятся в секретах этого окружения. Добавлен `SECURITY.md` (приватные сообщения об уязвимостях). Настройки репозитория (ruleset для `main`, сканирование секретов, Dependabot alerts, CodeQL, права Actions) включает владелец: список и команды — `docs/DEPLOY_BEGET.md`, приложение «Безопасность CI».
- **Отвергнуто:** сделать репозиторий приватным (решение владельца); `pull_request_target` (дал бы коду из форка доступ к секретам).

## D-092. Роли сотрудников: реализация `PermissionService` и защита от эскалации (RB-04, RB-07, RB-08, RB-13)
- **Решение:** права роли кэшируются в файловом кэше по ключу `perm:role:{id}:{permissions_version}` на 10 минут; любое изменение роли увеличивает `permissions_version`, поэтому действует сразу; память запроса сбрасывается в конце запроса и на каждом цикле очереди. Решения «по сути о роли» (последний администратор, администратор видит чужие экспорты) идут через `isAdministrator()` / `hasAdministratorRole()`, доступ к функциям — только через `allows()`. Эскалация: роли и пользователю можно выдать только права, которые есть у самого сотрудника; не-администратор не меняет и не удаляет учётку с более широкой ролью; свою роль и активность менять нельзя никому. Удаление импорта сопоставлено с `imports.full_sync` (в 25.4 нет `imports.delete`, в 1.0 было только у администратора). Права «Менеджера» по умолчанию — литерал в миграции, равенство с `PermissionRegistry::managerDefaults()` проверяет тест. Журнал хранит только идентификаторы, коды и ключи прав, без имён и email. FK `users.role_id` создаётся только на MySQL (SQLite не добавляет FK к существующей таблице); запрет удаления роли с пользователями — в `RoleService`.
- **Отвергнуто:** пакеты ролей (D-074); проверка `role === 'admin'` в коде.

## D-093. Возрастная плашка: состояние на клиенте, кэшируемый HTML не зависит от cookie (AG-01…AG-14)
- **Решение:** карточки всегда несут `data-age="16|18"` (независимо от включения плашки), настройки управляют только атрибутами `<html>` (`data-age-on`, `data-age-badge`); маленький inline-скрипт в `<head>` ставит `data-age-ok` по cookie `shop_age`, размытие и скрытие оверлея делает CSS. Действующий уровень вычисляется подъёмом по кэшированному дереву категорий (до 4 обращений к массиву, без SQL) — отличие от формулировки «карта на запрос» в AG-01. Кэш `age:has_restricted` (10 мин) сбрасывается событиями товаров/категорий, окончанием импорта и массовым действием. При выключенной плашке ничего не меняется, включая оформление. Cookie `shop_age` — не HttpOnly, SameSite=Lax, исключена из шифрования. Чекбокс возраста — в оформлении заказа и резерва; заявка не охвачена (16.6 называет только CheckoutForm и ReservationForm); `OrderService` перепроверяет по заблокированным товарам и пишет `orders.age_confirmed_level`. Экспорт пишет собственное значение товара, а не действующее.
- **Отвергнуто:** решать показ плашки на сервере (кэш главной зависел бы от cookie); скрывать содержимое страниц от роботов.

## D-094. Группы покупателей: `ViewerContext`, `CatalogAccess` и версия каталога (CG-01…CG-19, CG-27)
- **Решение:** версия каталога — токен в файловом кэше, увеличивается при изменении товаров, категорий, групп, страниц, меню, настроек, импорта, цен и остатков (через существующие точки сброса: `HomePageRenderer::forget()`, `MenuService::flush()`, наблюдатель групп, `CustomerGroupService`); ключи кэша — `home:{group}:{v}`, `menus:{group}:{v}`, `access:{group}:{v}`, `age:has_restricted:{v}` (10 мин). `ViewerContext` — singleton, лениво определяет группу из запроса и сессии (одинаково для Livewire); на этапе 8 зритель — всегда «Гость», этап 9 подключает guard `customer` в `resolveGroup()`. Сотрудник может «Просмотреть витрину как…» группу (флаг в сессии, баннер, `noindex`, `Cache-Control: private`). Режим `all_except` всегда фильтрует `NOT IN` по скрытым id (переключение «по короткому списку» из 25.6 не делалось — индекс по `category_id` используется в обоих случаях). Полностью отмеченные списки режимов/доставки/оплаты хранятся как `null` (без ограничения). `price_display=login` работает в коде, но в форме скрыт до этапа 9 (некуда входить). Если у группы есть раздел «Поиск», но нет «Каталога», поиск тоже закрыт. При удалении группы её id убирается из `visible_group_ids`; опустевший список остаётся `[]` (скрыто от всех, а не открыто всем). Коды способов доставки и оплаты (CG-09) неизменяемы и совпадают с прежними ключами.
- **Отвергнуто:** отдельные кэш-теги (файловый драйвер их не поддерживает); проверка доступа только в шаблонах.

## D-095. Правки по ревью PR #20: sitemap, главная роли без дашборда, предпросмотр витрины (CG-15, CG-18, RB-08, RB-13, AG-07)
- **Решение:** (1) sitemap пересобирается задачей `GenerateSitemap` (unique until processing, после коммита) при сохранении/удалении группы, при смене `is_active`/`parent_id`/`slug` категории и товара (+ `category_id`), страницы (+ `visible_group_ids`) и при удалении записей; создание записей ничего не ставит (новый URL подберёт ночной запуск); в тестах выключено `SITEMAP_REBUILD_ON_CHANGE=false` (sync-очередь пересобирала бы файл на каждое сохранение). (2) Роль без `dashboard.view` на `/admin` перенаправляется на первый пункт своей навигации, при отсутствии доступных разделов остаётся 403. (3) Не-администратор правит и удаляет только роли, права которых — подмножество его прав (`EscalationGuard::canManageRole`, и в политике, и в сервисе); `is_system` и `permissions_version` роли не массово заполняемые. (4) «Просмотреть витрину как…» — POST с CSRF (действие Filament — Livewire-действие, выход — форма в баннере); право `customer_groups.view` проверяется на каждом запросе; корзина, оформление, резерв и заявка в предпросмотре закрыты сообщением (`ViewerContext::assertNotPreview()` в `CartService`/`OrderService`). (5) `CatalogVersion::current()` и группа «Гость» запоминаются на время запроса, сбрасываются в `ViewerContext::beginRequest()`, при `bump()` и перед каждым заданием очереди. (6) Серверный слой не рисует возрастную плашку, если cookie `shop_age` уже подтверждает нужный уровень (и ставит `data-age-ok`), поэтому посетитель без JavaScript проходит; кэшируемые фрагменты (главная) от cookie по-прежнему не зависят.
- **Отвергнуто:** вызовы пересборки sitemap в каждом контроллере/форме; статическая память `CustomerGroup::guest()` в модели (устаревала бы в долгих процессах и тестах).

## D-096. Сессии покупателя: guard `customer`, версия авторизации, формы кабинета на Blade (CA-02…CA-08, CA-31, CA-32)
- **Контекст:** файловые сессии на Beget нельзя перечислить и удалить; сессии покупателя и сотрудника в одном браузере не должны влиять друг на друга.
- **Решение:** отдельный guard `customer` (провайдер `customers`, свой брокер паролей). Сессия хранит `auth_version`, с которой покупатель вошёл; middleware `ValidateCustomerSession` в группе `web` (покрывает и Livewire) сбрасывает сессию, если версия аккаунта выросла (сброс/смена пароля, смена email, блокировка, запрос удаления) или аккаунт заблокирован/обезличен. Сброс — удаление ключа guard и cookie «запомнить меня», а не `logout()`: тот меняет `remember_token` и завершил бы действующие сессии на других устройствах. Каждое увеличение версии меняет `remember_token`, сессия из cookie «запомнить меня» без сохранённой версии принимает текущую. Выход из админки переопределён (`StaffLogoutController`), чтобы не делать `session()->invalidate()` и не выбрасывать покупателя. Формы регистрации, входа, сброса и профиля — обычные Blade-формы с контроллерами и Form Request: CSRF, `session()->regenerate()` и работа без JavaScript; состояние многошаговых сценариев (ожидаемый email, билет сброса) — в сессии.
- **Отвергнуто:** таблица сессий для «завершить другие сессии» (драйвер сессий — файлы, раздел 2); Livewire-формы входа (регенерация сессии и CSRF внутри Livewire-запросов сложнее, без JS не работают).

## D-097. Коды подтверждения и лимиты (CA-04…CA-07, CA-25)
- **Решение:** `VerificationCodeService` хранит только хэш кода; пауза повторной отправки, часовые лимиты и блокировка — `RateLimiter` на кэше (в продакшене — файловый). Для неизвестного адреса выполняются те же проверки и лимиты, но ничего не сохраняется и не отправляется — ответ неотличим от существующего аккаунта. Пауза и неверный код — возврат с ошибкой; часовой лимит и блокировка — HTTP 429 с `Retry-After`. 20 неверных вводов за сутки блокируют все назначения для адреса, владельцу (только если аккаунт есть) уходит письмо о подборе. Письма с кодом — очередь с тремя попытками и `ShouldBeEncrypted`, чтобы открытый код не лежал в `jobs`/`failed_jobs`; контроллер не трогает почтовый транспорт, поэтому сбой почты не раскрывает существование аккаунта. Вход по паролю: счётчик ошибок по паре email+IP, на 5-й — блокировка пары на 15 минут; неподтверждённый аккаунт с верным паролем получает новый код и попадает на страницу подтверждения; запрошенное удаление отменяют вход по коду и сброс пароля по коду (вход по паролю при запрошенном удалении закрыт).
- **Отвергнуто:** таблица попыток (лишние записи в БД на каждую попытку); раскрытие «такого аккаунта нет».

## D-098. Заказ без регистрации, группа новых покупателей, кабинет (CA-01, CA-09…CA-18, CA-26…CA-28, CG-11, CG-12)
- **Решение:** `ViewerContext::mayOrder()` — вошедший покупатель может оформлять; гость — только при включённой настройке «Заказ без регистрации» и без `require_login_to_order` у группы «Гость». Корзина гостю остаётся доступной, закрываются оформление, резерв и заявка (проверка на сервере в `OrderService`, на витрине вместо кнопки — ссылка «Войти»). Группа новых покупателей — флаг `customer_groups.is_default_for_new` (ровно одна группа, меняется на странице настроек через `CustomerGroupService`), а не свойство настроек: удаление такой группы запрещено. Заказы под аккаунтом хранят снимок группы (`customer_group_id`, `customer_group_name`) без внешнего ключа на группу. Выборки кабинета ограничены `customer_id`, деталь обращения — по UUID через `OrderPolicy::viewAsCustomer`, чужой UUID — 404. Страницы вошедшего покупателя отдаются с `Cache-Control: private, no-store`.
- **Отвергнуто:** закрыть корзину гостю целиком (теряется подборка до входа, CA-15 сливает корзины); ключ группы новых покупателей в настройках (рассинхрон при удалении группы).

## D-099. Заявки на оптовый доступ (CG-20…CG-25)
- **Решение:** лимит «не более 3 заявок в месяц» — скользящие 30 дней, отклонённые заявки учитываются; одна ожидающая заявка и лимит проверяются в `WholesaleApplicationService` под блокировкой строки покупателя. Покупатель, уже состоящий в группе с `is_wholesale_default`, повторно не подаёт. При одобрении реквизиты копируются в `customer_companies`, только если их нет; юридического адреса в заявке нет — он остаётся пустым и заполняется в кабинете. «Вернуть в новые» (только Администратор) очищает решение и сохраняет комментарий, но не откатывает группу и реквизиты. Уведомления магазину — два независимых переключателя (email и Telegram), по задаче на адрес и одну на Telegram; сбой отправки не ломает подачу. Журнал действий хранит только идентификаторы, IP покупателя в журнал сотрудников не пишется. При обезличивании покупателя синхронный слушатель `CustomerAnonymizing` стирает персональные поля заявок (включая причину отказа и комментарий сотрудника), статус и решение остаются. Удаление группы (CG-25) — только с выбором группы для переноса покупателей (не «Гость», не неактивная); правила цен, промокоды и групповые цены появятся на следующих этапах — их очистка добавляется там же (наблюдатель группы или внешний ключ с каскадом).
- **Отвергнуто:** календарный месяц для лимита (сброс 1-го числа позволяет 6 заявок подряд); сброс группы при «Вернуть в новые» (неожиданно для покупателя, решение принимает менеджер отдельно).

## D-100. Один Telegram-бот для покупателей и магазина (версия 2.1, TG-01)
- **Контекст:** бот уже шлёт уведомления магазину в рабочий чат (NT-02); нужны Mini App, статусы покупателю и действия сотрудников. Номера D-100+ зарезервированы за версией 2.1, чтобы не пересекаться с решениями этапов 8–15.
- **Решение:** один бот и один токен; все настройки бота переносятся миграцией настроек из группы `notifications` в новую группу `telegram` (`TelegramSettings`) с сохранением значений; переключатели уведомлений магазину остаются в «Уведомлениях». Обновления — только через вебхук с секретом в заголовке, идемпотентность по `update_id`; быстрые ответы — в теле ответа вебхука, остальное — очередь.
- **Отвергнуто:** второй бот для покупателей (две настройки, два вебхука, путаница у владельца); `getUpdates`/long polling (нужен демон — запрещено разделом 2); сторонние Telegram-SDK для PHP (Bot API — несколько HTTP-вызовов, пакет не нужен).

## D-101. Mini App — та же витрина в «режиме Telegram» (TM-06)
- **Контекст:** владелец выбрал «весь магазин» в Mini App; на Beget нет Node и SPA запрещены.
- **Решение:** Mini App использует те же маршруты, контроллеры, Livewire-компоненты, Blade-шаблоны и сервисы; режим Telegram хранится в сессии (`channel = telegram`) и меняет только макет (`layouts.telegram`) и небольшой Alpine-компонент `tgBridge` (тема, `BackButton`, `MainButton`, вибрация). Страницы без `tgBridge` остаются рабочими.

## D-102. Вход в Mini App по подписи Telegram, привязка аккаунта кодом из письма (TM-02, TM-04)
- **Контекст:** покупатель не должен вводить пароль в Telegram; оптовикам нужны их цены.
- **Решение:** сервер проверяет `initData` по алгоритму Telegram (все поля, кроме `hash`, включая `signature`; HMAC-SHA256 с ключом `HMAC("WebAppData", токен)`; `hash_equals`; срок `auth_date` по умолчанию 1 ч, проверяется только при создании сессии). Неизвестный Telegram — гость. Привязка к аккаунту сайта — только после кода из письма (CA-04) или одноразовой ссылки из кабинета (TG-07); привязка подтверждается кнопкой в боте с маскированным email (защита от подсунутой чужой ссылки), владельцу уходит письмо; после привязки Mini App входит автоматически, только пока `customers.auth_version` равна запомненной при привязке — сброс пароля, смена email, «завершить сессии» и блокировка снимают привязку. Вход через Telegram действует только в режиме Telegram и не появляется на сайте.
- **Отвергнуто:** вход по `initDataUnsafe` (подделывается клиентом); автоматическое создание аккаунта по Telegram без email (ломает модель кабинета CA и обезличивание); сопоставление по номеру телефона без кода (номер в профиле не подтверждён).

## D-103. Cookie сессии в Mini App и поддержка Telegram Web (TM-03)
- **Контекст:** приложения Telegram открывают Mini App во встроенном браузере (cookie первой стороны), Telegram Web — во фрейме другого сайта, где браузеры ограничивают cookie.
- **Решение:** для `/tg*` и в режиме Telegram middleware `TelegramCookieMode` выставляет cookie сессии `SameSite=None; Secure; Partitioned`, остальные cookie витрины (XSRF, корзина, возраст, промо, согласие) создаются одной фабрикой `StorefrontCookie` с теми же атрибутами; пустой `WebApp.initData` на клиенте снимает режим (`POST /tg/leave`); поддерживаются официальные приложения Telegram, Telegram Web — где браузер принимает такие cookie, иначе понятное сообщение «Откройте в приложении Telegram или на сайте». Для ответов в режиме Telegram вместо `X-Frame-Options` отправляется `Content-Security-Policy: frame-ancestors 'self' https://web.telegram.org`; админка во фрейме не открывается.
- **Отвергнуто:** передавать `initData` с каждым запросом вместо сессии (переписка всех форм и Livewire-запросов); отключать защиту от фреймов для всего сайта.

## D-104. Внешний скрипт telegram-web-app.js (TM-13)
- **Контекст:** раздел 3 требует собирать фронтенд Vite и не тянуть внешние скрипты; Mini App не работает без официального скрипта Telegram.
- **Решение:** `https://telegram.org/js/telegram-web-app.js` подключается только на `/tg` и в режиме Telegram, без закрепления версии и SRI (Telegram требует актуальную версию и меняет файл), не входит в бюджет NF-03.
- **Отвергнуто:** копия скрипта в `resources/js` (устаревает и ломается при обновлении клиентов Telegram); собственная реализация протокола `postEvent` (недокументированные детали для разных платформ).

## D-105. Действия сотрудников из Telegram и «Рабочее место» (TS-03, TS-05)
- **Контекст:** менеджеру нужно реагировать на заказ с телефона, не открывая полную админку.
- **Решение:** кнопки в сообщениях рабочего чата и Mini App «Рабочее место» вызывают те же сервисы смены статуса и проверяют права через `PermissionService` при каждом действии; сотрудник определяется по привязке `telegram_accounts.user_id` (одноразовая ссылка из профиля). Защита от гонок — `orders.version`, опасные действия — в два нажатия. Вход «Рабочего места» — отдельный guard `telegram_staff` (провайдер `users`), который не принимают ни панель Filament, ни маршруты `auth:web`; переключение покупатель ↔ сотрудник в `/tg/session` выходит из другого guard. Пометка сессии флагом отвергнута на ревью: флаг перезаписывается при входе в Mini App покупателя, а маршруты `auth:web` вне Filament его не проверяют. Журнал — `admin_audit_log` и `order_status_history.source = telegram`.
- **Отвергнуто:** Filament во встроенном браузере Telegram (тяжело, вход через Telegram дал бы полный доступ к админке); действия без привязки сотрудника по участию в рабочем чате (любой участник группы мог бы менять заказы).

## D-106. Минимальные исправленные версии PHP (PHP2Shell, CVE-2026-109618/109619)
- **Контекст:** 21.10.2026 PHP выпустил экстренные исправления двух уязвимостей с удалённым выполнением кода без авторизации; эксплуатация подтверждена. Исправлены 8.3.36, 8.4.27, 8.5.12. Проект требует PHP ≥ 8.3 и проверял только это.
- **Решение:** минимальные исправленные версии веток — в `config/php_security.php` (обычный массив без `env()`, читается и без Laravel). Его используют: `EnvironmentChecker` (`shop:doctor`, страница «Система» — ошибка; для сборок дистрибутивов с суффиксом версии — предупреждение, так как они вносят исправления без смены номера), `.github/scripts/php_security_check.php` в CI (шаг после установки PHP) и в деплое (проверка PHP на хостинге до загрузки файлов — деплой останавливается; флажок запуска `allow_vulnerable_php` позволяет выкатить срочное исправление, пока хостинг не выпустил исправленный PHP, — с предупреждением в журнале). Проверка деплоя намеренно строже `shop:doctor`: суффикс сборки дистрибутива она не учитывает, Beget собирает PHP без суффикса. CI дополнительно прогоняет тесты на PHP 8.4 и 8.5 (необязательная проверка `compat`). При следующем исправлении безопасности обновляется только этот файл. Регрессия SimpleXML в 8.4.27/8.5.12 проект не затрагивает: SimpleXML используется только в dev-инструментах.
- **Отвергнуто:** поднять ограничение в `composer.json` до `^8.3.36` — платформенная проверка Composer роняла бы сайт с фатальной ошибкой при уязвимом PHP вместо понятного сообщения; закреплять точную версию PHP в CI — setup-php и так ставит последнюю сборку ветки.

## D-107. Название магазина в письмах — из настроек
- **Контекст:** имя отправителя и подвал писем брали `APP_NAME` из `.env`, а шапка письма, сайт и админка — «Название магазина» из настроек; владелец менял название в админке, а письма приходили со старым.
- **Решение:** `App\Support\ShopName::get()` — название из настроек с запасным `APP_NAME`; его используют шаблоны писем (шапка, подвал, текстовая версия), страницы ошибок и админка. Слушатель `ApplyShopNameToMail` (`MessageSending`) подставляет название в имя отправителя писем с адреса `MAIL_FROM_ADDRESS`. `APP_NAME` остаётся служебным: от него зависят имена cookie и ключи кэша, поэтому за настройкой он не следует.
- **Отвергнуто:** менять `config('mail.from.name')` при загрузке приложения (чтение настроек на каждом запросе, даже без писем).

## D-108. Канонический email и привязка кода регистрации к сессии (ревью этапа 9)
- **Контекст:** независимое ревью этапа 9 нашло захват аккаунта на MySQL: сортировка `utf8mb4_unicode_ci` не различает регистр и диакритику, поэтому `victim@gmail.com` = `victim@gmáil.com` в `WHERE` и уникальном индексе, а почта уходит на punycode-домен злоумышленника (сброс пароля, вход по коду, привязка гостевых заказов). Второе — гонка CA-05: повторная регистрация неподтверждённого адреса подменяла пароль, и жертва подтверждала аккаунт с паролем злоумышленника.
- **Решение:** `EmailNormalizer` — единственная форма адреса: обрезка пробелов, нижний регистр, локальная часть только ASCII, домен в punycode (`idn_to_ascii`, UTS-46); иначе адрес отклоняется правилом `CanonicalEmail` во всех формах покупателя и в оформлении. Хранение и поиск — только в канонической форме, плюс проверка точного совпадения после выборки (`hash_equals`) и сравнение в PHP в `OrderLinker`; миграция приводит сохранённые адреса к канонической форме. Данные повторной регистрации (имя, телефон, хэш пароля) хранятся в записи кода и применяются только при подтверждении этого кода; код привязан к сессии, из которой шла регистрация (хэш случайного токена сессии), — код из другой сессии не принимается. Регрессионный тест — на MySQL.
- **Отвергнуто:** сменить сортировку колонок на `utf8mb4_bin` (зависит от драйвера, SQLite в тестах её не проверит, остаются расхождения регистра); только перенос данных в код без привязки к сессии (жертва всё равно вводит новый код, запрошенный злоумышленником).

## D-109. Несколько сайтов из одного репозитория: окружение GitHub на сайт
- **Контекст:** владельцу нужно разворачивать ещё сайты на Beget из этого же кода (тот же или другой аккаунт).
- **Решение:** каждый сайт — отдельное окружение GitHub (`production`, `shop2`, …) со своими секретами `BEGET_*` и своими правилами защиты (подтверждение владельца, только `main`). `deploy.yml` получает вход `site` (выбор из списка) и использует `environment: ${{ inputs.site }}`; группа concurrency — на сайт. Добавить сайт = создать окружение с секретами и дописать имя в список `options` (`docs/DEPLOY_BEGET.md`, раздел 13).
- **Отвергнуто:** копия `deploy.yml` на каждый сайт (расходятся правки и исправления деплоя); префиксы секретов на уровне репозитория (`SHOP2_BEGET_PATH` и т. п.) — секреты всех сайтов видны любому запуску, нет отдельного подтверждения на сайт.

## D-110. Подтверждение телефона: звонок-сброс основным способом, провайдер за интерфейсом (версия 2.2, PV)
- **Контекст:** владелец хочет подтверждать номера покупателей недорого для российских номеров. С 2026 года SMS с буквенным именем отправителя требуют регистрации имени у операторов и ежемесячной платы за каждое имя (порядка 1–4 тыс. ₽ у каждого оператора), а SMS без зарегистрированного имени часть операторов блокирует; сама SMS стоит ≈ 5–11 ₽. Звонок-сброс стоит ≈ 0,2–1,9 ₽ и не требует имени отправителя.
- **Решение:** основной способ — звонок-сброс (ввод последних 4 цифр номера звонящего), запасной — SMS (по умолчанию выключен), бесплатный путь — номер из Telegram (TG-09). Провайдер — за интерфейсом `PhoneVerificationGateway`; первым реализуется SMS Aero (звонок и SMS в одном API), остальные (SMSC.ru, SMS.ru, МТС Exolve) подключаются драйверами. Отправка — синхронно в запросе (очередь на Beget раз в минуту слишком медленна для ожидания звонка), с лимитами на номер, IP, сессию и дневным пределом магазина против «накрутки» платных звонков. Сценарии включаются владельцем. Пропуск проверки возможен только при сбое провайдера из закрытого списка (сеть, 5xx, ошибка ключа) и включён по умолчанию, чтобы не терять заказы; нулевой баланс и исчерпание дневного предела блокируют (их может вызвать злоумышленник); лимиты и неверный код никогда не пропускают. Звонок запускается только после проверки остальной формы, отдельной точки «позвонить на номер» нет.
- **Отвергнуто:** только SMS (дороже и с абонплатой за имя); Telegram Gateway основным каналом (оплата в иностранной валюте, ограничения Telegram в России) — «Позже»; сторонние SDK провайдеров (новые пакеты не нужны: несколько HTTP-вызовов).
