# Журнал решений

Формат: контекст → решение → отвергнутые варианты.

## D-001. Версии стека (Этап 0)
- **Контекст:** ТЗ раздел 3 — Laravel 13.x, Filament 5.x, Livewire 4; резервы Laravel 12 / Filament 4.
- **Решение:** Laravel 13, Filament 5, Livewire 4 (через Filament), Pest, Larastan 3 (уровень 5). Все поддерживают PHP 8.3. Резервные версии не понадобились.
- **Отвергнуто:** Laravel 12 / Filament 4 — нет причин.

## D-002. intervention/image версии 3
- **Контекст:** в Packagist доступна 4.x, ТЗ требует 3.x с драйвером GD.
- **Решение:** `intervention/image:^3`, драйвер GD.
- **Отвергнуто:** 4.x — расходится с ТЗ, нет выигрыша для задачи.

## D-003. Роли пользователей
- **Контекст:** ТЗ 6.13 — роль в `users.role`, права через политики, без пакетов ролей.
- **Решение:** enum `App\Enums\UserRole` (`admin`, `manager`), колонки `users.role` (varchar, default `manager`) и `users.is_active`. Доступ в панель — `User::canAccessPanel()` (активен + есть роль). Страницы настроек, пользователи и «Система» — только `admin` (`canAccess()` / политики).

## D-004. Путь админки
- **Решение:** `config('shop.admin_path')` из `ADMIN_PATH` (по умолчанию `admin`), передаётся в `->path()` панели Filament.

## D-005. Отметка планировщика (heartbeat, AD-11)
- **Контекст:** нужна отметка последнего запуска планировщика, без Redis.
- **Решение:** `shop:heartbeat` пишет время в файл `storage/app/heartbeat` (не зависит от драйвера кэша и очищения кэша при деплое `optimize:clear`). Чтение — через сервис `App\Services\System\Heartbeat`.
- **Отвергнуто:** кэш (сбрасывается при `optimize:clear`/`cache:clear`), отдельная таблица (лишняя миграция ради одного значения).

## D-006. Деньги
- **Решение:** в БД `decimal(12,2)`; в коде — целые копейки (`int`) через value-объект/хелпер `App\Support\Money`, форматирование `1 290 ₽`. Без float.

## D-007. Composer в песочнице
- **Контекст:** скачивание dist-архивов с GitHub через прокси песочницы возвращает 403.
- **Решение:** Composer автоматически переходит на git-клоны; установка медленнее, но работает. На CI (GitHub Actions) ограничения нет.

## D-008. Alpine.js на витрине
- **Контекст:** витрина использует Livewire 4 (корзина, формы), а Livewire поставляет Alpine.js в своём бандле.
- **Решение:** не ставить `alpinejs` отдельно из npm; на всех страницах витрины подключать скрипты Livewire (`@livewireScripts`), Alpine берётся оттуда. Так нет двойной инициализации, а JS витрины меньше (NF-03).
- **Отвергнуто:** отдельный пакет `alpinejs` в Vite — конфликт двух экземпляров Alpine.

## D-009. Деньги в настройках — целые копейки
- **Контекст:** настройки (spatie/laravel-settings) хранятся в JSON; float в JSON и в форме ведёт к ошибкам округления (D-006).
- **Решение:** все денежные значения в настройках — `int` в копейках (`min_order_amount`, `price` и `free_from` способов получения). В формах Filament сумма вводится в рублях (допустимы `1 290,50`, `1290.5`, `1 290 ₽`; правило `App\Rules\RublesAmount`); перевод рубли ↔ копейки — только через `App\Support\Money` (`fromRubles`, `toRubles`, `format`) в `mutateFormDataBeforeFill/Save` страницы. Разбор строки — через bcmath, дробные копейки округляются half-up.
- **Отвергнуто:** строки `"0.00"` в настройках (приходится парсить при каждом расчёте); float.

## D-010. Настройки: кэш, миграции, секреты
- **Решение:** кэш пакета включён (`SETTINGS_CACHE_ENABLED`, по умолчанию `true`, хранилище — `CACHE_STORE`, т.е. `file`); при сохранении кэш группы сбрасывается пакетом. Миграция таблицы `settings` лежит в `database/migrations`, значения по умолчанию — в `database/settings/*` (путь в `settings.migrations_paths`), так что `php artisan migrate` создаёт всё одной командой. Токен Telegram хранится зашифрованным (`NotificationSettings::encrypted()`), в миграции значение `null`, реальные значения не засеиваются. Для шифрования нужен `APP_KEY` — в `phpunit.xml` задан тестовый ключ.
- **Ограничение пакета:** `phpdocumentor/type-resolver` не разбирает array shapes (`array{...}`) и `mixed` в `@var` — у свойств-массивов с вложенными массивами (`delivery_methods`, `payment_methods`, `social_links`, `blocks`) `@var` не указывается, структура описана обычным комментарием.

## D-011. Админка: формат дат, пароль, навигация
- **Решение:** форматы Filament задаются глобально в `AppServiceProvider` (`Table`, `Schema`, `DateTimePicker`): `d.m.Y`, `d.m.Y H:i`, `H:i`, валюта `rub`. Минимальная длина пароля 10 (NF-12) — через `Password::defaults()`, действует и в форме пользователя, и при сбросе пароля Filament. Порядок групп меню (AD-03) задан в `AdminPanelProvider::navigationGroups()` строками из `lang/ru/shop.php`; страницы и ресурсы возвращают ту же строку из `getNavigationGroup()`. Название бренда берётся из `GeneralSettings::shop_name` (при недоступной таблице — `config('app.name')`).
- **Доступ:** `canAccessPanel()` = `is_active`; страницы настроек и `UserResource` — только администратор (трейт `AdminOnlySettingsPage`, `UserPolicy`); администратор не может удалить сам себя. Менеджер получает 403 и не видит пункты в меню.

## D-012. Сессия, логи, тесты Livewire
- **Решение:** `SESSION_LIFETIME` по умолчанию 480 минут (NF-12); лог по умолчанию `daily`, хранение 14 дней (NF-21); `APP_TIMEZONE` (по умолчанию `Europe/Moscow`), локаль `ru`, faker `ru_RU`. Livewire-компоненты в тестах вызываются через `Livewire\Livewire::test()` — пакет `pest-plugin-livewire` не добавлялся (правило «пакеты только из раздела 3»).
- **Формат денег на витрине:** `Money::format()` — разряды узким неразрывным пробелом (U+202F), перед `₽` обычный неразрывный пробел (U+00A0), копейки показываются только если не нули: `1 290 ₽`, `1 290,50 ₽`.

## D-013. Шрифты витрины
- **Контекст:** шаблон Laravel подключал шрифт Instrument Sans с fonts.bunny.net через Vite-плагин; сборка зависит от внешнего хоста, а витрина — от стороннего CDN (NF-03, приватность).
- **Решение:** системный стек шрифтов, без внешних шрифтов.
- **Отвергнуто:** самостоятельный хостинг веб-шрифта — лишний вес для NF-03; можно добавить позже.

## D-014. CI на MySQL
- **Решение:** в `ci.yml` отдельная задача с сервисом `mysql:8.0`; переменные `DB_*` заданы на уровне задачи и имеют приоритет над `<env>` из `phpunit.xml` (без `force="true"`). Тесты не требуют сборки Vite (`withoutVite()`).

## D-015. Итоговая цена до Этапа 2
- **Контекст:** витрина и админка Этапа 1 используют `products.final_price`, а калькулятор цен (PR-01) появится на Этапе 2.
- **Решение:** сервис `App\Services\Pricing\ProductPriceUpdater` уже сейчас пишет `final_price`/`display_old_price`/`price_calculated_at` при сохранении товара по упрощённому правилу: `final = fixed_price ?? base_price`, `old = compare_at_price`, если он больше `final`. На Этапе 2 внутренняя логика заменяется на `PriceCalculator`, точка вызова остаётся.

## D-016. SalesModeResolver на Этапе 1
- **Контекст:** карточке товара в списке (SF-15) и колонке «Режим» (AD-40) нужен действующий режим продаж, а продажи реализуются на Этапе 4.
- **Решение:** на Этапе 1 создаётся `App\Services\Sales\SalesModeResolver` с определением режима (цена по запросу → товар → ближайшая категория → магазин) и источника. Поправки на наличие и рабочие кнопки появятся на Этапе 4; пока кнопки ведут на карточку товара.

## D-017. Разделение AD-42
- **Решение:** массовое изменение базовой цены (±% / ±₽ с предпросмотром) реализуется на Этапе 2 вместе с историей цен (PR-06) и правом «только администратор». Экспорт выбранных товаров в Excel — на Этапе 3 вместе с экспортом каталога (EX-01). Остальные массовые действия — на Этапе 1.

## D-018. Редиректы при смене slug (SF-80)
- **Решение:** при смене slug товара/категории в `redirects` пишется `from_path` (старый путь) → `to_path` (новый). Существующие редиректы, ведущие на старый путь, переписываются на новый (без цепочек); редирект, у которого `from_path` совпал с новым путём, удаляется. Проверка выполняется только для 404 на витрине (обработчик исключений / fallback), поэтому обычные запросы не платят лишним SQL-запросом.

## D-019. Поиск (SF-20)
- **Решение:** `products.search_text` = нормализованные (нижний регистр, ё→е, одиночные пробелы) название + артикул + бренд. Запрос нормализуется так же, разбивается на слова, для каждого слова `search_text LIKE %слово%` (AND). Точное совпадение артикула поднимается первым через `ORDER BY CASE WHEN LOWER(sku) = ? THEN 0 ELSE 1 END`. Спецсимволы `%`/`_` экранируются. Без полнотекстовых индексов (переносимость SQLite/MySQL 5.7).

## D-020. Обработка фото (AD-50…53)
- **Решение:** `App\Services\Media\ImageProcessor` (intervention/image 3, GD): ориентация по EXIF, варианты 1600/800/400 px по длинной стороне (без увеличения), WebP 80, если `imagetypes() & IMG_WEBP`, иначе JPEG 85. Пути `products/{product_id}/{uuid}-{size}.webp|jpg` на диске `public`. Исходник после обработки удаляется. В админке файлы загружаются во временный каталог Livewire и обрабатываются при сохранении товара; ошибка одного файла не мешает остальным (уведомление с именем файла).

## D-021. Подсчёт товаров в дереве категорий (AD-30)
- **Решение:** одним запросом получаем число товаров по `category_id`, затем суммируем по материализованным путям в PHP (без N+1 и без CTE). Дерево категорий кэшируется (NF-04) и сбрасывается при изменении категорий.

## D-022. Ассеты Filament
- **Решение:** `php artisan filament:upgrade` выполняется в `post-autoload-dump` Composer; опубликованные ассеты (`public/css|js|fonts/filament`) не хранятся в git и создаются при `composer install` — локально и в CI-сборке релиза перед загрузкой на Beget (на сервере Composer не нужен).

## D-023. Фильтр «Режим» в таблице товаров (AD-41)
- **Решение:** фильтр «Режим» использует собственную настройку режима продаж товара (`inherit` = `null`), а не действующий режим: действующий режим зависит от дерева категорий и настроек магазина и не хранится в таблице. Колонка «Режим» при этом показывает действующий режим (с источником).

## D-024. Арифметика PriceCalculator (PR-01)
- **Решение:** все суммы — целые копейки (`int`). Процент: `round_half_up(price * value / 100)` через bcmath (value — `decimal(12,4)` строкой), результат каждого шага сразу округляется до копейки. Фиксированные наценки/скидки — в копейках. Цена после фазы скидок не ниже 0.
- Округление: шаг в рублях (1/10/50/100), направление вверх/к ближайшему (половина — вверх)/вниз; «психологическая» −1 ₽ только при шаге ≥ 10 и если результат > 0. Округление применяется, если сработало хотя бы одно правило или в настройках выбрано «ко всем»; без правил при «только изменённые» цена не округляется.
- `cost_markup_percent` у товара без закупочной цены пропускается (в объяснении — шаг «пропущено: нет закупочной цены»).

## D-025. Старая цена и настройки показа
- **Решение:** `display_old_price` всегда считается по алгоритму 6.8 (и используется фильтром «Со скидкой» и меткой «Скидка»). Настройки «показывать старую цену / % скидки» влияют только на вывод на витрине.

## D-026. Загрузка правил и кэш
- **Решение:** `PriceRuleRepository` один раз загружает все активные правила с целями (2 запроса) и держит их в памяти процесса и в кэше (`pricing.rules`, сбрасывается при изменении правил); отбор по периоду — по переданному времени внутри калькулятора. Совпадение по категориям — через `CategoryTree::descendantIds` (флаг «включая подкатегории»).

## D-027. Пересчёт при изменении правил и прогресс (PR-02, PR-05)
- **Решение:** при сохранении/удалении/включении правила вычисляется множество затронутых товаров = товары, подходящие под область правила до изменения ∪ после изменения (для области «все» — все товары). Id ставятся в очередь задачами `RecalculatePrices` по 500 штук. Прогресс хранится в кэше (`pricing.recalc`: total/done), баннер в админке читает его; по завершении ключ удаляется.
- `--boundaries`: правила, у которых `starts_at` или `ends_at` попали в интервал (последний запуск, сейчас], последний запуск хранится в кэше (по умолчанию окно 16 минут).

## D-028. История цен (PR-06)
- **Решение:** `PriceHistoryRecorder` пишет изменения `base_price`, `cost_price`, `fixed_price`, `compare_at_price` из наблюдателя товара. Источник и `import_id` задаются контекстом (`PriceChangeContext`, по умолчанию «вручную» + текущий пользователь); массовое действие и импорт оборачивают изменения в свой контекст. Изменения `final_price` от правил не пишутся.

## D-029. PR-07 на Этапе 2
- **Решение:** на Этапе 2 гарантируется, что `final_price` — единственный источник итоговой цены (витрина, админка). Фиксация цены в корзине и сравнение при оформлении реализуются вместе с корзиной на Этапе 4.

## D-030. Пересчёт цен при «сырых» изменениях входных данных (PR-02)
- **Решение:** всё, что пишет `category_id`, `is_featured`, `is_new` или `path` категорий мимо наблюдателя товара, ставит пересчёт затронутых товаров в очередь через `PriceRuleRecalculator::dispatch()` (задачи по 500): массовые «Перенести в категорию» и «Задать/снять метки»; перенос ветки категорий (`CategoryObserver::saved` — товары категории и всех её потомков); удаление категории с переносом товаров (`CategoryTree::deleteMovingToParent`). Всегда без проверки, есть ли правила по категориям (простота важнее оптимизации). Настройки «Цены»: при смене округления/психологической цены ставится пересчёт всех товаров (`PriceRuleRecalculator::dispatchAll()`, тот же код, что у `shop:recalc-prices --all`); переключатели показа старой цены/% скидки пересчёта не требуют. Восстановление товара из корзины пересчитывает цену в наблюдателе (`needsUpdate`).
- Черновик нового правила в предпросмотре получает id `PHP_INT_MAX` (новое правило получит наибольший id и применится последним при равном приоритете); у редактируемого правила — настоящий id.
- Прогресс (`RecalculationProgress`) — необязательные данные: при `LockTimeoutException` пишем предупреждение в лог и пропускаем обновление. Отметка последнего запуска `--boundaries` хранится в файле `storage/app/pricing-boundaries-last-run` (переживает `optimize:clear` при деплое).

## D-031. Границы значений и диапазон дат (PR-01)
- **Решение:** наценка в процентах (`markup_percent`, `cost_markup_percent`) ≤ 1000 %; фиксированные суммы правила ≤ 99 999 999,99 ₽ — предел колонки `price_rules.value decimal(12,4)` (8 цифр в целой части; значение 9 999 999 999,99 в неё не помещается). `PriceCalculator` после каждого шага и после округления ограничивает цену максимумом `decimal(12,2)` (999 999 999 999 коп.).
- Колонки `price_rules.starts_at/ends_at`, `products.price_calculated_at`, `price_history.created_at` — `dateTime` вместо `timestamp` (у MySQL `timestamp` кончается в 2038 году). Миграции этапа 2 ещё не выпущены, поэтому правятся на месте.

## D-032. Массовое изменение цены — в очереди (AD-42)
- **Решение:** действие не меняет цены в HTTP-запросе. `BulkPriceChanger::computeTargets()` считает для выбранных товаров (пачками по 100) `id => [old, new]` в копейках; `dispatch()` режет их на задачи `ApplyBulkPriceChange` по ≤ 200 товаров (≈ 4 мс на товар — укладывается в 40 с). Задача получает автора действия явно (в очереди нет сессии) и выполняет `applyTargets()` в контексте «bulk»: под `lockForUpdate` обновляет только товар, у которого `base_price` по-прежнему равен ожидаемому «старому», остальные пропускает и считает — повтор или ретрай не применит изменение дважды. Источник истории — `bulk`, пользователь — автор.
- Жёсткий лимит выделения — 20 000 товаров (`config('shop.bulk_price_max_selection')`), больше — отказ с сообщением. Пользователь получает уведомление «Изменение цен поставлено в очередь: N товаров». Серверная проверка `changePrices` (`abort_unless`) сохраняется и покрыта тестом на прямой вызов Livewire от менеджера.

## D-033. Конвейер импорта (IM-01…IM-15)
- **Контекст:** Beget — только cron + database-очередь, задача ≤ 40 с, память ≤ 128 МБ; повторное чтение .xlsx для каждой пачки дорого.
- **Решение:**
  1. Загрузка: исходный файл (и ZIP) на приватный диск `local` в `imports/{id}/`; запись `imports` со статусом `uploaded`.
  2. Сопоставление колонок: `ColumnMapper` по заголовкам (без регистра/пробелов/знаков, синонимы приложения A, `Х:`/`Характеристика:` → характеристики); последнее сопоставление берётся из предыдущего импорта по совпадающим заголовкам.
  3. Анализ (задача `AnalyzeImport`): один потоковый проход по файлу — строки нормализуются и пишутся в промежуточный файл `imports/{id}/rows.jsonl`, параллельно считаются сводка «создано/обновлено/пропущено/ошибки» (без записи в каталог) и первые 20 строк для предпросмотра. Лист «Категории» — в отдельный `categories.jsonl`.
  4. Обработка: пачка = 200 строк промежуточного файла (смещение в байтах хранится в `imports`), каждая пачка — своя транзакция. Захват пачки атомарный (`UPDATE imports SET next_chunk = n+1 WHERE id = ? AND next_chunk = n`), поэтому очередь и резервный режим из браузера (IM-10) не обрабатывают одну пачку дважды. Повтор безопасен: идемпотентность по артикулу.
  5. Фото обрабатываются после коммита данных пачки, вне транзакции, с бюджетом времени; если бюджет исчерпан, оставшиеся фото уходят в следующую задачу.
  6. Завершение: полная синхронизация (деактивация отсутствующих), пересчёт цен затронутых товаров, сброс кэшей, событие `ImportFinished` (на него подпишется генерация sitemap на Этапе 5), уведомление в колокольчик Filament.
- **Отвергнуто:** перечитывание исходного файла для каждой пачки (O(n²) по времени для .xlsx); таблица строк в БД (лишний объём в MySQL на shared-хостинге).

## D-034. CSV: кодировка и разделитель (IM-01)
- **Решение:** по первым 64 КБ: если это валидный UTF-8 (BOM удаляется) — UTF-8, иначе Windows-1251 (перекодирование потоком во временный UTF-8-файл). Разделитель — тот из `;` и `,`, которого больше в строке заголовков.

## D-035. Загрузка фото по URL (IM-11)
- **Решение:** только http/https; DNS-резолв хоста и запрет приватных, loopback, link-local, зарезервированных адресов (IPv4/IPv6); соединение закрепляется на проверенный IP (`CURLOPT_RESOLVE`), редиректы проверяются вручную (не более 3, каждый адрес — заново). Таймаут 15 с, ≤ 10 МБ (обрыв по превышению), `Content-Type: image/*` и проверка содержимого, одна повторная попытка. Кэш «URL → файл» в рамках импорта. Ошибка фото — предупреждение в отчёте.

## D-036. EX-02 переносится на Этап 4
- **Решение:** экспорт обращений (EX-02) делается вместе с ресурсом «Обращения» на Этапе 4, так как таблиц заказов ещё нет. Общий механизм фоновых экспортов (EX-03, журнал `exports`) создаётся на Этапе 3.

## D-037. Уведомления в админке
- **Решение:** таблица `notifications` и `databaseNotifications()` панели Filament подключаются на Этапе 3 для уведомлений об импорте/экспорте (раздел 9); остальные уведомления — на Этапе 6.

## D-038. Импорт и мягко удалённые товары
- **Решение:** артикул мягко удалённого товара считается существующим: строка импорта обновляет и восстанавливает товар (в сводке анализа — счётчик `restored`), новый товар с тем же артикулом не создаётся (артикул уникален в БД).
