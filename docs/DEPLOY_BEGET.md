# Развёртывание магазина на Beget — пошагово

Инструкция для владельца магазина без опыта администрирования серверов. Каждый шаг описан по порядку; все команды даны в блоках кода. Команды выполняются в одном из мест:

- **панель Beget** — в браузере, на сайте beget.com;
- **терминал на вашем компьютере** — Terminal (macOS, Linux) или PowerShell / Git Bash (Windows);
- **терминал на сервере** — после входа по SSH (шаг 4);
- **GitHub** — в браузере, в репозитории магазина.

## Обозначения

| Обозначение | Что подставить |
|---|---|
| `LOGIN` | логин вашего аккаунта Beget, например `ivan123`; виден в панели |
| `X` | первая буква логина, например `i` для `ivan123` (так устроены пути Beget) |
| `shop` | имя папки сайта. Инструкция использует `shop`; если панель назвала папку иначе, подставляйте её имя везде вместо `shop` |
| `example.ru` | ваш домен. Пока домен не привязан, используйте технический домен Beget (шаг 2) |
| `ИМЯ_БАЗЫ`, `ИМЯ_ПОЛЬЗОВАТЕЛЯ` | имя базы и пользователя MySQL, как их показала панель (шаг 3) |

Полный путь к каталогу сайта на сервере: `/home/X/LOGIN/shop`, например `/home/i/ivan123/shop`.

Путь к PHP 8.3 на сервере: `/usr/local/php/cgi/8.3/bin/php`. Во всех командах ниже он указан полностью.

**Никогда не отправляйте никому** пароли, файл `.env`, приватный SSH-ключ и токен Telegram-бота. Их не нужно пересылать ни в чат, ни в поддержку.

## 1. Регистрация на Beget и выбор тарифа

1. Откройте сайт beget.com и зарегистрируйте аккаунт.
2. Если Beget предлагает тестовый период, активируйте его в панели. Тестовый период позволяет проверить магазин до оплаты тарифа.
3. Выберите виртуальный хостинг (не VPS) и тариф:
   - **Blog** — для небольшого каталога;
   - **Start** — для каталога более 3 000 товаров с фотографиями (больше места на диске: 35 ГБ против 12 ГБ у Blog).

Тарифы и цены меняются, поэтому сверяйте их с актуальной страницей Beget.

## 2. Создание сайта, домен, версия PHP

1. В панели Beget откройте раздел **«Сайты»** и нажмите создание сайта.
2. Укажите домен:
   - свой домен, например `example.ru` (его нужно зарегистрировать и подключить к Beget);
   - или **технический домен** Beget вида `SITE.LOGIN.beget.tech` — он виден в панели. Пока свой домен не привязан, работайте с техническим.
3. Если панель просит имя папки сайта, укажите `shop`. Итоговый каталог: `/home/X/LOGIN/shop`. Если панель назвала папку иначе, запомните её имя и подставляйте вместо `shop` во всей инструкции.
4. Выберите версию PHP **8.3** для сайта. Обычно это делается в карточке сайта: раздел «Сайты» → нужный сайт → версия PHP (названия пунктов могут отличаться). Проверить версию можно после входа по SSH (шаг 4).

**Важно про структуру.** Веб-сервер Beget отдаёт папку `public_html` внутри каталога сайта. Код Laravel лежит в `/home/X/LOGIN/shop`, а `public_html` — это ссылка на папку `public` проекта. Скрипт деплоя создаёт эту ссылку сам. Ничего не загружайте в `public_html` вручную.

## 3. База данных MySQL

1. В панели откройте раздел **«MySQL»** и создайте базу данных.
2. Beget добавляет к имени префикс вашего логина, например `ivan123_shop`. Имя базы и имя пользователя совпадают (на Beget пользователь базы = её имя). Запомните оба имени точно, как их показала панель.
3. Задайте пароль пользователя базы. Пароль должен быть длинным (не менее 16 символов, со случайными символами). Сохраните его в менеджере паролей.
4. Хост базы — `localhost`.
5. Проверьте версию MySQL. Сделайте это после входа по SSH (шаг 4):

```bash
mysql -V
```

```bash
mysql -h localhost -u ИМЯ_ПОЛЬЗОВАТЕЛЯ -p ИМЯ_БАЗЫ -e "SELECT VERSION();"
```

Во второй команде терминал попросит пароль: введите его (символы не отображаются) и нажмите Enter.

Нужна версия **8.0**. Если выводится **5.7**, обновите сервер до 8.0: в разделе «MySQL» панели есть кнопка обновления. Сделайте это до первого деплоя. Код магазина работает и на 5.7, но целевая версия — 8.0.

## 4. Доступ по SSH и ключ для GitHub Actions

SSH нужен, чтобы настроить сервер и чтобы GitHub Actions мог загружать обновления.

### 4.1. Включение SSH

1. В панели Beget откройте раздел **«Доступ по SSH»** (или «SSH») и включите доступ.
2. Если панель предлагает задать пароль для SSH, задайте его и сохраните в менеджере паролей.

### 4.2. Вход на сервер

На вашем компьютере откройте терминал и выполните (подставьте свой логин):

```bash
ssh LOGIN@LOGIN.beget.tech
```

При первом входе терминал спросит, доверяете ли вы серверу. Ответьте `yes` и нажмите Enter. Затем введите пароль SSH. Символы при вводе не видны, это нормально.

Проверьте, что вы на сервере, и версию PHP:

```bash
pwd
```

```bash
ls /home/X/LOGIN
```

```bash
/usr/local/php/cgi/8.3/bin/php -v
```

В выводе последней команды должно быть `PHP 8.3.x`. Выход из сервера — команда `exit`.

### 4.3. Создание ключа для GitHub Actions

Ключ создаётся **на вашем компьютере**, а не на сервере. Выполните в терминале вашего компьютера:

```bash
ssh-keygen -t ed25519 -f ~/.ssh/github_deploy -N ""
```

Команда создаст два файла:

- `~/.ssh/github_deploy` — **приватный** ключ. Его не показывайте никому, кроме секрета GitHub (шаг 5).
- `~/.ssh/github_deploy.pub` — **публичный** ключ. Его можно добавить на сервер.

Покажите публичный ключ:

```bash
cat ~/.ssh/github_deploy.pub
```

Скопируйте всю строку, которая начинается с `ssh-ed25519`.

### 4.4. Добавление публичного ключа на сервер

Войдите на сервер (`ssh LOGIN@LOGIN.beget.tech`) и выполните команды. Вместо `ВСТАВЬТЕ_СТРОКУ` вставьте скопированную строку целиком, в кавычках:

```bash
mkdir -p ~/.ssh
```

```bash
chmod 700 ~/.ssh
```

```bash
echo "ВСТАВЬТЕ_СТРОКУ_ИЗ_github_deploy.pub" >> ~/.ssh/authorized_keys
```

```bash
chmod 600 ~/.ssh/authorized_keys
```

Выйдите с сервера командой `exit`.

### 4.5. Проверка ключа

Выполните на вашем компьютере (не на сервере):

```bash
ssh -i ~/.ssh/github_deploy LOGIN@LOGIN.beget.tech "echo вход по ключу работает"
```

Если появилась строка `вход по ключу работает` и не запросился пароль, ключ настроен.

## 5. Секреты GitHub и первый запуск деплоя

### 5.1. Таблица секретов

| Имя секрета | Что записать |
|---|---|
| `BEGET_HOST` | адрес SSH-сервера, например `LOGIN.beget.tech` (из раздела SSH в панели) |
| `BEGET_USER` | логин аккаунта Beget, `LOGIN` |
| `BEGET_SSH_KEY` | содержимое **приватного** ключа `~/.ssh/github_deploy` целиком, включая строки `-----BEGIN OPENSSH PRIVATE KEY-----` и `-----END OPENSSH PRIVATE KEY-----` |
| `BEGET_PATH` | полный путь к каталогу сайта: `/home/X/LOGIN/shop` |
| `BEGET_PHP` | путь к PHP 8.3 для командной строки: `/usr/local/php/cgi/8.3/bin/php` |
| `BEGET_KNOWN_HOSTS` | **необязательный**. Отпечаток ключа сервера: вывод команды `ssh-keyscan LOGIN.beget.tech`, выполненной на вашем компьютере. Если секрет задан, деплой доверяет только этому ключу; если не задан, ключ запрашивается у сервера при каждом запуске |

Содержимое приватного ключа выведите на своём компьютере:

```bash
cat ~/.ssh/github_deploy
```

`BEGET_PATH` и `BEGET_PHP` должны быть абсолютными путями из латинских букв, цифр и символов `.` `_` `/` `-` (без пробелов и кавычек), иначе деплой остановится с сообщением об ошибке.

Скопируйте весь вывод, включая первую и последнюю строки. В Windows откройте файл `github_deploy` в Блокноте (он находится в папке `.ssh` в вашей домашней папке пользователя) и скопируйте его содержимое.

### 5.2. Где задать секреты

1. Откройте репозиторий магазина на GitHub.
2. Перейдите в **Settings** → **Secrets and variables** → **Actions**.
3. Нажмите **New repository secret**, введите имя из таблицы и значение. Повторите для каждого секрета.

Проверьте путь `BEGET_PATH` на сервере. Войдите по SSH и выполните:

```bash
ls -ld /home/X/LOGIN/shop
```

Если папки нет, она появится после создания сайта (шаг 2). Если нет и её — создайте: `mkdir -p /home/X/LOGIN/shop`.

### 5.3. Первый запуск деплоя

1. В репозитории откройте вкладку **Actions**.
2. Слева выберите workflow **Deploy**.
3. Нажмите **Run workflow**, в поле ветки оставьте `main` и нажмите зелёную кнопку **Run workflow**.
4. Ждите 5–10 минут и откройте запуск. Зелёная галочка — загрузка прошла.

**Важно: первый запуск только загружает файлы.** Пока на сервере нет файла `.env` с заполненными `APP_KEY` и `DB_DATABASE`, деплой считает установку первой: он загружает файлы, создаёт ссылку `public_html` и папки `storage`, копирует `.env.example` в `.env` (только если `.env` ещё нет, существующий файл никогда не перезаписывается) и **не выполняет** миграции, кэширование и проверку сайта. Запуск завершается успешно с пометкой: «Первая установка: файлы загружены. Заполните .env на сервере (шаг 6 DEPLOY_BEGET.md) и запустите Deploy ещё раз».

Порядок первой установки:

1. Запустите **Deploy** (этот раздел): файлы загружены, на сервере появился шаблон `.env`.
2. Заполните `.env` и создайте ключ приложения (шаг 6.1 и 6.2).
3. Запустите **Deploy** ещё раз: теперь `.env` настроен, деплой выполнит миграции, кэширование и проверит сайт.
4. Заполните начальные данные (`--seed`) и создайте администратора по SSH (шаги 6.2 и 6.3).

Старая папка `public_html`, если она была настоящей папкой, при первом деплое переименовывается в `public_html.bak-ДАТА` (в корне сайта). Деплой её не удаляет; удалите вручную, когда убедитесь, что сайт работает.

## 6. Первоначальная настройка на сервере

Выполняйте команды на сервере (войдите: `ssh LOGIN@LOGIN.beget.tech`).

### 6.1. Создание файла `.env`

Файл `.env` содержит пароли и ключ приложения. Деплой его не перезаписывает и не загружает из репозитория. Первый запуск деплоя (шаг 5.3) уже положил на сервер шаблон `.env`, скопированный из `.env.example`; если по какой-то причине его нет, создайте командой ниже.

```bash
cd /home/X/LOGIN/shop
```

```bash
test -f .env || cp .env.example .env
```

```bash
nano .env
```

Откроется редактор `nano`. Измените значения (переход между строками — стрелками, символы вводите как обычный текст):

```ini
APP_NAME="Название вашего магазина"
APP_ENV=production
APP_KEY=
APP_DEBUG=false
APP_URL=https://SITE.LOGIN.beget.tech
SHOP_EXTRA_HOSTS=
ADMIN_PATH=admin
DB_DATABASE=ИМЯ_БАЗЫ
DB_USERNAME=ИМЯ_ПОЛЬЗОВАТЕЛЯ
DB_PASSWORD=ПАРОЛЬ_ОТ_БАЗЫ
SESSION_SECURE_COOKIE=true
MAIL_FROM_ADDRESS=
```

Что означают значения:

- `APP_URL` — полный адрес магазина с `https://`, без `/` в конце. **Пока свой домен не привязан, укажите технический домен Beget**, например `https://SITE.LOGIN.beget.tech`. Когда привяжете свой домен, замените его на `https://example.ru` и оставьте технический адрес в `SHOP_EXTRA_HOSTS` (см. ниже и раздел 11).
- `SHOP_EXTRA_HOSTS` — дополнительные адреса, через запятую, которые тоже должен принимать магазин. Обычно пусто, пока свой домен не привязан. После привязки домена сделайте так: в `APP_URL` впишите настоящий домен (`https://example.ru`), а технический адрес оставьте в `SHOP_EXTRA_HOSTS` (например, `SHOP_EXTRA_HOSTS=SITE.LOGIN.beget.tech`). Магазин примет такой адрес, но сразу перенаправит (301) на адрес из `APP_URL`: иначе страницы технического домена загружали бы скрипты с другого адреса и не работали. Затем выполните `optimize:clear` и `optimize` (или запустите Deploy).
- `ADMIN_PATH` — часть адреса входа в админ-панель: `https://ваш-адрес/admin`. Можно заменить `admin` на другое слово из латинских букв, например `office-7k2`. Запомните его.
- `DB_DATABASE`, `DB_USERNAME`, `DB_PASSWORD` — данные из шага 3.
- `MAIL_FROM_ADDRESS` — адрес, с которого уходят письма. Заполняется в шаге 8, без него письма не отправляются.

Сохранить и выйти из `nano`: нажмите `Ctrl+O`, затем `Enter`, затем `Ctrl+X`.

Строки `APP_NAME`, `APP_ENV`, `APP_DEBUG`, `SESSION_SECURE_COOKIE` в `.env.example` уже правильные для продакшена. Не меняйте `APP_DEBUG` на `true`: при ошибках он покажет посетителям служебные данные.

### 6.2. Ключ приложения и таблицы базы

```bash
cd /home/X/LOGIN/shop
```

```bash
/usr/local/php/cgi/8.3/bin/php artisan optimize:clear
```

```bash
/usr/local/php/cgi/8.3/bin/php artisan key:generate
```

Команда `optimize:clear` сбрасывает кэш конфигурации: без неё `key:generate` может записать в `.env` второй ключ рядом со старым, и сайт перестанет открываться (ошибка 500). Команда `key:generate` создаёт `APP_KEY`. **Не запускайте её повторно**, когда магазин уже работает: новый ключ сделает нечитаемыми зашифрованные данные (токен Telegram, настройки).

Теперь запустите **Deploy** в GitHub ещё раз (шаг 5.3): он создаст таблицы (`migrate`) и включит кэширование. Затем на сервере заполните начальные настройки:

```bash
/usr/local/php/cgi/8.3/bin/php artisan migrate --force --seed
```

Команда `migrate --force --seed` создаёт недостающие таблицы и начальные значения настроек (после деплоя таблицы уже есть, останутся только начальные данные). Флаг `--force` нужен, чтобы команда выполнялась на сервере без вопросов.

Вместо полного пути к PHP можно создать короткий псевдоним на время сессии: `alias php83=/usr/local/php/cgi/8.3/bin/php`. Тогда команды пишутся так: `php83 artisan shop:doctor`. Ниже используется полный путь.

### 6.3. Администратор

```bash
cd /home/X/LOGIN/shop
```

```bash
/usr/local/php/cgi/8.3/bin/php artisan shop:create-admin
```

Команда спросит имя, адрес электронной почты и пароль (не менее 10 символов). Вводите пароль в ответ на вопрос, а не в самой команде, чтобы он не остался в истории терминала. Менеджеров администратор добавляет потом в админке: «Настройки → Пользователи».

### 6.4. Проверка окружения

```bash
/usr/local/php/cgi/8.3/bin/php artisan shop:doctor
```

Каждая строка отчёта — «ОК», «Внимание» или «Ошибка» с подсказкой. Строку «Ошибка» нужно исправить до запуска. «Внимание» желательно исправить. Пункт про планировщик покажет «Внимание», пока не настроен cron (шаг 7). Пункты про почту (`MAIL_FROM_ADDRESS`, `MAIL_HOST`) покажут «Ошибку», пока не настроен SMTP в шаге 8: после шага 8 они станут «ОК».

### 6.5. Повторный деплой

Дальше обновления выкладываются запуском **Deploy** (раздел 5.3): `.env` настроен, деплой проходит полностью.

## 7. Cron: две задачи в CronTab

Магазин выполняет фоновую работу через cron Beget. Для этого в панели создаются **две задачи**, каждая запускается **каждую минуту**.

В панели откройте раздел **«CronTab»** (иногда «Планировщик задач»), нажмите **«Добавить задачу»** и создайте две задачи. Периодичность — каждую минуту (`* * * * *`).

Первая задача — планировщик (расписание магазина):

```bash
* * * * * /usr/local/php/cgi/8.3/bin/php /home/X/LOGIN/shop/artisan schedule:run >> /dev/null 2>&1
```

Вторая задача — очередь (уведомления, импорт, пересчёт цен):

```bash
* * * * * /usr/local/php/cgi/8.3/bin/php /home/X/LOGIN/shop/artisan queue:work --stop-when-empty --max-time=50 --tries=3 >> /dev/null 2>&1
```

Если панель просит отдельно поле «периодичность» и поле «команда», в первое введите `* * * * *`, во второе — текст после этих пяти звёздочек (путь к PHP и дальше). Замените `X` и `LOGIN` на свои значения.

### Зачем две задачи

- `schedule:run` каждую минуту проверяет расписание магазина и запускает нужные задачи (список ниже).
- `queue:work` обрабатывает очередь: письма, Telegram-уведомления, импорт и пересчёт цен пачками.
- Очередь вынесена в отдельную строку, чтобы длинная пачка (например, импорт) не задерживала задачи расписания. Каждая задача очереди должна завершиться не дольше 40 секунд, а процесс принудительно останавливается через 50 секунд (`--max-time=50`), потому что хостинг не допускает постоянно работающих процессов.
- `--stop-when-empty` завершает обработку, когда очередь пуста. Каждую минуту запускается новый короткий процесс.
- `--tries=3` — три попытки для задачи, которая не удалась.

### Задачи расписания, которые выполняются автоматически

| Команда | Когда | Что делает |
|---|---|---|
| `shop:heartbeat` | каждую минуту | отмечает время запуска cron (проверка на странице «Система») |
| `shop:expire-reservations` | каждые 5 минут | снимает просроченные резервы и возвращает товар на склад |
| `shop:notify-expiring-reservations` | каждый час | предупреждает о резервах, которые истекают в ближайшие 6 часов |
| `shop:recalc-prices --boundaries` | каждые 15 минут | пересчитывает цены по правилам, которые начались или закончились |
| `shop:recalc-prices --all` | ежедневно, 03:10 | полный пересчёт итоговых цен |
| `shop:sitemap` | ежедневно, 04:20 | создаёт файл карты сайта `sitemap.xml` |
| `shop:cleanup` | ежедневно, 04:40 | удаляет старые корзины и служебные файлы |
| `queue:prune-failed --hours=168` | ежедневно, 04:50 | очищает упавшие задачи старше недели |

Эти задачи запускает сам магазин. Вам их в cron вручную добавлять не нужно.

### Проверка cron

1. Подождите 2–3 минуты после добавления задач.
2. Войдите в админ-панель: `https://ваш-адрес/admin` (или ваш `ADMIN_PATH`).
3. Откройте страницу **«Система»** (раздел «Система» в меню). Строка «последний запуск планировщика» должна быть свежей (не старше 5 минут). Раздел очереди покажет количество ожидающих и упавших задач.
4. На главной странице админ-панели (дашборд) не должно быть предупреждения «Планировщик не запускался более 5 минут».

Проверка через сервер: файл `heartbeat` обновляется каждую минуту.

```bash
ls -l /home/X/LOGIN/shop/storage/app/heartbeat
```

Выполните команду дважды с интервалом в две минуты: время изменения файла должно смениться.

## 8. SSL, принудительный HTTPS, почта

### 8.1. Сертификат SSL (Let's Encrypt)

1. В панели Beget откройте **«Сайты»**, выберите сайт и откройте раздел **SSL** (или «Let's Encrypt»).
2. Выпустите бесплатный сертификат Let's Encrypt для домена. Сертификат выдаётся бесплатно и продлевается автоматически.
3. Через несколько минут откройте `https://ваш-адрес` в браузере: должен быть замочек без предупреждений.

### 8.2. Принудительный HTTPS

Чтобы посетители всегда попадали на `https://`, включите переключатель принудительного перенаправления на HTTPS в карточке сайта в панели Beget. Название пункта может отличаться; если его нет, обратитесь в поддержку Beget.

Блок перенаправления в файле `public/.htaccess` в репозитории закомментирован. Раскомментировать его на сервере можно, но при следующем деплое файл будет перезаписан из репозитория, поэтому предпочтителен переключатель в панели.

Убедитесь, что `APP_URL` начинается с `https://` (шаг 6.1).

### 8.3. Почтовый ящик на домене

1. В панели Beget откройте раздел **«Почта»** и создайте ящик на вашем домене, например `shop@example.ru`. Для технического домена почта может быть недоступна, тогда используйте ящик на своём домене.
2. Запомните адрес и пароль ящика.

### 8.4. Настройки SMTP в `.env`

Откройте файл на сервере:

```bash
cd /home/X/LOGIN/shop
```

```bash
nano .env
```

Заполните блок почты:

```ini
MAIL_MAILER=smtp
MAIL_HOST=smtp.beget.com
MAIL_PORT=ПОРТ
MAIL_USERNAME=shop@example.ru
MAIL_PASSWORD=ПАРОЛЬ_ОТ_ЯЩИКА
MAIL_FROM_ADDRESS=shop@example.ru
MAIL_FROM_NAME="Название магазина"
```

- `MAIL_PORT` — порт и тип шифрования уточните в панели Beget в разделе «Почта». Обычно указывают порт 465 (SSL) или 2525; значение из панели важнее примера.
- `MAIL_FROM_ADDRESS` — обязателен. Без него письма не уходят. Обычно это тот же ящик, что и `MAIL_USERNAME`.

Сохраните файл (`Ctrl+O`, `Enter`, `Ctrl+X`), сбросьте кэш конфигурации и соберите его заново:

```bash
/usr/local/php/cgi/8.3/bin/php /home/X/LOGIN/shop/artisan optimize:clear
/usr/local/php/cgi/8.3/bin/php /home/X/LOGIN/shop/artisan optimize
```

### 8.5. Тест почты

1. Войдите в админ-панель.
2. Откройте **«Настройки»** → **«Уведомления»**.
3. В разделе «Email» нажмите кнопку проверки отправки и укажите адрес, на который вы получаете письма.
4. Если письмо не пришло, проверьте папку «Спам», значения `MAIL_*` и раздел 11 («Письма не уходят»).

## 9. Проверка работы магазина

### 9.1. Страница «Система»

В админ-панели откройте **«Система»**. Ошибок («Ошибка») быть не должно. Пункты «Внимание» прочитайте: к каждому приложена подсказка, что сделать.

### 9.2. Витрина открывается

В браузере откройте `https://ваш-адрес`. Главная страница открывается без ошибок.

Проверка служебного адреса (с вашего компьютера):

```bash
curl -I https://ваш-адрес/up
```

В первой строке ответа должно быть `HTTP/2 200` (или `HTTP/1.1 200`).

### 9.3. Первый импорт

Файлы для проверки лежат в репозитории в папке `examples/`:

- `import-demo.xlsx` — демонстрационный каталог (вымышленные товары);
- `import-demo-photos.zip` — фотографии к нему.

Файлы можно скачать на GitHub: откройте папку `examples`, выберите файл и нажмите **Download**.

Порядок:

1. В админ-панели откройте **«Импорт»** и запустите мастер импорта.
2. Загрузите `import-demo.xlsx`. На шаге «Сопоставление колонок» проверьте соответствия, на шаге «Предпросмотр» — что строки распознаны.
3. Фотографии: если ZIP небольшой, загрузите его в мастере вместе с файлом. Если ZIP большой (сотни мегабайт), загрузите его по SFTP (см. раздел 11, пункт «Большие ZIP»), а в мастере выберите его из списка на сервере.
4. Запустите импорт и дождитесь отчёта. Большие импорты выполняются пачками в очереди, поэтому отчёт может появиться через несколько минут — это нормально, если работает cron (шаг 7).
5. После проверки удалите тестовые товары в админ-панели.

### 9.4. Тестовый заказ

1. Откройте витрину в **режиме покупателя** (другой браузер или окно инкогнито).
2. Добавьте товар в корзину, оформите заказ.
3. В админ-панели откройте **«Заказы»** — заказ должен появиться.
4. Письмо о новом заказе должно прийти на адрес, указанный в настройках уведомлений.
5. Тестовый заказ после проверки отмените или удалите в админ-панели.

### 9.5. Telegram-бот для уведомлений

Уведомления о заказах и заявках можно получать в Telegram.

1. В Telegram найдите бота **@BotFather** и отправьте команду `/newbot`.
2. Укажите название бота и его имя пользователя (оно должно заканчиваться на `bot`, например `shop_orders_7k2_bot`).
3. BotFather пришлёт **токен** вида `123456789:AA...`. Это секрет: не публикуйте его и не отправляйте в чатах.
4. Откройте чат с вашим ботом и отправьте ему любое сообщение, например `привет`.
5. Узнайте **Chat ID**. В браузере откройте адрес (вместо `ТОКЕН` подставьте токен):

```text
https://api.telegram.org/botТОКЕН/getUpdates
```

В ответе найдите фрагмент `"chat":{"id":123456789,...}`. Число `123456789` — это Chat ID. Для группы добавьте бота в группу, отправьте в группу сообщение и откройте тот же адрес: ID группы начинается с минуса.

6. В админ-панели откройте **«Настройки»** → **«Уведомления»** → раздел **Telegram**. Вставьте токен и Chat ID, включите отправку и нажмите кнопку проверки. В Telegram должно прийти тестовое сообщение.

Токен хранится в базе в зашифрованном виде.

## 10. Обновление, откат, резервные копии и восстановление

### 10.1. Обновление магазина

1. В GitHub откройте **Actions** → **Deploy** → **Run workflow**.
2. Оставьте ветку `main` (или выберите нужную) и запустите.
3. Во время обновления посетители видят страницу обслуживания. По окончании деплой выводит магазин из режима обслуживания сам. Миграции базы применяются автоматически.

Если деплой завершился с ошибкой, откройте запуск и прочитайте, на каком шаге он остановился. При ошибке деплой сам выводит сайт из режима обслуживания, даже если файлы или миграции обновились не полностью. Поэтому после неудачного деплоя исправьте причину и запустите его повторно, или откатитесь (раздел 10.2). Если сайт всё же остался в режиме обслуживания (например, оборвалось соединение), выведите его командой:

```bash
/usr/local/php/cgi/8.3/bin/php /home/X/LOGIN/shop/artisan up
```

### 10.2. Откат к предыдущей версии

Откат кода выполняется повторным деплоем старой версии:

1. Найдите тег или хеш коммита предыдущей рабочей версии (в GitHub: **Releases**, **Tags** или история коммитов).
2. В **Actions** → **Deploy** → **Run workflow** укажите в поле ветки (`ref`) этот тег или хеш коммита и запустите.

**Миграции базы при откате не откатываются автоматически.** Если новая версия добавила таблицы или поля, старая версия может работать некорректно. Тогда откатите последнюю миграцию вручную, но сначала сделайте резервную копию базы (раздел 10.3):

```bash
cd /home/X/LOGIN/shop
```

```bash
/usr/local/php/cgi/8.3/bin/php artisan migrate:status
```

```bash
/usr/local/php/cgi/8.3/bin/php artisan migrate:rollback --step=1
```

`migrate:rollback` удаляет структуру, связанную с миграцией, и может удалить данные. Выполняйте её только после резервной копии. Если не уверены — сначала обратитесь к разработчику.

### 10.3. Резервные копии (NF-20)

Магазин использует два вида копий:

1. **Штатные резервные копии Beget** — копии файлов сайта и базы MySQL. Откройте в панели раздел **«Резервные копии»** (название может отличаться) и проверьте, что копирование включено и хранятся копии за нужный период. Перед каждым обновлением запускайте копию вручную, если панель позволяет.
2. **Экспорт каталога в Excel** — в админ-панели откройте раздел **«Экспорт»** и выгрузите каталог. Файл можно повторно загрузить через **«Импорт»**: повторный импорт того же файла не меняет данные.

### 10.4. Восстановление

**Файлы сайта.** В разделе «Резервные копии» выберите копию файлов и восстановите каталог `shop`. Если восстанавливаете отдельные файлы, используйте SFTP (раздел 9.3). Файл `.env` на сервере при восстановлении не удаляйте: без него магазин не работает. Если восстанавливаете целиком, сначала сохраните текущий `.env`:

```bash
cp /home/X/LOGIN/shop/.env ~/shop.env.backup
```

**База данных.** Восстановите базу из резервной копии в разделе «Резервные копии» или импортируйте дамп через phpMyAdmin (раздел «MySQL» в панели).

**После восстановления** выполните на сервере:

```bash
cd /home/X/LOGIN/shop
```

```bash
/usr/local/php/cgi/8.3/bin/php artisan optimize:clear
```

```bash
/usr/local/php/cgi/8.3/bin/php artisan migrate:status
```

Если в выводе есть строки `Pending` (невыполненные миграции), выполните:

```bash
/usr/local/php/cgi/8.3/bin/php artisan migrate --force
```

```bash
/usr/local/php/cgi/8.3/bin/php artisan shop:doctor
```

**Каталог из Excel.** Если база потеряна полностью, восстановите каталог из файла экспорта: «Импорт» → загрузите файл экспорта. Товары и категории будут созданы заново.

## 11. Частые проблемы

### «500 Internal Server Error» после деплоя

Причина видна в журнале. Журнал ведётся по дням в `storage/logs`. Посмотрите последний файл:

```bash
ls -t /home/X/LOGIN/shop/storage/logs | head -3
```

```bash
tail -n 50 /home/X/LOGIN/shop/storage/logs/ИМЯ_ФАЙЛА_ИЗ_ПРЕДЫДУЩЕЙ_КОМАНДЫ
```

Если в журнале про права доступа, выставьте права на запись:

```bash
chmod -R 775 /home/X/LOGIN/shop/storage /home/X/LOGIN/shop/bootstrap/cache
```

Если написано про ключ шифрования (`No application encryption key`) и `APP_KEY` в `.env` пуст, сначала очистите кэш, затем один раз создайте ключ (как в шаге 6.2) и снова включите кэш:

```bash
/usr/local/php/cgi/8.3/bin/php /home/X/LOGIN/shop/artisan optimize:clear
/usr/local/php/cgi/8.3/bin/php /home/X/LOGIN/shop/artisan key:generate
/usr/local/php/cgi/8.3/bin/php /home/X/LOGIN/shop/artisan optimize
```

### Деплой остановился: «APP_KEY пуст на работающем сайте»

Деплой проверяет сервер до загрузки файлов. Если сайт уже работает (есть кэш конфигурации `bootstrap/cache/config.php`), а в `.env` пропал `APP_KEY`, он останавливается с этой ошибкой и ничего не загружает. Новый ключ сделал бы нечитаемыми зашифрованные данные (например, токен Telegram и сессии), поэтому деплой его не создаёт. Откройте резервную копию `.env` (раздел 10.3), перенесите из неё строку `APP_KEY=...` в `.env` на сервере и запустите Deploy заново. Ключ создаётся командой `key:generate` только при первой установке (шаг 6.2).

### «400 Bad Request» на техническом домене

Магазин принимает только адреса, указанные в `APP_URL`, и их вариант с `www.`. Технический домен Beget (`*.beget.tech`) пропускается, только если он указан в `APP_URL` или в `SHOP_EXTRA_HOSTS` (в последнем случае он перенаправляется на адрес из `APP_URL`). Исправьте `.env` (шаг 6.1), затем выполните `optimize:clear` и `optimize` (или запустите Deploy).

### `www.` перенаправляет на основной адрес

Адрес `www.example.ru` (а также адреса из `SHOP_EXTRA_HOSTS`) перенаправляется (301) на `example.ru` (адрес из `APP_URL`). Если раньше вы настроили наоборот (`APP_URL` = технический домен, а свой домен в `SHOP_EXTRA_HOSTS`), то теперь ваш домен будет перенаправляться на технический: поменяйте значения местами (свой домен — в `APP_URL`, технический — в `SHOP_EXTRA_HOSTS`) и выполните `optimize:clear` и `optimize`. Это нормально: так у магазина один основной адрес. Если хотите основной адрес с `www.`, укажите его в `APP_URL` и оставьте без `www.` привязанный домен в панели.

### На сервере нет rsync

Деплой сам переключается на архивный режим (загрузка архива `tar.gz`). Ничего делать не нужно: в журнале GitHub Actions появится соответствующая строка.

### Cron не работает

- Проверьте две строки CronTab (раздел 7): пути, версия PHP 8.3, поле «каждую минуту».
- Проверьте, что путь к PHP существует:

```bash
ls -l /usr/local/php/cgi/8.3/bin/php
```

- Подождите 2–3 минуты и откройте «Система». Если последний запуск не обновляется, проверьте путь к `artisan` в CronTab.

### Письма не уходят

- Пустой `MAIL_FROM_ADDRESS` — заполните его (шаг 8.4).
- Неверный `MAIL_PORT` или пароль ящика — сверьте с разделом «Почта» в панели Beget.
- Проверьте журнал (`storage/logs`) — там записывается причина без адресов покупателей.
- После изменения `.env` выполните `optimize:clear`, затем `optimize` (или запустите Deploy).

### Большие ZIP с фотографиями

Веб-загрузка ограничена лимитами хостинга. Большой архив загрузите по SFTP (WinSCP, FileZilla или любой SFTP-клиент; вход — `LOGIN.beget.tech`, порт 22, логин `LOGIN`, пароль SSH) в папку:

```text
/home/X/LOGIN/shop/storage/app/import-media/
```

Папку создайте, если её нет:

```bash
mkdir -p /home/X/LOGIN/shop/storage/app/import-media
```

В мастере импорта выберите архив из списка «на сервере».

### Админ-панель открывается с ошибкой 404

Проверьте `ADMIN_PATH` в `.env` и адрес в браузере: `https://ваш-адрес/ЗНАЧЕНИЕ_ADMIN_PATH`. После изменения выполните `optimize:clear`, затем `optimize`.

### Магазин показывает страницу обслуживания

Если деплой остановился на середине, магазин может оставаться в режиме обслуживания. Выведите его:

```bash
/usr/local/php/cgi/8.3/bin/php /home/X/LOGIN/shop/artisan up
```

## 12. Перед запуском для покупателей

Пройдите список перед открытием магазина:

1. **Тексты страниц политики и согласия.** Сейчас это шаблоны с пометкой «Шаблон — проверить у юриста». Замените текст на согласованный с юристом и удалите пометку. Это обязательное условие: без согласованного текста согласие на обработку персональных данных не имеет юридической силы. Страницы редактируются в админ-панели (раздел «Контент», пункт «Страницы»).
2. **Остальные страницы.** Проверьте остальные страницы в админ-панели: черновики не показываются покупателям, пока их не включите.
3. **Реквизиты продавца.** Заполните название, ИНН, ОГРН, юридический адрес и контакты в настройках магазина и в текстах страниц.
4. **Почта и Telegram** проверены (разделы 8.5 и 9.5).
5. **Тестовые данные удалены:** тестовые товары, заказы и заявки.
6. **Резервная копия сделана** (раздел 10.3).
7. **Режим магазина.** В настройках проверьте переключатель «магазин открыт / закрыт» и текст закрытого режима.
8. **Окончательная проверка.** Откройте «Система» (ошибок быть не должно) и `https://ваш-адрес` в режиме покупателя.

Если что-то не получается, обратитесь в поддержку разработчика. Передавайте только текст ошибки и вывод `shop:doctor`, убрав из него всё, что похоже на пароли и ключи. Файл `.env` и приватный ключ не передавайте никогда.

## Приложение. Безопасность CI

GitHub Actions в `.github/workflows` подключены по тегам версий (`actions/checkout@v4` и т. д.). Тег может быть перемещён автором, поэтому надёжнее закрепить действие по хешу коммита. Dependabot (`.github/dependabot.yml`, раз в неделю) сам предлагает обновления. Закрепление по хешу делает владелец один раз вручную: нужны права на чтение публичных репозиториев и `gh`.

1. Узнайте хеш коммита для каждого тега (для аннотированного тега поле `object.type` равно `tag`, тогда выполните второй запрос с `object.sha`):

```bash
gh api repos/actions/checkout/git/ref/tags/v4 --jq '.object.type + " " + .object.sha'
gh api repos/actions/cache/git/ref/tags/v4 --jq '.object.type + " " + .object.sha'
gh api repos/actions/setup-node/git/ref/tags/v4 --jq '.object.type + " " + .object.sha'
gh api repos/shivammathur/setup-php/git/ref/tags/v2 --jq '.object.type + " " + .object.sha'
# только если type = tag:
gh api repos/ВЛАДЕЛЕЦ/РЕПОЗИТОРИЙ/git/tags/ХЕШ_ИЗ_ПРЕДЫДУЩЕЙ_КОМАНДЫ --jq '.object.sha'
```

2. В `.github/workflows/ci.yml` и `deploy.yml` замените тег на полученный хеш, оставив тег в комментарии, например: `uses: actions/checkout@<40-символьный хеш> # v4`.
3. Dependabot будет предлагать новые хеши вместе с обновлением комментария. Решение принято в `docs/DECISIONS.md` (D-061).
